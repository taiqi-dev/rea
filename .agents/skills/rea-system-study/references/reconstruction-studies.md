# 机制研究与独立规格

在用户要求深入算法、核心结构、伪代码，或明确要借鉴到自己的产品时读取。适用于不同软件系统，不将某个游戏、引擎或架构作为默认目标。

## 保持两条问题线

- 原目标：用户指定的行为如何发生；有哪些直接证据、推导和未知。
- 自研产品：用户实际希望支持什么；哪些能力需要自行设计，哪些约束尚未确定。

沿用已确认的范围、目标身份、输出位置和授权。追问新增一个子系统时，只扩展该问题，不重置既有结论或自动调查邻近产品阶段。只对会改变方案且不能从上下文推断的缺失信息提问；不要重复询问已确认的能力和许可。

原目标没有某个机制时可以提出独立规格，但在对应标题、公式和算例附近标明性质。不要只在全文结尾笼统免责声明，然后把自研算法写成原作事实。用户后来提供产品代码时，先读其真实契约，再判断是否采用研究建议。

## 从可见行为追到执行对象

详细解释按问题选取以下环节，补齐真正影响行为的连接：

1. 输入与选择：什么触发，候选从哪里来，目标与具体执行对象如何筛选。
2. 表示与所有权：设计定义、运行实例、当前状态、缓存、任务和进度分别由谁维护；同名或相似对象不自动共用身份。
3. 约束与执行：资格、资源、预约、冲突解决、执行顺序和结果提交。
4. 变化与失效：输入结构变化、控制者更换、取消、重复回调、异步旧结果怎样影响原方案；已提交结果与尚未执行的预测分开。
5. 观测与诊断：成功输出、拒绝原因、失败证据，以及哪些现象还需运行验证。

例如“选一个技能”应在确有多执行者时解释技能、目标、执行部件/工作者的联合关系；“数量”可能是容量、当前实例、预约或累计任务进度。先确认实际对象与作用域，再写公式，不能仅凭显示数字或字段名称合并它们。

## 伪代码与完整演算

使用自己组织的行为伪代码，不将恢复代码转换成生产实现。给出实际用到的数据字段、输入输出、状态转移和辅助步骤；声明未知函数，避免把所有关键逻辑藏进 `ChooseBest` 或 `UpdateEverything`。

每个请求模块给一个贯通例子：前置状态 → 输入 → 合法候选/分支 → 数值或状态演算 → 执行结果。需要解释结构变化时，沿用同一个例子展示变化前后和旧方案失效。无需为不涉及评分的系统强加评分表。

原作常数与构造参数分开。公式说明单位、计数作用域、聚合规则和资格过滤；不要默认多个部件、多个角色和多次事件都可以直接相加。事件或异步系统需要时说明版本戳、结果去重与预约提交，但不宣称仅靠示例的内存状态就能保证并发、联网或崩溃恢复。

对规则演算选择相称的验证：可执行算例核对算术和关键不变量，源码测试核对真实实现，运行观察核对目标行为。教学动画、示意网页和独立测试不建立原目标的参数、画面或算法等价性。纯文档编辑不自动触发项目全量构建。

## 面向后续开发的输出

用户要求分目录/模块文档时，按职责拆分并维护阅读路线；不要把所有续问不断追加到一个大文件。细则见 [报告与续查约定](study-delivery.md)。

自研建议说明与用户需求的对应关系、输入状态、约束和仍需验证的部分。没有用户产品仓库时交付可讨论的规格，不声称已适配其现有架构。后续实施采用自己的代码和适当授权资产。

若用户要求蒸馏调查经验，分别记录明确需求、助手操作问题、通用规则和目标专属内容；不保存原始对话或人格画像，不把同日的一次观察升级为所有项目的强制要求。项目技能更新按当前明确授权执行；全局个人原则另按其审核规则处理。
