# 最小部件库：AI资产、程序几何与导入契约

这是[Unity demo](README.md)的独立资产规格。Tiny Glade原网格只作为研究证据，不导入本demo。先用程序占位完成规则，再替换为我们生成或适当授权的资产。

## 1. 首版资产清单

| 自己的asset key | 来源 | 最小版产物 | 需要满足的条件 |
| --- | --- | --- | --- |
| `building.wall` | 程序 | 有厚度的墙面、洞口侧壁 | 长宽变化、多个洞/破损合并、碰撞同源 |
| `building.floor` | 程序 | 矩形楼板/地基薄盒 | 与建筑足迹同步，无重叠顶面 |
| `building.roof` | 程序 | 双坡厚屋面与山墙 | 随宽深高变化，有外/内/端面 |
| `building.beam` | 程序 | 带独立ID的0.12m梁 | 可燃、可破坏，长度改变不修改ID |
| `window.frame.small` | AI，程序占位可替换 | 外框，不含墙片或整栋房子 | 洞口净宽/高1.2m，支持面明确 |
| `window.glass.small` | 程序 | 独立薄面/薄盒 | 与窗框同原点，可单独关闭，不参与墙碰撞 |
| `lamp.shell.wall` | AI，程序占位可替换 | 灯壳及挂墙支架 | 挂点清楚，内部允许放入发光部分 |
| `lamp.emitter.wall` | 程序 | 灯内简单发光几何 | 局部中心清楚，开关与实际灯光同步 |
| `decoration.flowerpot` | AI，可选 | 精美装饰试件 | 不影响第一版墙洞/火水验收 |
| `surface.palette` | 自制材质 | 木/石/瓦/金属/发光/玻璃 | 共享色板，不依赖AI模型自带复杂shader |
| `effect.fire-water` | 程序或自制 | 粒子、颜色、调试标识 | 外观只读规则状态，不决定是否燃烧/受损 |

砖瓦逐块摆放放到基础几何验收后：首版可用颜色和少量程序倒角件表达砖/瓦节奏。可选AI砖/瓦模板须满足接缝和尺寸约定；不让首版依赖从AI整栋模型拆出几千块砖。

## 2. AI整栋房子的用途与边界

可用AI整栋房屋确定色板、比例、屋顶轮廓和装饰密度；也可以尝试提取已经完整的窗、灯或雕饰。它不能直接提供自由变化的墙长/屋顶算法、干净内壁、碰撞开口、可燃状态或稳定owner。

分割后可能只有原外表面的一部分；原本不可见的背面、墙厚、内部和材质连续性需单独检查。AI工具也可能猜测不可见结构，见[Meshy图生模型说明](https://help.meshy.ai/en/articles/9996860-how-to-use-meshy-image-to-3d)。当前工具有部件分割入口，例如[Tripo Mesh Segmentation](https://platform.tripo3d.ai/docs/editing)，但功能存在不保证任何房子都能自动转为合格建筑套件。

特别注意分割流程的输出用途：[Meshy Auto Split接口](https://docs.meshy.ai/en/api/auto-split)针对可打印部件，说明不保留输入纹理。不能将它默认当作保留游戏材质的拆模流程。选定工具后用一份自有资产先验证实际输出，不在方案阶段承诺某个账号/版本必然可用。

## 3. 给AI的部件要求

窗框生成要求可描述为：单个风格化木窗框、正视与侧视一致、框内净开口明确、无墙片/屋顶/背景、背面为平整挂墙面、玻璃另做。壁灯要求：单个挂墙灯壳、完整背板和支架、内部留空、无墙片/环境、发光内芯另做。

这些是生成方向，实际尺寸仍由导入工具校验和调整。不要只相信“低面数”“可用于游戏”等文字；必须读取实际网格、材质和边界。

## 4. 统一局部坐标和挂点

本demo统一1 Unity unit=1m，Y向上；附件局部X沿墙u、Y沿墙v、Z朝墙外。挂墙原点在背面中心的支持面；正缩放，不采用负缩放来翻面。

窗框：局部原点对应开口中心。外框可以比1.2m净洞口大，但净开口尺寸必须由独立元数据提供，不能用包含外框的整体bbox推导洞。局部Z=0为墙外表面；框的深入量及外伸量独立声明。

灯：`mount`在背板挂墙点，`emitter`在灯壳内部中心。Point Light的位置使用emitter锚点，不用猜bbox中心。生成器将整个附件沿外法线偏移0.01m以免共面；这是我们选择的默认值，可在资产验收后调整。

木梁：程序模板原点在首端，局部Y沿长轴；长度由生成器指定。梁是有状态的逻辑件；美术显示可以替换，永久损坏不会随模板更换消失。

## 5. 资产元数据和验收

每个正式部件记录：asset key、源文件、来源/可用许可记录、生成工具与可识别版本、原文件摘要、单位/轴向、挂点、开口净尺寸、材质映射、顶点/三角形数量、导入尺度和验收状态。缺来源或尺寸不明确时仅作草稿，不能静默成为生产资源。

| 验收项 | 检查方式 | 失败处理 |
| --- | --- | --- |
| 独立部件 | 从正/背/侧面查看，不含背景墙 | 裁切并补面，或重新生成该小件 |
| 几何有效 | 索引、有限坐标、法线、退化三角形 | 报告问题；修复后再导入 |
| 开口/挂点 | 用程序洞口或挂点基准叠合 | 调整pivot/尺寸，不能迁就错误洞形 |
| 面数/材质 | 实读网格与材质数，在场景中测 | 简化或重建；预算为自研目标而非工具保证 |
| 可见内侧 | 从可操作相机角度观察 | 补背面/厚度，不能默认双面解决全部问题 |
| 碰撞/交互 | 使用独立简化代理 | 不按精美外壳自动生成复杂玩法碰撞 |

首版美术目标预算：单窗框≤3000三角形、单灯壳≤3000，默认最多8个窗和8个灯/房屋。它们是可调整的内容预算，未证明帧性能。达到预算也仍需检查实际渲染与操作。

## 6. Unity导入与替换流程

优先接收能保留分件的常见交换文件；选定格式先验证Unity实际导入能力，不为GLB等格式偷偷添加未锁定插件。将资源转换到目标项目支持的FBX/OBJ或锁定的导入器后，建立统一Prefab：外观子节点、挂点、选择代理、asset key。

窗/灯外观Prefab不能拥有权威墙洞或火水状态；状态由运行模型管理。替换外观时保持逻辑ID、净开口和挂点契约，重新生成视觉与交互代理即可。

正式模型放未来Unity工程`Assets/BuildingSandbox/Art/Approved/`，草稿放`Art/Drafts/`；工具脚本放`Editor/`，不把它们长期留在Temp。带版权或未知来源的研究原文件不进入这两个目录。

### 构造验收例：AI窗框怎样接入

生成一份窗框，bbox外宽1.4m，但框内净宽仅1.1m。默认逻辑洞宽为1.2m，因此不能直接通过验收。保持逻辑洞契约：调整/重建框内开口到1.2m，或制作对应1.1m的新窗口类型并一并调整类型规格；首版优先调整该资源。材质外观与状态无关，不通过改墙洞去遮掩错配。
