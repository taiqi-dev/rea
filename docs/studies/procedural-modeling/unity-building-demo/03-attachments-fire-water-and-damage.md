# 窗户、挂灯、燃烧、灭火和破坏的统一流程

本篇是[demo](README.md)的自研规则。火水、永久损坏与支持清理没有被宣称为Tiny Glade机制。数据和几何职责见[02](02-building-geometry-and-cutouts.md)，发布/存档见[04](04-unity-runtime-save-and-rebuild.md)。

## 1. 命令先改逻辑对象

| 命令 | 权威状态变化 | 派生变化 |
| --- | --- | --- |
| PlaceWindow / MoveWindow / RemoveAttachment | 新建/修改/删除Attachment，保持移动前后的ID | 按owner替换窗口切口，墙/碰撞重建，框/玻璃更新 |
| PlaceLamp / ToggleLamp | 修改Lamp及enabled | 壳、内芯、选择代理与Point Light更新；无Cutout |
| Ignite | 指定可燃DamageCell或Piece，检查有实体/燃料/未破坏/不太湿 | 下一仿真步进入燃烧，显示火焰 |
| AddWater | 对目标增加湿度并降温 | 同步灭火/材质湿润指示，不生成流体几何 |
| BreakCell / BreakPiece | 完整度归零，Destroyed不可逆（Reset除外） | 墙开破坏洞或梁消失，支持/附件清理 |
| ResizeBuilding | 参数及revision修改 | 四墙/楼板/屋面/挂点更新，原损坏仍在 |

一次命令须原子验证后提交。失败显示CommandRejected(code, ownerId, explanation)，旧状态不变。重复command ID不重复放窗/加水；ID去重生命周期和存档字段由04规定。

初始Door只发布固定矩形切口，首版不生成门扇，不参加Window/Lamp的挂墙支持清理；它仍需在尺寸编辑时通过边界校验。梁锚定楼板，与挂墙装饰的支持资格不同。

## 2. 放置窗与拖动

普通点击用Solid层墙射线取世界点P，转换：`u=dot(P−O,e)`、`v=P.y−O.y`。Window仅接受外侧面命中；输入中心限制到有效域不是自动“吸附”，越界时显示候选红色并拒绝提交。

拖动已存在窗时先用Selection层识别AttachmentId，随后将鼠标射线投到**该宿主墙外平面**，再转换u/v并验证。即使鼠标经过旧洞的Air，也能继续拖动，不依赖必须命中残余墙三角形。

窗口支持检查用框四角外侧的小支持区域，检验对应墙面仍有实体；不把自己洞内的点作为支持点，也不让AI整体bbox决定洞宽。Window间重叠拒绝；破坏侵入支持区域后移除失效窗，记录SupportLost。移除窗会移除其派生切口，墙恢复的是未永久破坏部分。

框体、玻璃、选择代理属于同一个Attachment owner；切口由该定义派生交给宿主。更换框外观不会产生新切口或重新分配逻辑ID。

## 3. 挂灯、发光与支持清理

Lamp位置由`P(u,v,0)+0.01*n`与外观挂点确定；局部X/Y/Z对应e/up/n。外壳与内芯可在同Prefab分件，Point Light位置由emitter挂点给出。开关命令同时修改内芯发光和实际Light.enabled；装饰灯默认不向元素系统释放热量，点火工具另行控制，避免“开灯就自动烧房”。

支持区域是挂点周围0.12×0.12m矩形，必须完全在Solid墙面上。default lamp=(4.25,1.75)的支持区域为`[4.19,4.31]×[1.69,1.81]`。它不发布洞。

墙修改/破坏提交后重新检查支持：失效灯从逻辑Attachment集合移除；释放灯壳/内芯、选择代理、Light和所有缓存索引，并记录SupportLost。第一版直接移除，不做掉落刚体。正常移窗或尺寸编辑若会破坏附件支持，命令提交前拒绝；真实破坏不会被挂灯阻止，因此在提交后执行清理。

## 4. 损坏对象的稳定身份

墙DamageCellKey=(WallId,iu,iv)，尺寸0.5m，原点固定为该逻辑墙的u=0/v=0；不以当前生成Mesh、砖序号或GameObject名字为ID。每个单元可有部分面积被窗切掉，但窗口不会将它标为Destroyed。

梁使用独立PieceId=beam-01，锚定建筑楼板，不采用每次排板序号。它可单独燃烧、消失；首版不把去梁解释为屋顶必然坍塌。

永久Destroyed单元负责产生破坏切口；部分损坏单元仍有实体，可变色。房屋缩小导致单元暂时在域外时，状态保留；以后扩大仍保留旧损坏。窗盖住单元时，不给Air继续加燃烧损伤；该单元的剩余实体面积为零则停止燃烧并按冷却/干燥规则处理，状态不擦掉。

损坏网格与附件坐标都随逻辑墙u/v约定变化，首版选择“距墙起点的米数保持”，不承诺世界坐标保持。缩放/改高不拉伸格尺寸；合法附件留原u/v，越界的编辑整体拒绝。

## 5. 第一版火水模型

这些是可验证的游戏规则，非真实热力学或其它游戏恢复算法。石材不可燃；木材可燃。状态：temperature（示意摄氏度）、wetness∈[0,1]、fuel∈[0,1000]、integrity∈[0,1000]、burning、destroyed。初始20°C、湿0、燃料1000、完整度1000。

固定步长dt=0.1秒。Ignite合法时把温度提高到至少90°C；AddWater(amount=1)把湿度加1并clamp，温度降低60°C但不低于20°C。每步处理顺序固定：

1. 按命令序号应用所有外部命令，包括点火和加水。
2. 若Destroyed则不能点火/恢复；若实际实体面积为零，则burning=false。
3. 用当前状态判定可燃：木材、有实体、fuel>0、integrity>0、temperature≥60、wetness<0.6。
4. burning=true时，每步fuel−10、integrity−20；温度+1°C。
5. 所有未破坏状态向20°C冷却0.4°C，湿度降低0.005。
6. integrity≤0则归零，设Destroyed=true、burning=false，永久几何变更；fuel耗尽仅停止燃烧。

使用整数完整度/燃料保证每步损耗可精确比较；温湿度以明确容差检查。不会因为加水把完整度/燃料补回。命令应用后的湿度先参与是否燃烧判定，再做干燥，因此加水当步不会再偷偷扣一次燃烧完整度。

首版不做热传播、烟气、氧气、风、水流、冰电或材料配方。多个燃烧对象可以独立更新；以后传播应从前一步快照计算贡献再合并，避免迭代顺序造成先处理对象更强。

### 构造演算：灭火与彻底烧毁

从完好木单元点火，10步=1秒：integrity=800、fuel=900、temperature=96°C、wetness=0、burning=true。随后加水1并推进一仿真步：温度先降至36，湿1；不扣燃烧损耗，再冷却/干燥至35.6°C和0.995，integrity仍800、fuel仍900、burning=false。

这个湿单元立即点火应拒绝TooWet。等待变干或Reset后再验证。独立从完好状态连续点火50步=5秒：integrity=0、fuel=500、temperature=120°C，Destroyed=true。这里最后一步仍先更新温度再设置Destroyed；已Destroyed的后续步不再更新这些冻结数值。Reset明确恢复初始场景，普通重建/存档加载不会执行Reset。

## 6. 破坏洞与灯清理的贯通例

从移动后的window-01中心u=3开始，窗洞右界3.6。点燃north单元(8,3)：其破坏区域为`[4,4.5]×[1.5,2]`，与窗洞不相交。

单元完整度归零后：损坏状态先提交，几何生成器把该矩形加到开口并集，生成洞的内外边界/侧壁和新碰撞；lamp-01支持区域全部在洞内，移除lamp逻辑定义及所有产物。当前window-01仍有支持，保留。再调屋顶升高只更新屋顶，洞不会复原，灯不会回来。

若破坏碰到窗框支持，则先按当前附件计算失效列表，移除窗，重新派生开口和支持；重复到没有新失效附件。每轮至少移除一个，最多原附件数轮，避免无限循环。损坏切口不删除，原窗洞其它未破坏区域可以恢复为墙。单栋附件很少，先实现此明确规则，不做通用结构求解器。

BreakCell使用同一Destroyed提交路径；它只是直接将完整度归零。BreakPiece删除梁的显示/碰撞并保留Piece损坏状态。粒子碎片只作表现，不承担新的结构或存档身份。

## 7. 必须诊断的无效状态

包括宿主不存在、点火命中Air/石材/已毁/太湿、无效数字、窗边界或支持不合法、重复ID、缺asset key、光源遗留、碰撞revision落后于视觉。首版允许缺可选美术时回退程序占位，但必须显示AssetFallback(key,reason)，不能悄悄漏灯或漏窗。
