# Tiny Glade：槽 23 的后续写入、容量与 shadow 提交条件

承接 [81](81-tiny-glade-command-initialization-and-slot23.md) 的 460 B 初始零 payload 与 typed `DrawIndexedIndirectBuffer` 身份。本轮新增两个确定连接：**阶段字节 3 有实际的 shadow 图构造路径**；主 `gpu_generate_draw_lists` 两个分支把同一 typed 图句柄接入 `draw_indexed_indirect_to_dispatch`，该 shader 读取命令的 `instanceCount` 并写入另一份 dispatch 参数缓冲。前者仍要有第二个 shadow 项、非空且合格的墙条目、成功的资源绑定与图节点执行，才会走到槽 23 回调。后者不提供同一命令缓冲的四个非计数字段后续写者或扩至 ≥480 B 的确定路径，故不能将静态条件冲突定性为运行越界。

## 输入与读取边界

沿用 [81](81-tiny-glade-command-initialization-and-slot23.md) 已核验的同版 `tiny-glade.exe` 与相邻 PDB；地址均为 EXE preferred VA。针对 PDB 精确查询 `*DrawIndexedIndirectBuffer*` 得 12/12、`*render_bucket*` 得 1/1、`*draw_passes*` 得 323/323，均穷尽且未截断。定点 PE `E8 rel32` 候选再以 VS2022 `dumpbin /disasm /range` 的指令边界复核。新增原始输出在 `.cache/procedural-modeling/static-slot-followup/tiny-glade/`：`draw-indexed-symbols.json`、`bucket-symbols.json`、`shadow-construction.txt`、`bucket-callers.txt`、`render-world-entry.txt`、`render-world-early.txt`、`render-world-call.txt`、`drawlists-new.txt`、`buildlists-caller.txt`、`gpu-main-full.txt`、`cull-binder.txt`、`draw-to-dispatch-binder.txt`、`draw-indexed-to-dispatch.json/txt` 及各个 `*-lists.txt` 定点反汇编；复用 [77](77-tiny-glade-draw-callback-mapping.md) 的注册/回调证据、[79](79-tiny-glade-draw-command-slot-provenance.md) 的同键资源与槽计算，以及 [81](81-tiny-glade-command-initialization-and-slot23.md) 的 `draw-write-typed.txt`、`clear-lists.txt` 等。SPIR-V 文件使用已有 `tools/spirv_probe.py` 和缓存的 Khronos grammar 解析，所得 1 模块、83 指令、0 rejected。没有启动、附加游戏或读取私人存档；图执行、驱动提交和 FPS 均未观测。

## 阶段 3 如何进入 `render_bucket`

| closure 传桶与阶段     | 在该特化的 `0x141757260–269`，从第三捕获读 `i` 并要求 `i<3`；不满足跳过本段。`0x141757284–292` 从第一捕获取 `DrawLists` 的 `+8` 指针、`+0x10` 长度作为 `render_bucket` 的 `rcx/rdx`；`0x141757296` 计算 `i+2`，`0x14175729F–2AA` 写入第五实参并调用 `render_bucket` VA `0x140AF4DC0`。         | `i=1` 产生**实际可传的阶段 3**，而非只在墙回调内部假定该值。该闭包读取的是第一桶切片；其运行时内容未由此证明。 |
| 条目与最终回调         | `render_bucket` 在 `0x140AF4E00–08` 检查图资源状态，在 `0x140AF503C–51` 检查三处绑定且要求桶长度非零，随后以每条 64 B 处理。墙构造的循环组 `i=1` 若确实出现在此桶，仍需条目 `+0x20` 函数指针非零并通过绑定查找；[77](77-tiny-glade-draw-callback-mapping.md) 已证其 payload 为 `((1<<48)       | 0x10000000001)`，`indirect_draw_bricks`对阶段 3 才选择`r9=23`。                                                | **尚未证明**该墙实体在此图实例中必然入第一桶、存活且通过全部绑定；不能把循环构造数当实际 draw 数。 |

构造演算：若 shadow 列表至少两项，第二项令 `i=1<3`，closure 传给 `render_bucket` 的阶段是 `1+2=3`。再假设第一桶有一个通过绑定的循环墙组 1 条目，则其 payload 匹配阶段组号 1，回调选择命令槽 `0x17=23`，`indexed_indirect` 录制的字节偏移为 `23×20=460`。若第一桶长度为 0，`render_bucket` 在 `0x140AF5041–44` 直接跳过条目循环；若 shadow 列表不足两项，阶段 3 节点根本未在该循环建立。这是条件链演算，不是实测帧。

## 主 draw-list 表首项的传出与转换节点

`gpu_generate_draw_lists`（`0x1409B6690`）在 `0x1409B68E9–F7` 调用 `BufRef::fetch`，首个 20 B 返回字段落在 `[rbp-1Ch]`；[81](81-tiny-glade-command-initialization-and-slot23.md) 已将该首字段追至 typed `DrawIndexedIndirectBuffer`。`0x1409B6A60–64` 把 `&[rbp-1Ch]` 存入资源指针表 `[rbp+1C0h]` 的 `+0`。下表只列主函数里该**表首项的直接读取与整表传出**，不把其他局部变量恰好复用 `[rbp+4A8h]` 当作同一值。

| 主函数传出点                                                                                                                                                                                                                               | 首项的实际使用                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0x1409B6AF0–F6` `clear_draw_lists`、`0x1409B6BE8–EE` `prepare_empty_unsorted_draw_lists`、`0x1409B8201–0A` 再次 `clear_draw_lists`                                                                                                        | 整表作为参数；所查 helper 中前者按索引选其他表项，后者在 `0x1418C3CF5` 取 `+0x48`。不能据整表传参就断言首项被清零。                                                                                                                                                         |
| `0x1409B761D–24` 与 `0x1409B799B–A2`                                                                                                                                                                                                       | 两个分支**明确读取表 `+0`**，都暂存于 `[rbp+4A8h]`；分别在 `0x1409B770D–14`、`0x1409B7A8B–92` 放进 compute 参数块 `[rbp+320h]`，并由 `0x1409B774E`、`0x1409B7ACC` 调用同一个 `ComputeNode::bind_entry_point` VA `0x141796F90`。这是当前主函数内首项已证的直接 binder 路径。 |
| `0x1409B81B2–F9` `fill_instance_lists`、`0x1409B84A7–B1` `prefix_sum_unsorted_instances_per_atlas_entry`、`0x1409B84B6–F7` `allocate_draw_lists`、`0x1409B84FC–8523` `group_draw_cmd_prefix_sum`、`0x1409B8528–856A` `generate_draw_lists` | 整表再次传出。定点 callee 读取分别是 `+0x18/+0x28/+0x48`、`+0x28/+0x48`、`+0x28`、`+0x38`、`+0x18/+0x28/+0x40/+0x48/+0x50`；这些明确读取中没有 `+0`。其中 `generate_draw_lists` 还从 `+0x28` 连取 16 B。所列偏移是**指针表偏移**，不是命令槽偏移。                          |

`ComputeNode::bind_entry_point` 在 `0x141797071–82` 实际调用 `country_core::shader::nani::draw_indexed_indirect_to_dispatch` 的绑定器 VA `0x141A5F220`。后者从参数块 `+0` 取 typed 句柄并在 `0x141A5F2B0` 登记首个资源访问；从参数块 `+8` 取另一个图句柄，在 `0x141A5F393` 登记第二个资源访问。它还在 `0x141A5F401–41C` 写两个 push-constant 标量。发行包 `nani/draw_indexed_indirect_to_dispatch.precomp` 的 `draw_buffer` 为 set 0/binding 0，带 `NonWritable`（包偏移 `0x39C–0x3C8`）；`args_buffer` 为 set 0/binding 1（`0x3F8–0x408`）。shader 在 `0x5DC–0x5F8` 以 `push_constants.bucket` 索引 `draw_buffer` 的成员 1 `instanceCount`，`0x608–0x644` 计算 `(instanceCount+group_size-1)/group_size`，`0x678` 只向 `args_buffer` 存一组 `(group_count,1,1,instanceCount)`。例如假设某桶计数 37、组大小 8，则产出 `(5,1,1,37)`；这不是槽 23 的观测值。这个节点把同一命令缓冲**作为输入读取计数**，不会在本 shader 中写 `count/firstIndex/vertexOffset/firstInstance` 或替换 backing buffer。两个分支的运行选择、此节点实际是否 dispatch，仍依赖主函数控制流和图执行。

## 同一 typed 命令缓冲的写入与长度边界

`*DrawIndexedIndirectBuffer*` 的 12 个 PDB 命中仅给出该类型的 `add_new`、`new_storage_buffer`、图读/写及 finish 专门化、类型擦除和 drop；没有此类型的 `replace_with_data` 专门化。上轮完整 `*replace_with_data*` 19/19 也没有它。`write_rg_buffer<DrawIndexedIndirectBuffer>` VA `0x14152B6C0` 的 `0x14152B6E2–777` 以 typed `FrozenMap` 键取得 buffer 并 `GraphImportable::import_mut`，随后记录图句柄；这条**写租约取得路径**不做五字段 CPU byte update，也不包含 resize。`BufRef::fetch` 在 `0x140A92089` 将这一图句柄存入结果首个 20 B 字段，后续墙节点和 callback 沿 [79](79-tiny-glade-draw-command-slot-provenance.md) 的同键读写使用。

主 `gpu_generate_draw_lists` 的已查重置也不能补足模板：其 `clear_draw_lists` 读取资源指针表 `+0x20/+0x28/+0x38`，随后的显式 `GraphApi::clear_buffer` 在 `+0x08` 与 `+0x10` 之间选择；`DrawIndexedIndirectBuffer` 则是表 `+0`。这只排除**这两个直接入口**。已证初建仍是 `23×20=460` B 零 payload，槽 23 完整 20 B 命令需要字节区间 `[460,480)`；即便设备底层做分配对齐，逻辑图资源的最终长度及读边界仍须另证。缺失的具体桥是 **同一 typed entry 的 backing buffer 在构造后经何种 CPU 通用更新、图节点或其他写端填入 `count/firstIndex/vertexOffset/firstInstance`，以及其逻辑可用长度是否到 480 B**。未发现具名专门化不是排除内联、动态分派或 GPU writer 的证明。

**状态。** 阶段 3 的 shadow 索引生产、`DrawLists` 第一桶切片传参和进入 `render_bucket` 的条件，以及主 `gpu_generate_draw_lists` 的表首项到 `draw_indexed_indirect_to_dispatch` 的只读计数桥，为 **Answered（静态）**；墙循环组 1 是否实际进入该桶，以及槽 23 的四字段后续生产者、扩容和有效 draw 为 **Partial/未知**。游戏执行、GPU 捕获、FPS 与真实提交结果均为 **Not Run**。
