# 综合建造 demo：Steam Workshop、Mod 与 DLC 的独立设计建议

建议先做**建筑/地图作品分享，再做受约束的外观内容包，最后接正式 DLC**。三者共用内容注册与兼容检查，分别保留分发来源、使用权限和版本身份。可执行脚本、任意插件和自定义程序化生成器留到有实际需求时评估。

这是依据官方 Steamworks/Unity 文档和[四款游戏对照](122-mod-workshop-dlc-comparison.md)组织的独立规格，**没有检查或修改 `3DSandboxTest`，没有替该项目确定现状、批准实施或证明性能收益**。核对日期：2026-10-21，Pacific Time。下面所有目录、字段、状态和预算职责都是建议，不能当作原作实现。

## 先决定用户能创作什么

| 内容              | 第一阶段建议开放的输入                                                  | 游戏继续拥有的行为                             | 为什么适合当前目标                                                             |
| ----------------- | ----------------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------ |
| 建筑蓝图/整个场景 | 已支持的对象类型、稳定资源 ID、参数、变换、seed、版本及依赖清单         | 真实几何、开口、碰撞、地形编辑、合法性与保存   | 用户能分享完整作品，导入后仍走正常建造规则；不上传成套派生 mesh 来替代世界事实 |
| 外观主题          | 调色板、允许的材质参数、已有构件的配方和组合                            | Shader、渲染管线、实例布局、LOD 和投影阴影规则 | 内容多样性先沿既有批处理能力增长，便于约束性能                                 |
| 新装饰资产        | 作者工具生成的受限模型/贴图包，附 bounds、锚点、允许的材质族和 LOD 描述 | 选择/占用/碰撞描述的验证及现有命令             | 开放新美术而不要求用户编程；需要第二阶段额外制作与验证工具                     |
| 正式 DLC          | 官方主题/装饰/关卡包，绑定 Steam DLC App ID                             | 权限、版本检查及相同内容注册流程               | DLC 与免费主题不需要两套世界格式或渲染系统                                     |
| 新模拟/脚本插件   | 暂缓                                                                    | 编辑、存档、网络及运行生命周期的契约仍待定义   | 不能用“允许导入一个模型”推导出“已支持增加一种挖掘算法”                         |

## 一套内容系统，多个来源

建议数据流为：

```text
内置目录 / 本地作者目录 / Steam Workshop 安装目录 / 正式 DLC 目录
    → 各来源适配器提供候选包及来源事实
    → 解析 manifest、依赖与格式兼容性
    → 在临时内容目录中建立完整候选注册表
    → 检查依赖、ID 冲突、资源预算和 DLC 使用资格
    → 在安全边界发布不可变的内容目录版本
    → 既有命令、世界、生成器、渲染与存档读取同一目录
```

Steam 适配器只报告分发/安装/授权事实；不能直接向世界生成对象。内容注册表只解释资源；不能成为第二份库存、地形、世界时钟或存档权威。接项目时应先对齐现有注册/命令/保存入口，再选择最小扩展位置。

这里的“目录版本”是应用分配的世代号，供任务失效判断使用；**不是另行计算的摘要或内容指纹**。同一世界开始使用后冻结该世代，重载内容应在退出世界或明确的重载事务中进行。

## 稳定 ID、包清单与依赖

建议把作品身份、内容身份、Steam 分发身份分开：

- `packageId`：例如 `creator.harbor-kit`，与作者显示名和磁盘目录名无关。
- `definitionId`：例如 `creator.harbor-kit:lamp.round`，保存后不能因导入顺序或翻译改名。
- `packageVersion`、`contentRevision`、`schemaVersion`、`contentApiVersion`：分别表示作者版本、作者声明的修订、文件结构和可用内容接口；声明相同不证明文件相同。
- `PublishedFileId_t`：Workshop 发布条目 ID；跨 JSON/JavaScript 等边界按十进制字符串保存，避免把 64 位身份交给不能精确表达它的数值类型。
- `requiredPackages`、`requiredDlcAppIds`：世界、蓝图和内容包都能声明依赖；DLC 权限只接受平台适配器事实，不能由 manifest 自称拥有。

示例清单只表示拟议契约，不是已经实现的解析格式：

```json
{
  "schemaVersion": 1,
  "packageId": "creator.harbor-kit",
  "packageVersion": "1.2.0",
  "contentRevision": "7",
  "contentApiVersion": 1,
  "kind": "decoration-pack",
  "requiredPackages": [{ "packageId": "base", "compatibleMajor": 1 }],
  "requiredDlcAppIds": [],
  "definitions": "definitions.json"
}
```

同名 ID 默认报冲突；只有明确的替换声明才允许覆盖，且保存获胜包与版本。依赖先拓扑排序，环或缺失必需依赖则停在注册前；无依赖关系的顺序要确定，不能依赖目录枚举或下载先后。用户自行换一个显示顺序不应悄悄改变碰撞或资源身份。

Steam 的 Mod/应用依赖元数据属于软依赖，不能替代游戏的兼容和使用资格检查。分发 ID 与上面的应用内容 ID 也不能混成一种身份。[ISteamUGC：依赖接口](https://partner.steamgames.com/doc/api/ISteamUGC#AddAppDependency)

## Workshop 从制作到可用

采用可以直接下载使用的社区内容模式。先用本地作者目录走通同一验证器，再增加 Steam 上传/订阅适配器，便于排除“Steam 成功上传，但游戏根本不能加载”的假闭环。

| 步骤      | 平台入口/事实                                                                 | 建议游戏与作者工具承担的部分                                                    |
| --------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 配置      | Steamworks 启用 ISteamUGC 文件传输，配置预览所需 Cloud 配额与 Workshop 可见性 | 先在开发/测试范围准备首个可用条目，不把后台设置已保存当公开发布已完成           |
| 新建      | `CreateItem` 返回发布 ID                                                      | 保存 ID；区分创建失败、待接受协议、已有条目更新，失败重试不能每次重新创建       |
| 上传/更新 | `StartItemUpdate` → `SetItemContent`/预览/元信息 → `SubmitItemUpdate`         | 上传已经验证并冻结的候选目录；以成功回执作为完成，进度到末尾不代替成功          |
| 获取订阅  | 枚举订阅并读 `GetItemState`                                                   | “订阅”“已安装”“兼容”“已启用”分别显示；列表浏览阶段只读元信息和小预览            |
| 安装/更新 | `DownloadItem` 的异步结果、`ItemInstalled_t`、`GetItemInstallInfo`            | 核对 App ID/条目 ID 后重新核状态；更新中不读正在变动的文件；使用 API 返回的位置 |
| 加载      | 平台给出可读文件，不给出游戏语义                                              | 解析、依赖、预算和注册全部通过，才成为可用于新世界的内容                        |

上传流程、协议状态及后台前提来自 [Workshop 实施指南](https://partner.steamgames.com/doc/features/workshop/implementation)；安装状态、回调归属和安装目录来自 [ISteamUGC](https://partner.steamgames.com/doc/api/ISteamUGC#GetItemInstallInfo)。本次未操作 Steamworks 账号、创建/上传条目或订阅下载。

拟议下载状态为 `Discovered → WaitingForInstall → Validating → Ready`；验证失败保留原因，不能标成 Ready。异步回调只推进对应条目和请求世代；世界已切换或包已被替换时，旧解析/网格任务不能提交到新世界。退出页面、取消本地解析与取消平台上传是不同的状态；平台提交后的上传没有通用取消接口，UI 应如实显示。[上传生命周期](https://partner.steamgames.com/doc/features/workshop/implementation#Uploading_a_Workshop_Item)

Workshop 安装目录作为只读分发输入。生成缓存和用户编辑另有应用自有位置；不能往订阅目录写回修改，再期待 Steam 更新替用户合并。本地作者包与同 ID 订阅包同时出现时，由明确的作者模式/选择规则决定，不能静默双重加载。

## 更新与存档：先保住可恢复性

Steam 默认把条目更新传播给订阅者。当前官方还提供 SDK 1.60 起的按游戏 beta branch 关联 Mod 版本机制；这要求开发者维护分支、启用对应 Workshop 功能并提交兼容区间。它不是游戏自动获得的任意历史修订下载器。[Workshop Item Versioning](https://partner.steamgames.com/doc/features/workshop/itemversioning)

独立建议：在现有存档根里附内容需求记录，保留对象 ID、参数、seed 和不可解析条目的原始字段。保存的是采用的内容版本声明及分发定位，不能声称单靠版本文本就锁住原文件。未来需要完全可重放时，再定义被保留的许可内容副本、兼容分支与迁移政策；本阶段不承诺 Steam 会替游戏恢复任意旧版本。

| 加载遇到的问题                     | 建议处理                                                                                            |
| ---------------------------------- | --------------------------------------------------------------------------------------------------- |
| 缺一个只影响外观的装饰包           | 提示缺失并允许有标识的预览占位；保存时保留原条目，不能把占位写成新资源身份                          |
| 缺会影响碰撞、地形或程序化几何的包 | 默认阻止可写加载，保留原档；不能随意替成标准方块再覆盖保存                                          |
| 版本不兼容/定义被删除              | 展示包与定义级诊断；迁移先形成新候选存档，成功后发布，旧档保留                                      |
| 下载失败或 Steam 离线              | 已有内容是否足以加载由本地可验证事实决定；没有平台事实时显示未知/待恢复，不能把网络失败等同未购买   |
| 世界运行时订阅包升级/退订          | 当前世界继续用已持有的内容对象；在切世界/退出时释放。下一次打开重新检查，不在世界中途拆掉几何或碰撞 |

**构造例子**：蓝图 `harbor-house` 引用了 `creator.harbor-kit:lamp.round`；用户只有包 1.1，而蓝图要求 1.2。导入先得到“依赖不满足”，原世界保持不动。取得兼容包后，先解析并检查全部对象，再经既有命令/导入事务创建。若第 80 个对象失败，应恢复事务前的世界或完全不提交候选，不能留下 79 个对象后报“导入失败”。这里是建议验收行为，未执行运行测试。

## DLC：购买资格、磁盘内容与可用资源分别判断

Steam DLC 有自己的 App ID，可随基础文件分发并由游戏检查使用资格，也可放在只向拥有者分发的 depot。原声另有专门的应用类型，不能用“商店有原声”证明游戏做过可用建筑包的解锁与挂载。[DLC 官方说明](https://partner.steamgames.com/doc/store/application/dlc)

建议大型主题资源用独立 depot，小型公共外观是否全员携带由下载体积与联机政策决定。官方包使用独立目录和 ID，避免把 Steam depot 的文件覆盖顺序当成游戏的内容依赖解析器。[Depot 挂载规则](https://partner.steamgames.com/doc/store/application/depots#Depot_Mounting_Rules)

`BIsDlcInstalled` 同时检查拥有与安装，返回 false 不能区分“未购买”“尚未安装”等具体原因。`DlcInstalled_t` 用于通知 DLC 变为已拥有且已安装；通知后仍要检查包版本、文件与应用注册条件。它只是客户端条件，不能当作有价值服务端物品发放的授权凭证。[ISteamApps](https://partner.steamgames.com/doc/api/ISteamApps#BIsDlcInstalled)

DLC 本身的新程序能力仍随基础程序更新交付；主题包调用已经存在的内容接口。Workshop 作者引用 DLC 时上传依赖 ID 和自己的作品数据，不能把正式 DLC 资源夹复制进 Workshop 包。没有 DLC 的用户如何观看联机作品，是单独的产品政策：共同分发可见资源、外观占位或拒绝加入应选定一种，不能让无权限内容改写世界规则。

官方 DLC 指南仍描述基础 App 管理 depot；当前 Depot 页面另述可启用独立管理 DLC depot。实际制作时按当前账号后台和 SDK 核对，本文不固定“DLC depot 永远只能在哪个 App 下”这一存在文档差异的细节。[DLC 配置](https://partner.steamgames.com/doc/store/application/dlc#Configuration)、[Depot 配置](https://partner.steamgames.com/doc/store/application/depots)

## Unity 载体与性能边界

第一阶段的蓝图/配色/配方可以是普通结构化数据。新模型包若采用 AssetBundle，它承载面向目标平台构建的非代码资源；使用者需要匹配平台并管理资源依赖。它不是把外部 C# 放进包就能增加新游戏逻辑的机制。[Unity 6.0 AssetBundle 简介](https://docs.unity3d.com/6000.0/Documentation/Manual/AssetBundlesIntro.html)

对新装饰资产，建议由受控作者工具限制可用组件、材质族、贴图尺寸、mesh/LOD 和占用描述；首版不直接实例化任意作者 prefab，也不开放任意 shader/pass。具体打包方式及 Unity/渲染版本契约，要等项目正式接入时根据自己的依赖与平台选择；本研究没有替项目安装 Addressables 或导入库。

| 成本                   | 建议预算与失效边界                                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 订阅很多但世界只用少量 | 启动只建轻量索引；按世界依赖加载包，按使用对象持有资源，不把每个订阅项的全部纹理放入常驻内存                       |
| 材质/贴图打散实例批次  | 资产声明受支持材质族；能共享的颜色/参数作为实例输入；按空间与兼容绘制键组织，不能只按 Mod 名称拆批                 |
| 高面数、透明与阴影     | 作者工具给出三角形、贴图内存、透明层、LOD、caster 及实例上限诊断；数值由目标场景实测制定，不冒充原作或硬件通用阈值 |
| 程序化生成与导入尖峰   | 解析/验证可异步，Unity 对象创建和 mesh/碰撞提交按明确预算分段；任务带世界/目录世代，过期结果丢弃并释放             |
| 卸载与内存             | 由世界、预览与未完成任务共同持有引用；最后使用者离开后才释放，失败记录不能抹掉仍有持有者的资源                     |
| 静止时反复扫描         | 订阅/安装事件、显式刷新和切世界触发索引变化；正常帧只消费已有结果，不遍历文件树和重建目录                          |

AssetBundle 的跨包依赖及卸载关系应由一处管理，避免包 A 被卸载后仍有包 B 的对象引用其资源。[Unity：AssetBundle 依赖](https://docs.unity3d.com/6000.0/Documentation/Manual/AssetBundles-Dependencies.html)

## 最小可交付顺序与验证提案

| 顺序 | 可审阅产出                                                          | 必要的未来验证；本次均 Not Run                                                        |
| ---- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 1    | 用内置内容导出/导入一个建筑蓝图，含稳定 ID 和版本，复用现有世界权威 | 合法导入、坏文件/未知 ID、失败不污染世界、往返保存、撤销及缺依赖                      |
| 2    | 一个本地外观包，通过同一验证器增加配色/装饰配方                     | 冲突/环依赖、版本迁移、禁用后旧档保护、资源按需加载；固定场景与包规模测加载/帧时/内存 |
| 3    | Workshop 上传更新、订阅安装和启停状态的完整链                       | 两个测试账号；首次协议、失败/重复更新、下载中启动、离线、退订、并发更新及旧回调隔离   |
| 4    | 正式 DLC 主题包接同一内容注册，平台适配器独立判断资格               | 有资格未安装、无资格、已安装、运行中安装、未知平台状态；含 DLC 作品的保存与分享政策   |
| 5    | 规模增长后开放新模型包和高级版本分支                                | 制作工具兼容、渲染预算、多人若适用时的内容集合/权限一致性；旧档与回退分支             |

最先值得落地的是 **“一个无需 Steam 的本地包 + 一个可往返的建筑蓝图 + 缺依赖时原档保持可恢复”**。这会先验证内容契约，随后平台功能能接到同一条可靠加载链。它不是要求先做一个通用 Mod 框架，也不需要复刻四款游戏的全部内部系统。

- **自研建议**：内容目录、manifest、事务、存档保护、分阶段范围和性能准入；没有游戏或项目运行证据为这些设计背书。

- **待项目接入时决定**：实际 App ID、SDK/绑定库版本、现有内容注册位置、资产包载体、联机观看权限和性能阈值。本次不需要这些值便能完成调查，不猜测项目当前实现。
