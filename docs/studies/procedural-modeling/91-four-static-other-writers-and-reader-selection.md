## 两个优先问题收到了哪些答案

Tiny Glade 此前只接通墙 compute 对 `instanceCount` 的写入，现在找到另一种生产方式：CPU 静态表经暂存、图资源索引和设备录制路径进入同一 typed 命令资源。这修正了“未见完整模板”的旧证据边界。表并非全零：例如槽 16 是 `[900,0,0,0,0]`，槽 22 是 `[18,0,0,0,0]`；若复制先执行，再由相应 compute 增加一次实例数，槽 16 可演算成 `[900,1,0,0,0]`。这个算例有执行顺序前提，不是一帧观测。表总长仍为 460 B，槽 23 的 `[460,480)` 没有被包含。

容量方面，已定位的实际创建调用会走 460 B 空输入分支，460 B 也被传到底层创建信息；不是只有 CPU 上传长度已知。图句柄宽度、视图偏移、物理内存对齐和图记录容器增长都不构成扩容证据。下一条有判别力的边仍是**同 typed entry 或 raw handle 是否在生命周期中被替换**，及新描述符的大小。未闭合这条链前，不把初始容量写成最终容量，也不把条件槽 23 路径写成已发生的越界。

沙堡本轮排除了“reader 入口已经偏移 4 字节”的具体假说。文件类型表选择的直接 reader 从 GUID 首字节读取，末次读取对象 `+0x38c` 的零值后在 `+0x390` 返回；对象表终点为 `+0x394`，通用加载器因此进入不等长诊断路径。末尾 `03 00 00 00` 确属当前对象载荷，但从消费侧连接仍推不出构建侧字段。其生产来源继续标为 Unknown，不改名为 allowed、padding 或版本标志。

## 局部更新与性能结论的适用范围

SUMMERHOUSE 现在具有“遮罩 producer 先、主相机 consumer 后”的条件调度证据；Transform 父子关系与 URP Overlay stack 已分别核对，不能混用。原生是否把两者纳入当前列表仍未知，所以不能从静态排序推出每显示帧完整重画 2048²，也不能说只有建筑变化才更新遮罩。手动截图只明确绘制主相机，不能自动套用普通列表顺序。

掘地求财补出的默认复制入口会影响模式判断的时间点：原生 ctor 零值、CDO/模板属性、actor 反序列化和 renderer 重采样是不同阶段。普通 LoadConfig 的 bit14 门仍按[13](digging-a-hole/13-material-property-flags-and-config-gates.md)成立，但它不阻断默认对象复制。没有实际最终 CDO 值时，继续以条件分支解释单材质与 handler 的选择，不能把 constructor 初值升级为所有 chunk 的永久模式。
