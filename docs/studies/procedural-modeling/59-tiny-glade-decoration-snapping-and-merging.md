# Tiny Glade 窗户邻居协调、等级合并与写回

同一发行版中，窗户靠近已有墙装饰时，存在一条已确认的协调链：收集范围相交的邻居，尝试把两者的等级合并，查询合并等级的形状尺寸，调整目的地，再排除会与其它装饰冲突的方案。有效方案按目的地移动距离选择，最后写入既有目标的状态。

这补充[54的墙面投影与放置](54-tiny-glade-edit-picking-and-wall-placement.md)。这里确认的是等级资源替换和具体位置调整，没有证明自由浮点缩放、全局禁止重叠或通用物理推挤。

本机证据位于本会话可视化根的 `tinyglade-decoration-coordination/findings.md/json`、完整 listings 与 `verification.json`。新解码17个函数、9,274字节；28个细范围核对了原字节SHA256、PDB源行、指令边界和线性覆盖。caller复用前轮匹配证据。EXE/PDB全文SHA再次与既定身份核对；没有运行游戏，也没有把静态记录冒称为REA provider Evidence。

## 1. 候选来自当前墙内的装饰

`calculate_decorator_interaction_intent` 的 `14CA802–14CA8A6` 先检查一个caller传入的允许标志；非零才进入本邻居/合并链。它传入当前墙、候选的 `(s,y,w,h)`、当前ID和碰撞资源，实际调用 `24CC460 intersect_wall_decorators`。这个标志与具体按键/控制器模式的映射尚未完整确认，不能仅凭同址 `disable_snapping` 名称补写。

扫描对象是当前墙的 `Decorators` map。predicate先排除当前ID；邻居destination的raw tag为0或1才继续，为2跳过，更大的值在这个墙内容器协议下进入panic。碰撞描述由邻居的派生subtype和等级查得；缺资源进入panic。它没有查询全场景每个装饰，也不保证map遍历顺序就是屏幕距离顺序。

设候选为 `(s,y,w,h)`，邻居为 `(sn,yn,wn,hn)`。宽度来自collision的`+30`，高度来自`+3C−+38`。对有限有效输入，实际资格可整理为：

| 邻居raw kind | 先行垂直过滤 | 水平扩张量 | 垂直扩张量 |
| --- | --- | --- | --- |
| 2 | 无此额外过滤 | 0.2 | 1 |
| 其它 | `abs(y−yn) <= 0.3*hn` | 0.6 | 0 |

之后两项必须同时成立：

```text
abs(y−yn) < (h + hn + padH)/2
d(s,sn)  < (w + wn + padW)/2
```

线性墙的 `d=abs(s−sn)`；周期墙实际调用 `2A46110`，对已投影到一圈内的坐标：

```text
a = abs(s−sn)
d = min(a, abs(L−a))
```

这不是任意多圈归一化。周期判别来自 `24CC485` 的wallspace raw tag是否为1。第一项垂直过滤允许等号，最终两个相交条件都严格排除等号。代表证据为`24CCEC9–24CCF75`、`24CD0DF–24CD135`及`2A46110–2A46141`；小数是f32常量的舍入表示。

`901350 DecoratorType.is_window` 实际比较`kind<3`，所以0、1、2可按发行版自身的窗口资格描述；三者对应玩家看到的窗型名称没有恢复。当前范围不把raw kind2擅自命名成某种门或哥特窗。

## 2. 合并是等级求和，再查新形状

`14F7500 find_best_wall_decorator_merge_position` 对候选ID逐个调用`14F7A10`。内层确认该ID存在、其destination属于允许的墙分支，再核对主要类型：通常kind必须相等；kind6另外要求资源key相等。

两个`DecoratorInfo+59`字节相加，作为新等级`r`。`901330 max_rank` 的实际规则是：

```text
kind < 3 → 最大等级3
其它kind → 最大等级1
```

`r`超出上限时方案失败，返回raw tag8；没有把它截断到上限。通过之后，使用派生subtype和`r`查询新的collision描述，取新的`Wnew/Hnew`。因此不能把新宽度写成`w+wn`，也不能说游戏在这一入口自由连续拉伸窗口。它选择合并等级对应的资源形状。

类型、等级及资源查找的证据为`14F7B5F–14F7C74`、`14F7CDA–14F7D5D`。等级上限与窗口判定的小函数分别在`901330–901341`、`901350–901357`。

## 3. 新尺寸朝输入侧展开

对未附角的raw kind0/1路径，程序使用 `WallSpace.subtract(sn,s)` 的符号决定水平修正：

```text
若 subtract(sn,s) >= 0:
    new_s = sn − (Wnew−wn)/2
否则:
    new_s = sn + (Wnew−wn)/2
```

随后调用 `WallSpace.project`，失败则拒绝方案；周期墙沿该API的余数/包裹规则处理。对非周期直墙，这使增加的宽度朝输入侧延伸，同时保持另一侧边的位置。

该路径通常保留邻居的Y；raw derived subtype9另有：

```text
new_y = yn + (Hnew−hn)/2
```

不能把这个raw subtype名称直接补成普通窗。raw kind2跳过这段宽度差与高度修正，保留邻居中心。另一个 `WallCornerAttachment.is_attached` 返回真时也保留原中心/标志，不走上述调整。

代表范围`14F7DB2–14F7E9C`。这组公式证明了特定合并时的位置协调；它没有证明任意拖动都存在网格磁吸或其它装饰边缘对齐。

## 4. 用合并后的范围再检查第三者

程序以`(new_s,new_y,Wnew,Hnew)`实际调用`24CC760`进行第二次碰撞检查。此predicate先排除当前ID、此次合并目标ID以及caller提供的额外excluded列表，再对其它邻居执行前述范围资格。

如果仍有一条相交，`14F7F22–14F7F56`拒绝该proposal。排除两个参与者可以避免新形状把自己的输入或目标当成第三者；附加列表的完整上游用途未恢复。

这是合并方案的可用性检查。没有看到在这里移动第三者或反复推开窗口的规则；所有合并方案都失败时，caller回到[54的普通墙路径](54-tiny-glade-edit-picking-and-wall-placement.md)。所以“拒绝这个合并”不能扩写成“任何重叠都无法放置”。

有效方案的分数为：

```text
score = sqrt((new_s−input_s)^2 + (new_y−input_y)^2)
```

分数写入128字节proposal的`+7C`。`14F78EA–14F7915`只在新分数严格更小时替换当前方案，相等保留先到者，NaN比较进入panic。这里没有用周期差计算score，也不是已确认的屏幕或三维世界距离。输入候选顺序来自map扫描，未证明跨会话的等分选择稳定。

## 5. 合并结果确实写入状态

caller在`14CA94F–14CA9C8`接受非tag8的proposal，取新中心、新等级和目标ID，并在intent中保存：

```text
+40 = 1，表示选中该merge分支
+44 = targetID
+48 = newRank
```

UI在`86D680–86D715`据此构造change操作：`op+88=targetID`、`op+70=1`、`op+71=newRank`。实际调用链是：

```text
UI → apply_decorator_op
   → C402B0 DecoratorStorage.apply_decorator_change
```

不能把它与普通place分支合称为同一入口。`C40581/C40585`在rank修改许可下，读取`op+71`并写入主map目标的`DecoratorInfo+59`，建立了实际等级写端。

change还有两条存储路径：新storage raw tag为3时跳过迁移；否则先`C40314`移除旧目标，再取得目的容器，`C4037A → C8F970`按同一个targetID重新插入，然后继续参数更新。由此不能仅凭“同墙合并”假定完全原位更新。

`C40491`与insert内部`C8F9BB`都把目标ID加入`Decorators+60`的`HashMap<DecoratorId,()>`集合。底层`3B0DE0`找到相同ID时直接返回，重复标脏不会增加重复集合项。该集合接既有`iter_modified`读取端，供蓝图生成挑选修改对象；它本身没有清空所有窗的视觉实例。

主map已有ID时，`1407B18–1407B79`返回旧96字节记录并把新96字节写回。新插入情形另有全局ID→storage关联更新，缺预期关联会panic。移除、插入、标脏和参数修改之间没有建立原子事务或失败回滚保证，具体帧顺序仍未知。

## 6. 构造例：两窗合并，第三窗阻挡

以下是依据已核规则构造的输入，没有调用发行版函数。资源尺寸是演算选择，不能当作原游戏rank2窗的真实尺寸。

前置：尚未提交的候选ID100，raw kind0、rank1，中心`(4.1,3.1)`，collision尺寸`1.2×2`。同墙目标ID11同kind、rank1，中心`(4,3)`，尺寸`1.2×2`，未附角且subtype不是9。caller允许本链，exclude为空，非周期墙`L=10`。为演算指定rank2资源尺寸`2.4×2`，原modified集合为`{9}`。

1. `dy=0.1 <= 0.3×2=0.6`；最终垂直阈值为2，水平阈值为`(1.2+1.2+0.6)/2=1.5`。`dx=0.1`也通过，ID11成为候选。
2. 类型相同，`rank1+rank1=2 <= 3`，新资源提供`Wnew=2.4,Hnew=2`。
3. `sn−s=−0.1`，所以`new_s=4+(2.4−1.2)/2=4.6`，`new_y=3`。旧左边为`4−0.6=3.4`；新左边为`4.6−1.2=3.4`。
4. 二次检查排除ID100和11，其余为空。分数为`√(0.5²+0.1²)=√0.26≈0.509902`。
5. UI提交针对ID11的change，写rank2和新目的地。modified集合变为`{9,11}`；后续重复插入11不再增加元素，下游modified迭代可以挑选11。

本例的ID100尚未提交，不能由它推断移动两扇已持久化窗时怎样清掉另一ID或合并历史记录。

现在加入第三装饰ID12，wall destination、raw kind7，中心`(5.3,3)`，collision尺寸`1.2×2`且不在exclude中。二次检查的水平距离为0.7，小于`(2.4+1.2+0.6)/2=2.1`，垂直距离为0；该proposal因第三者相交被拒。ID12作为合并目标又因kind不匹配失败，最终没有合法merge。caller回普通墙路径，没有在此缩小窗口或挪走ID12的证据。

另两个边界：`rank2+rank2=4`会被拒，不截断到3；若第一轮水平距离恰为1.5，则严格相交条件不成立。周期墙`L=10,s=0.1,sn=9.9`时，资格距离为`min(9.8,0.2)=0.2`，周界两端可以相邻，但不能因此把score也改写为周期距离。

## 7. 可独立借鉴的规则与边界

自研可以独立采用：先收集局部候选，再通过类型/等级资源协议生成新形状；调整中心以保留一侧边；用新尺寸重新排除第三者；对合法方案按明确分数选择；最后将稳定目标ID加入集合，由产物生成器读取修改对象。

这是一份按发行指令重组的行为规格。自己的等级、尺寸资源、容差、失败后是否允许普通放置以及并发提交方式应按自己的产品需求设计，不携带目标的资源或恢复代码进入生产实现。

未做：未运行拖放场景、未验证控制器/按键映射、未恢复所有窗型UI名称、移动既有双对象的完整历史清理或全调度顺序。自由resize和更广磁性吸附仍未证明。

风险：把等级资源替换说成宽高任意求和，把merge失败说成全局重叠禁止，或把change与place生命周期合并，会产生错误的重建规格；正文和本机证据已分别限定。
