# 四款游戏：美术表现、局部更新与性能续查

本轮按 **SUMMERHOUSE → Tiny Glade → Sandcastle Demo → 掘地求财** 的顺序补缺口，各有两篇新专题。四款都新增了本地发行制品的语义证据，而非仅列可研究方向。最有用的共同结论是：**逻辑状态的修改范围、显示产物的重建范围、绘制时的筛选范围和保存范围，往往不同。** 不能用“局部编辑”直接推出每帧只处理局部，也不能用“异步”推出没有主线程复制、等待或数据积累。

这是截至 **2026-10-14 晚间 Pacific Time** 的静态研究。四款核心 EXE/程序集身份均与上一轮匹配；本轮实际使用的资源按原授权核对。未启动、附加或改写游戏，未读取私人存档，未将游戏代码、贴图或网格导入自研项目。

## 美术表现：四种生产方式的边界

**SUMMERHOUSE** 的强项是现成构件、局部惊喜和统一镜头风格。普通窗与人物窗复用主体和遮罩，后者额外增加人物与眼睛 Renderer。其可见复杂度来自 prefab 子对象、材质、纹理、颜色和低分辨率重绘；当前没有证据把它归为连续墙轮廓的通用建模器。默认相机接入像素化已在配置层闭合，但最终 blit shader 的取样公式仍未知。

**Tiny Glade** 把生成几何和着色进一步分开。砖实例有颜色 ID、seed 和 bevel 等输入，选定片元将颜色与法线打包，选定光照 shader 以相容格式解包。景深准备另用深度、焦点和分辨率生成带符号 CoC 及 tile 范围。这些是实际模块内的生产/消费，CPU attachment 绑定、完整 GI、接触暗部和后续景深合成还未贯通，不能把同名资源当作整条运行链已经验证。

**沙堡** 的水沙外观与格网状态紧密相连，但细节不都靠网格。原始水量在 `0.001–0.02` 区间完成湿沙色过渡；可见水面另用 `max(W−0.05,0)`。水体利用流动法线、屏幕深度/背景色、距离衰减和视角高光产生外观。所选片元没有证实真实场景倒影，完整混合状态和材质当前值仍未知。

**掘地求财** 除了体素地形，还有单独的矿物表现层。煤层候选的选定蓝图路径以三轴间距/扰动和层深生成位置，再添加 StaticMeshComponent、设置 cull distance，并在石/煤/铁网格间分派。煤矿网格的包外引用与实际 export 身份已连接；露出/掩埋判定、最终材质槽和玩家看到的频率未证实。不能把矿物网格等同于体素 mesher 的直接产物。

## 局部更新到底节省哪一部分

| 游戏        | 已证实的局部边界                                                                      | 局部操作之外仍可能发生的工作                                                                                  |
| ----------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| SUMMERHOUSE | 预览、刷色、高亮主要作用一个块；组合命中替换整个块实例                                | 放置事件的组合判定扫描已放置列表；启用网格辅助时，每次高亮新建/请求销毁线条，并作线对检查；像素化重绘指定层   |
| Tiny Glade  | dirty WallID 去重，相关对象清旧产物并生成/上传自己的实例                              | 绘制候选仍依据当前视图筛选、统计和写列表；未编辑对象也可能参与，不能只按本次新增砖数估计                      |
| 沙堡        | 画刷内条件决定哪些格子改值；碰撞轮到一个平面 chunk 才刷新                             | 通用 Dispatch 按该层整张 resolution 发射；读回取该层全部格数据；轮到的碰撞 chunk 逐顶点刷新，而非只刷附近顶点 |
| 掘地求财    | 影响盒选择 chunk；同类任务槽占用时不再启动副本；完成提交检查现存 chunk 和当前任务令牌 | 每 chunk 的 pending 数组仍可追加；旧 cook 取消未必马上停算，析构可能等待；保存处理当前全部修改叶块            |

这里没有统一的“最优实现”。SUMMERHOUSE 的事件查找成本、Tiny Glade 的几何/候选成本、沙堡的格网面积成本、掘地求财的任务与修改叶块成本，需要分别建模。

## 可以计算的规模，和仍缺少的实测

| 专题中的构造演算                                                                   | 它能说明什么                                                         | 它不能说明什么                                   |
| ---------------------------------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------ |
| SUMMERHOUSE：K=2 个 cell，至多 8 条高亮线、28 对比较                               | 条件启用时的对象创建和二次线对比较规模                               | 场景是否启用、GC 字节、帧耗时                    |
| Tiny Glade：两个被重建墙共 5 条砖记录，64 B/条即 320 B；另设 130 个绘制候选        | 实例 payload 与视图候选是不同的数量；候选覆盖至少需要 3 个 64 线程组 | 实际 dispatch、传输合并、总显存、FPS             |
| 沙堡：假设读回为 256² 格，32 B/格，即每次 2 MiB；名义 5 Hz 为 10 MiB/s             | 读回 payload 随格网面积增长，0.2 秒参数只是调度意图                  | 实际关卡分辨率、PCIe/驱动吞吐、完成时延与 stall  |
| 掘地求财：任务未消费期间同 chunk 收到 10 次通知，选定路径追加 320 B pending 记录体 | 任务启动受槽限制，但通知记录和回调仍可积累                           | 总堆占用、通知实际频率、最终删除时点与长期稳定性 |

以上全是明确输入下的指令/资源推导，**没有任何游戏的 FPS、帧时间、CPU/GPU 占比或峰值内存实测**。也没有做真实画面 A/B、连续挖掘压力测试、存档磁盘体积曲线或跨机器性能比较。

如果后续取得受控运行证据，最能补缺口的是：同一镜头/场景下记录可见对象和材质、各 pass 的 CPU/GPU 时间；连续编辑时记录脏对象/候选数、读回在途数和延迟、mesh/cook 在飞任务与旧结果丢弃、碰撞更新时间；保存时同时记录唯一修改叶块数、快照锁持有时间及压缩前后峰值。此处是尚未执行的采证规格，没有启动游戏或扩张当前授权。

## 证据、工具与迁移

新正式工具都放在研究目录，原始反汇编、参数表、蓝图投影和解析输出仍在仓库忽略的 `.cache/procedural-modeling/`。报告不依赖把缓存、PDB、游戏资源或分析器构建产物提交到 Git；换电脑时应先核对本地文件和版本，再按各页命令重新读取，不能仅靠同名缓存。

| 可复用入口                                                         | 范围                                                                                                 |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| [SUMMERHOUSE 资源链读取器](summerhouse/tools/visual_assets.py)     | 本次 Unity 2023.2.22f1 的选定 prefab/material/pipeline/camera 表，要求已有资源索引，遇到布局不符失败 |

SPIR-V opcode 数据来自 Khronos 的 [SPIRV-Headers 固定提交 JSON](https://raw.githubusercontent.com/KhronosGroup/SPIRV-Headers/86f980c731e62ae4eaf383d320449d71687936bf/include/spirv/unified1/spirv.core.grammar.json)，提交 `86f980c731e62ae4eaf383d320449d71687936bf`。本机缓存为 `.cache/procedural-modeling/followup-art-updates/spirv.core.grammar.json`，仅作为格式数据，没有安装新软件。一个可复现的景深读取例：

```powershell
python -X utf8 docs/studies/procedural-modeling/tools/spirv_probe.py "C:/Software/Steam/steamapps/common/Tiny Glade/compiled-shaders/country-core/compiled/dof/prepare.precomp" --grammar .cache/procedural-modeling/followup-art-updates/spirv.core.grammar.json --output .cache/procedural-modeling/followup-art-updates/recheck-dof.json
```

对应结果为 1 个模块、2529 words、478 条指令、没有 rejected 模块；这只确认当前读取器通过其结构检查。其它 precomp 的文件名、模块偏移与指令锚点见 69、70。各专题另列可复查原始位置与未完成项。
