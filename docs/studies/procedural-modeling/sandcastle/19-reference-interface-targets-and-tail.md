# 沙堡：引用映射接口的实际目标与尾部 `3` 的生产边界

**本轮静态进展**：找到一个会传入 `+0x88` 虚调用的非空 `context+0x38` 接口实例，其虚表首槽是 `0x1815c1430`。该实现按有序的 32 位键值对查找旧引用值，精确命中才把替代值写入候选输出；未命中时保留原值。它没有访问 SerializedFile 流。此实例在 `0x1815c18ee` 传给动态查得对象的 `+0x88`，但目前不能从静态输入证明这次动态选择必然是 class 129 `PlayerSettings`。因此已接通**一个接口实例、首槽实现和一个上层虚调用**，尚未接通“本作 class 129 实际走过这个实例”的最后一边。资源末尾 `+0x390=3` 的构建端 writer 仍未知。

## 接口实例到虚调用

只读输入仍为原安装 `C:\Software\Steam\steamapps\common\Sandcastle Demo\UnityPlayer.dll`；以下为本机 `dumpbin.exe` 对明确 VA 的静态反汇编，未经目标执行。调用者 `0x1815c14b0` 在 `0x1815c15f8–161c` 做三件事：把输入映射表指针 `r14` 保存至栈上 `[rbp+0x78]`；将只读表地址 `0x181f9a1d8` 写在 `[rbp+0x70]` 作为接口首指针；调用 `0x18120fb30` 构造 `[rbp+0xc0]` 的上下文，并以 `r8d=1` 设置 `context+0x6c`。构造函数的 `0x18120fb7e` 先把 `context+0x38` 置零；**同一调用者**紧接着在 `0x1815c1625–1629` 写入 `&[rbp+0x70]`，即 `context+0x38=[rbp+0xf8]`。这说明前篇 [18](18-transfer88-and-tail-production.md) 看到的零初始化不是所有调用现场的最终值。

PE 初始化节 `0x181f9a1d8` 的首个 64 位指针为 `0x1815c1430`；代码中指向该表的 RIP 位移候选只有 `0x1815c15ff`，并由上段 `lea` 核准。`0x1815c1430–14a5` 从接口对象 `rcx+8` 取得映射表；`[table]` 是 8 字节记录数组首址、`[table+0x10]` 是记录数量。它在 `r8d` 旧值上按 **有符号 int32** 比较做 lower-bound 查找；只有候选键等于旧值，才以该记录后四字节写 `[rdx]`，否则写回 `r8d`。返回值是输出地址。此实现不使用第四参数 `r9d`，也没有流游标或文件写入指令；它对该实例可见的作用是**内存引用值映射**。数组有序性来自该查找算法的前提，尚未对运行时每份映射表的排序有效性做观察。

在同一调用者 `0x1815c1660–16b6`，它从输入数组每条 8 字节记录的第二个 32 位值调用 `0x180067010`，结果保存为 `r15`。`0x1815c18dd–18ee` 以 `rcx=r15`、`rdx=&[rbp+0xc0]` 调用 `[vptr+0x88]`。所以这里的接收者**不是**附近 `lea r15,[0x18216d2d0]` 所指的固定全局对象：`r15` 已在 `0x1815c16b6` 被查找结果覆盖。前篇的 158 个 `FF /2 +0x88` 字节候选不能全归 class 129；本篇仅核准上述调用点及其数据流。

已证 class 129 虚表 `0x181eb1a30+0x88 → 0x180e63540 → 0x180e67200`（[14](14-player-settings-tail-owner-and-loader.md)、[18](18-transfer88-and-tail-production.md)）。**条件连接**是：若 `0x180067010` 在某次迭代返回这个虚表的 `PlayerSettings` 对象，那么 `0x1815c18ee` 将用上述非空接口调用其 `+0x88`，六处顶层资源引用及嵌套 `+0x128` 引用会交给 `0x1815c1430`。当前既没有实际迭代记录的对象身份，也没有把该输入数组第二项确定为 class 129 的静态资源记录；不能把条件写成已发生的调用。对照 `0x18122ba76` 的另一个真实 `+0x88` 调用，它的栈上下文经 `0x18120fb30` 后没有同样的 `+0x38` 非零写入，依旧不能借用此实例或当作 class 129 的证据。

**构造演算**：假设映射表有有序记录 `(7→11), (42→99)`，且某次动态接收者确为 `PlayerSettings`，其被处理的四字节引用成员当前为 `42`。`+0x88` 把 `r8d=42` 和候选输出地址传给接口首槽，查找命中后候选为 `99`；因本上下文 `+0x6c=1`，回调把 `99` 写回该**内存对象成员**。若成员为 `8`，lower-bound 找到键 `42` 却不相等，候选仍为 `8`。数值、映射表及接收者身份均是构造输入，不是本游戏观测值；这个例子不产生文件字节，也不触及对象末尾的 `3`。

## `+0x390=3`：本轮能区分的生产路线

本作 `globalgamemanagers` 的 class 129/pathID 1 对象为 `[0x4c0,0x854)`，共 `0x394=916` 字节。其文件相对 `+0x38c` 是 `0`，`+0x390` 是 `03 00 00 00`。[16](16-class129-reader-branch-and-tail-origin.md) 已把直接 reader `+0x90` 接到这个对象：它读前一值给内存 `allowedHttpConnections`，在 `+0x390` 返回；通用 loader 随后可走长度不等诊断。新发现的引用映射接口既不取这个资源流，也不追加尾字节，不能充当缺失的 writer。

| ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| writer 按另一种布局在 `allowedHttpConnections` **之后**写了额外四字节                 | 文件中确有完整对象内尾值；本机 reader/字段登记和精确版本公开 Release 树均在前一零值结束，未提供尾成员名称                                     | 本作所用 Editor/build serializer 的 class 129 写入次序，或同次构建保留的对象类型树 |
| writer 在末项**之前**写了一个额外四字节零槽，而 `3` 是构建侧 `allowedHttpConnections` | 字节长度和值在算术上相容；本机 reader 明确把 `+0x38c` 读作该成员，因此这只可能是写端与本机读端的布局差异，不能宣称已证                        | 构建端字段到 `+0x38c/+0x390` 的逐项写入证据及其配置输入                            |

这三项是**可检验的来源解释，不是原作已采用的三条实际路径**。发行安装内七份已解析 SerializedFile 只有这一件 class 129，且类型树均关闭（[17](17-tail-build-writer-and-profile.md)）；在当前限定的目标和缓存内无法用另一份同类对象消歧。`+0x88` remap 及 player reader 是消费侧，不会证明 Editor writer 的字段意图。尤其不能因值 `3` 与公开配置例子相同，就把它命名为 `allowedHttpConnections`。

## 后续更值得追的沙水问题

1. **实际湿沙/薄水过渡是否与美术阈值一致。** 已定位沙片元 `shader-605-0-05` 的湿色权重 `W≈0.001–0.02`、水片元 `shader-587-0-03` 的 `W>0.05` 可见水层，以及场景 Ground/Water 到 Material 20/41 的绑定（[05](05-surface-mesh-and-water-rendering.md)、[06](06-surface-materials-and-effects.md)、[08](08-material-bindings-render-state-and-invalidation.md)）。值得补的是不同 shader 变体、真实场景水量/相机条件及玩家画面是否让两道门槛形成预期的湿边；当前静态公式不能给最终视觉验收。
2. **局部笔刷到碰撞的延迟上界。** `Ground/Paint` 限制状态写入范围，但 `Compute.Dispatch` 仍按全网格发线程；`Readback.Draw` 以约 0.2 秒的累加间隔提交读回，`Ground.Run` 每偶数步轮换四个碰撞块（[07](07-local-updates-readback-and-costs.md)）。下一步应从已定位的 `Readback.Draw`、`Readback.<Draw>b__11_0` 与 `PlaneChunk.UpdateMeshCollider` 核算失败/重叠请求时的快照年龄，并在获得单独运行授权时测真实场景时延；目前没有实际帧时、GPU 完成时间或触碰反馈。
