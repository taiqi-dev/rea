# 沙堡：全局颜色写入端、材质覆盖与调用顺序

## 范围与结论

本篇续查 [23：湿沙到薄水](23-wet-sand-and-thin-water-transitions.md) 的颜色来源。目标仍为 `C:/Software/Steam/steamapps/common/Sandcastle Demo` 中的 `GameAssembly.dll`（47,654,400 B）、`Sandcastle_Data/il2cpp_data/Metadata/global-metadata.dat`（8,928,184 B）、`level0`（96,756 B）和 `sharedassets0.assets`（76,135,784 B）。既有身份摘要见 [01](01-artifact-and-method-map.md)，本篇没有新算摘要，也不以文件长度证明逐字节未变。所有新结果为本地只读静态派生，**不是 REA Evidence 或一次运行帧的读数**；条件未变的 Ghidra procedure 搜索超时未重试。

**已答的静态事实**：`Ground.Run` 依次向 `sandColor`、`sandColor2`、`wetSandColor`、`sedimentColor` 调用 Unity 的 `Shader.SetGlobalColor(string, Color)`；`Water.Run` 后续向 `waterColor`、`waterScatteringColor` 调用同一 API。值的 RGB 在调用前逐通道经过 `Mathf.GammaToLinearSpace`，alpha 直接传入。`Sand` Material 20 保存 `sandColor/wetSandColor`，`Water` Material 41 保存 `waterColor/waterScatteringColor`；但本次读取所选 Shader 的序列化属性前缀后，这些颜色**均不在 Shader 声明的两项 Properties 中**。同名 `m_SavedProperties` 键本身不足以证明材质会覆盖全局写入。

## 原生写入与配置来源

IL2CPP metadata v39 的 `Assembly-CSharp.dll` 中，`Configuration` 字段依次含 `sandParameters`、`waterParameters`；两种 `Parameters` 类型分别含 `color/color2/wetColor/sedimentColor` 和 `color/scatteringColor`。这是类型和字段**顺序**证据。原生 `Game.Instance` `0x18048ee50` 返回的对象 `+0xb8` 被 `Ground.Run`、`Water.Run` 读取为当前配置；[Game.Prepare](../../../../.cache/procedural-modeling/sandcastle/disasm/Game_Prepare_3d5.txt) 在 `0x18048bfe1–0x18048bffc` 把传入的配置放入这一字段，`Game.New/ResetConfiguration` 还有按所选 profile 向该配置复制参数的分支。故这里的生产者是**当前 Configuration 实例**，不等于某个 Material 对象中的同名颜色。

## 顺序、条件与材质取值

`Game.FixedUpdate` 在 `0x18048a936` 检查实例 `+0x34 == 1` 时跳过；其他路径在 `0x18048a953` 调用 `Game.SetGlobals`，再在 `0x18048a96a` 调用 `Beach.Run`。`Game.Run` 的另一入口也在 `0x18048d123` 先 `SetGlobals`，再在 `0x18048d13a` 调 `Beach.Run`。`Beach.Run` 先以 `beach+0x20` 调 Ground 的运行虚方法，再以 `beach+0x28` 调 Water 的运行虚方法（`0x18042802c–0x18042806a`）；两段 `Run` 又在颜色写入前分别以虚方法返回值作早退判断：Ground `0x1804500ca–0x1804500e2`，Water `0x1804833ed–0x180483405`。所以**若这一轮两个层都通过各自的运行条件**，六次写入的程序次序就是上表次序。相同的六个名字在这两段中各只写一次，彼此并无同名后写覆盖；其他潜在写端、Unity 内部命令缓冲及跨 `FixedUpdate`/Render 的准确帧次序未穷举。

`$Globals` 是所选 DXBC 的 constant buffer 名，与 `UnityPerMaterial` 的绑定类别不同；单凭常量缓冲区名称也不能读出某次 draw 的实际数值。Unity [6.0 `Shader.SetGlobalColor` API](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Shader.SetGlobalColor.html)说明：shader 需要而材质未定义的属性使用 global；该 API 自身不做颜色空间转换。Ground/Water 在 setter 前显式做 RGB 转换，与该 API 语义一致。[08 的实际场景链](08-material-bindings-render-state-and-invalidation.md)确认 `Ground → Material 20 → Shader 605`、`Water → Material 41 → Shader 587`；[材质重读](../../../../.cache/procedural-modeling/static-art-followup/sandcastle/materials-current.json)确认 Sand 保存 `sandColor=(0.925490,0.886275,0.725490,1)`、`wetSandColor=(0.906000,0.810376,0.633294,1)`，Water 保存 `waterColor=(0.960344,0.985799,0.999542,1)`、`waterScatteringColor=(0.568383,0.356864,0,1)`。这些首先只是 `m_SavedProperties` 序列化值。

[所选 Shader 属性前缀回执](../../../../.cache/procedural-modeling/static-consumer-followup/sandcastle/shader-property-prefixes.json)按既有 [605](../../../../.cache/procedural-modeling/sandcastle/graphics/shader-605-index.json) / [587](../../../../.cache/procedural-modeling/sandcastle/graphics/shader-587-index.json) 精确对象范围重读 `sharedassets0.assets`：605 起点 `0x2fc0e80`、587 起点 `0x2f34df0`；其 ParsedForm 属性前缀的 `+0x04` 均为两项，605 的名称为 `sandMap`（`+0x08`）与 `causticsMap`（`+0x48`），587 为 `refractionFactor`（`+0x08`）与 `waterNormalMap`（`+0x58`）。属性前缀分别至 `+0x90`、`+0xa8`，颜色名均不在该范围；如 `sandColor/wetSandColor/sedimentColor` 分别在 605 对象 `+0x164/+0x238/+0x178`，`waterColor/waterScatteringColor` 在 587 对象 `+0x2e0/+0x324`，属于后续 Shader 参数描述。与 [06 的 DXBC 绑定表](06-surface-materials-and-effects.md)交叉看，所选颜色是 `$Globals cb0` 参数；反例 `refractionFactor` 同时在 587 声明属性中、Material 41 保存值中、`UnityPerMaterial cb1[0].x` 中。这里的读取器是该确切版本与两个对象的固定布局核验，不是任意 Unity Shader 的通用解析器。

因此所选 shader 的六种颜色**没有“已声明的 Material 属性优先”这一前提**，即使其中五个名字出现在材质保存表。按 Unity 文档与上述静态调用，当前 Configuration 的 CPU global 写入是所选 `$Globals` 颜色的更有依据的来源候选；`sedimentColor` 连材质保存项也没有。然而本篇没有截取绘制时常量缓冲区上传、MaterialPropertyBlock、替换 shader/实际变体，也未穷举其他同名全局写端，所以**不能把 API 通则升级成这一帧 `cb0` 的赢家或具体值**。六次 setter 的先后次序已知，最终覆盖顺序只闭合到这些静态调用点。

**贯通条件算例（构造输入）。** 假设当前 Configuration 的 `sandParameters.color=(0,0,1,1)`、`wetColor=(0,1,0,1)`、`sedimentColor=(1,0,0,1)`，两个运行门均通过，且选用的 Sand 605 draw 在这些名字上没有其他写端或属性块覆盖。`Ground.Run` 的第 1、3、4 次 setter 分别把这三色写作 global；`Mathf.GammaToLinearSpace` 对此例的 0/1 RGB 不改变数值；之后 `Water.Run` 写两个不同名的 global。按 [23 的湿沙公式](23-wet-sand-and-thin-water-transitions.md)，在 `W=0.0105` 时干湿混合权重为 `0.5`，先得 `(0,0.5,0.5)`；若沉积混合权重再取 `0.1`，则得 `(0.1,0.45,0.45)`。这说明在**所述绑定假设下**全局生产者足以贯通所选片元两个混合阶段；纹理、光照与真实帧上传均未计入。它不使用 Material 20 的残留同名保存值，更不是游戏实际配置或截图颜色。Water 的两种颜色若也按上述已查属性前缀与 API 语义由 global 供给，[23 的透射公式](23-wet-sand-and-thin-water-transitions.md)应代入其当前 Configuration 转换后的值；本篇尚无可靠的场景初值与绘制提交来给出真实数值。

## 当前闭合度与复核

**Answered**：六个 setter 的字面量、实参来源、RGB 转换、Ground→Water 条件调用次序、所选 Shader 的两项声明属性及其与 Material 同名保存项、DXBC `$Globals` 的区分。**Partial**：当前配置来自所选 profile、`Game.New/ResetConfiguration` 可重置参数，但 `level0` 无 type tree；本篇未把场景里每一段初始序列化参数可靠映射为六个 Color 数值，也未证明首次绘制前一定经历哪条配置/FixedUpdate 路径。**Unknown**：实际帧内 global 与 MaterialPropertyBlock/变体及其他写端的最终冲突结果、GPU constant buffer 的每帧值。**Not Run**：游戏、Unity、GPU 抓帧、私人存档、目标函数和 Ghidra 重试。

复核只需对原有指令切片和新 JSON 逐项看同一 VA、slot 和 literal；[调用字面量读取器](tools/global_color_literal_probe.py)和[Shader 属性前缀读取器](tools/shader_property_prefix_probe.py)均为正式只读工具，拒绝覆盖已有输出。新缓存还含 [Unity 颜色 API 类型](../../../../.cache/procedural-modeling/static-consumer-followup/sandcastle/unity-color-types.json)与[方法映射](../../../../.cache/procedural-modeling/static-consumer-followup/sandcastle/unity-color-method-map.json)，均非 REA Evidence。最小下一步是给 `level0` 的 Game 配置及所选 profile 找到经类型/对象边界验证的序列化布局，再用实际提交或帧抓取验证全局最终绑定；本篇不以字段名或地址相似代替这两项证据。
