# 沙堡：启动配置到 Setup 改色的静态生产链

## 结论与身份

在所选 `level0` 的静态初值下，`Game.phase=0`。`Game.Awake` 的异步主体对非 `phase=4` 分支先调用 `ResetConfiguration(randomSeed)`，以新建的 `Configuration` 替换 `Game+0xb8`，再调用 `Prepare(Game+0xb8)`；随后另有 `New(Game+0xb8)` 的续行，`New` 会按选中的 `Refs` 表重拷参数并再次调用 `Prepare`。因此 `level0` 内联的六个零 `Color` 不能直接代入这条启动分支的 `Ground/Water.Setup`。这是**由序列化状态和指令控制流推出的条件路径**，不是已经观察到的一次游戏启动；异步续行、外部状态变更和实际绘制仍未知。`phase=4` 的另一分支跳过这段重建，稍后也有以当时的 `Game+0xb8` 调用 `New` 的路径，仍会先按 profile 覆盖颜色。

## 从场景值到当前配置

[25 的固定布局解析](25-profile-color-inputs-and-competing-writers.md)将 `level0` 的 `Game` GameObject `pathID=11` 连到组件 `pathID=476`，其 `profile=(2,8784)`、`refs=(2,8790)`；内联配置在组件 `+0xf4` 起，`seed=70255`、`sand=0`、`water=0`，六色均为零。该组件 `+0x34` 的 32 位 `phase=0` 见本轮[窄读取回执](../../../../.cache/procedural-modeling/static-producer-followup/sandcastle/scene-phase.json)；字段归属还由 metadata 的 `Game` 字段次序及 `Game.Awake` 对 `Game+0x34` 的 phase 比较支持。这里仍只证明文件里的初值。

`Game.Awake` 的本体 `0x18048a2c0` 创建异步状态机；[其 MoveNext 指令](../../../../.cache/procedural-modeling/static-producer-followup/sandcastle/Game_Awake_MoveNext.txt)在 `0x180499e47` 比较 `Game+0x34` 与 4。在非 4 分支，`0x180499ed5–0x180499ee2` 由 `Game.GetRandomSeed` 的返回值调用 `ResetConfiguration`；`0x180499ef7/0x180499f0e` 分别将新配置的 `format(+0x18)=2`、`resolution(+0x28)=1`，`0x180499f22` 把 `Game+0xb8` 交给 `Prepare`。`ResetConfiguration` 的[现有指令](../../../../.cache/procedural-modeling/sandcastle/disasm/Game_ResetConfiguration_3d3.txt)从 `0x18048ce03` 新建配置、在 `0x18048ce23` 替换 `Game+0xb8`，设置 seed、resolution，并按配置的 sand/water/waves 选择值复制 `Refs` 记录。所用 `Configuration..ctor` `0x18042d670` 只转入共享基类初始化，[定点片段](../../../../.cache/procedural-modeling/static-producer-followup/sandcastle/Configuration_ctor.txt)没有设置选择字段的指令；新对象的零初始化使该分支在无其他写入时选择表中第 0 项。新 seed 由 `Game.GetRandomSeed 0x18048aac0` 取自 `Game+0xd8` 的 RNG，**并非可直接等同于**场景里 `70255`。

异步主体 `0x18049a1e5–0x18049a1f2` 的一个续行将 `Game+0xb8` 作为 `New` 实参；`0x18049a5d9–0x18049a5e9` 另一续行也这么做。前者前面有异步等待与分支检查；后者又取随机 seed 写入该配置，故不能把所有调用合成一次无条件启动事件。`phase=4` 检查跳到前者附近，给出保留原有 `Game+0xb8` 再 `New` 的静态路径。另有 [直接调用候选回执](../../../../.cache/procedural-modeling/static-producer-followup/sandcastle/startup-direct-calls.json)在文件支持的 `il2cpp` 中定位 `Game.New/Prepare/ResetConfiguration`：Beach.Play、菜单载入/重启、设置重启等也可调用 `New`；本轮只把上述 Awake 两处和已有 Game 方法调用当作已由反汇编确认的指令边界。`Game.Load` 也可直接 `Prepare` 保存配置，未读取任何私人存档。

`Game.New 0x18048b820` 的[指令](../../../../.cache/procedural-modeling/sandcastle/disasm/Game_New_3cc.txt)将传入的配置保存在 `rsi`，在 `0x18048b906` 用其 `sand(+0x1c)` 选择 `Refs` 的沙表，并于 `0x18048b9a3` 后把参数复制进同一配置 `+0x2c..+0xdc`；`0x18048ba60–0x18048baa5` 依 `water(+0x24)` 将水表值写到 `+0xe0..+0x108`。`+0x10c` 的写入是 **waves**，不是水色，延续 [24/25 的勘误](24-global-color-writers-and-order.md)。`0x18048bb2f` 随后调用 `Prepare`。[Prepare 指令](../../../../.cache/procedural-modeling/sandcastle/disasm/Game_Prepare_3d5.txt)在 `0x18048bfe1–0x18048bffc` 把实参设置为 `Game+0xb8`；`0x18048c1d0–0x18048c1d5` 以当前配置 `seed(+0x10)` 调 `UnityEngine.Random.InitState`，`0x18048c1ef` 调 `Beach.Setup`。方法身份和下面随机/颜色 helper 的精确映射见[回执](../../../../.cache/procedural-modeling/static-producer-followup/sandcastle/setup-color-math-with-seed.json)。

## Setup 的两种改色行为

`Beach.Setup` 的[扩展片段](../../../../.cache/procedural-modeling/static-producer-followup/sandcastle/Beach_Setup_extended.txt)从 `0x1804281e6` 开始依次经虚表调用 `beach+0x20`、`+0x28`，对应既有层次证据中的 Ground、Water；两者没有通过空检查时会进入错误路径。这里能给出**条件成立时**的 Ground→Water 顺序，不能把虚调用存在说成已运行一次。`Prepare` 每次到达这一步都会重播 Setup。Ground 与 Water 写的是不同名字，六色之间没有彼此覆盖；各自 Setup 与 Run 写同名 global。

`Ground.Setup` 的[完整指令](../../../../.cache/procedural-modeling/sandcastle/disasm/Ground_Setup_full.txt)在 `0x180450a4b–0x180450a84` 从当前配置 `+0x2c/+0x3c/+0x4c/+0x5c` 拷四个 Color 到本地副本。`0x18045107f–0x1804510c5` **只抽三次** `Random.Range(-0.02,+0.02)`，将同一组扰动分别加到前三个颜色各自的 HSV 三分量（H/S/V），逐项钳到 `[0,1]` 后 `HSVToRGB`；第四个 `sedimentColor` 保持拷贝值。`0x180451386/13e1/1444/149f` 再将四个本地 Color 的 RGB 经 `GammaToLinearSpace`，写 `sandColor/sandColor2/wetSandColor/sedimentColor` global。该方法在所查配置到 setter 路径上**没有把这些扰动色写回 Configuration**，所以后续 `Ground.Run` 仍会从原有四个配置色计算并覆盖四个同名 global。

`Water.Setup` 的[完整指令](../../../../.cache/procedural-modeling/sandcastle/disasm/Water_Setup_full.txt)先读当前配置 `+0xe0`，`0x1804844c2` 做 `RGBToHSV`；`0x1804844ec/452c` 独立抽两次 `Random.Range(-0.01,+0.01)`，分别扰动 H、V（S 不变），钳到 `[0,1]` 后 `HSVToRGB`，`0x18048459d` **写回配置 `+0xe0`**。第二色从 `+0xf0` 另做相同的两次抽样及 H/V 变换，在 `0x180484662` 写回 `+0xf0`。随后 `0x1804846d3/4742` 由**写回后的**两色经 RGB gamma-to-linear 转换写 `waterColor/waterScatteringColor` global。因此若同一个配置在没有 `New/Reset` 重新拷 profile 的情况下重复 `Prepare`，水色会以已扰动的配置色再次变换；若先经 `New/Reset`，两色先被表值覆盖再变换。`Prepare` 会按配置 seed 重新初始化 Unity 随机状态，但其间调用的完整抽样序列未逐项封闭，不能宣称两次扰动必相同。上述随机范围、helper 身份及字面量来自本轮[数值回执](../../../../.cache/procedural-modeling/static-producer-followup/sandcastle/setup-color-math-with-seed.json)与 `0x18048448a–0x180484742` 指令，不是采样结果。

具体的**条件演算**：若配置选择 `sand=0/water=0`，`Refs` 的 [25 表](25-profile-color-inputs-and-competing-writers.md)使 `Game.New` 把 `sandColor=(0.925490201,0.886274517,0.725490212,1)` 放到配置 `+0x2c`，`wetSandColor=(0.789000034,0.759226441,0.647575498,1)` 放到 `+0x4c`，把 `waterColor=(0.898039222,0.972549021,1,1)` 放到 `+0xe0`，第二水色 `(1,0.494117647,0.262745112,1)` 放到 `+0xf0`。例如某次 Ground 抽样若是 `(u_H,u_S,u_V)=(+0.01,-0.01,0)`，对每个前三色分别计算 `HSVToRGB(clamp01(H+0.01),clamp01(S-0.01),clamp01(V))`，但配置里的四个沙色仍保留表值；某次 Water 抽样若两色分别取 `(+0.005,-0.005)`、`(0,+0.005)`，则各自计算 `HSVToRGB(clamp01(H+u_H),S,clamp01(V+u_V))` 并回写两个配置槽。四个抽样值均在指令给出的区间内，**是构造例，不是目标抽样**。在下一次对应 `Run` 通过运行门且没有其它写端时，Ground 的四个 global 被 `G(配置沙色 RGB)` 覆盖，Water 的两个 global 被 `G(已扰动配置水色 RGB)` 覆盖，alpha 沿调用的第四分量传递；`G` 是 `Mathf.GammaToLinearSpace`。这解释了 Setup 的沙色短暂 global 与 Run 沙色、以及 Setup/Run 水色所共享的**被修改配置**，没有给出某一帧最终像素或 GPU 常量。
