# 四款游戏：静止场景仍做什么，哪些条件能省下工作

这轮从 **Tiny Glade 的稳态渲染**开始，继续读取四款发行制品的具体分支。最有用的新结论是：**几何重建、视图绘制、持续模拟、异步完成提交有各自的触发条件，不能用一个“场景没变化”概括。** 参考游戏也有持续计算；它们控制成本的方式，应按这些职责分别学习。

用户已补充：自研项目在 Editor Game 视图静止时也约 10 FPS；最新指令要求先研究参考游戏。本轮没有读取该项目规范、源码、资产或日志，没有连接其 Editor，也没有采样或修改它。10 FPS 仍只是用户报告，不能在没有同条件测量时归因给某个模块。

## 最值得综合 demo 借鉴的三个层次

第一层是保留生成结果。已经形成的建筑、地形块、实例数据不应因为画面又过了一帧就全部重新生成。Tiny Glade 的持久实例和局部失效、掘地求财的块任务/完成队列提供了不同实现例子。**自研建议**是明确哪些逻辑状态变化使哪份表现失效，按建筑或空间块去重；这不是声明四款都采用同一种脏标记。

第二层是控制持续工作的规模。Tiny Glade 仍筛选视图候选，并分别处理阴影；沙堡的积分和固定水处理仍可覆盖全层格网；SUMMERHOUSE 的较小目标仍有重绘和反射回调。**自研建议**是分开记录候选实例、提交条目、阴影视图、像素数量、模拟格数和子步数。批量实例主要改变表示与提交规模，降低分辨率主要改变像素工作，二者不能代替局部重建。

第三层是限制完成后的主线程工作。掘地求财有空队列门和工作单元之间的时间检查；沙堡降低读回请求频率并轮换碰撞块。**自研建议**是为网格应用、碰撞更新、读回消费各设可观察队列与预算，明确旧结果是否仍适用。后台计算结束不等于提交免费，单元间检查截止时间也不保证重型单元可以被中断。

构造演算（非任何原作参数）：假设一帧没有编辑，建筑重建数可以为 0；但若场景有 20,000 个候选实例、3 个阴影视图，仍可能有多视图筛选；若水格网为 256×256、每次三个全域 kernel，名义线程格处理量至少为 `3×65,536=196,608`，另算每组向上取整、子步与片元。另一方面，空完成队列可让提交数保持 0。这个例子说明“静止”并不把四类成本一起归零；它不是时间模型，也不证明哪个游戏更快。

本机 ignored 原文统一在 `.cache/procedural-modeling/steady-performance-followup/`，按四款分目录。正式探针为 [Tiny](tiny-glade/tools/steady_render_probe.py)、[沙堡](sandcastle/tools/steady_budget_probe.py)、[掘地求财](digging-a-hole/tools/idle_tick_probe.py)，SUMMERHOUSE 复用既有离线 CIL 读取器。各专题列出函数、token/地址、分支、解析覆盖与构造例；新探针与同轮回执支持静态核对，具体检查数分专题保留，不把交叉检查累加成独立测试总数。

本轮核对通过：10份Markdown的271个本地链接、3个新Python读取器的语法、构造算术，以及Tiny的37处原生调用/指令/分支/字符串站点与3个shader模块结构。沙堡41处文本站点在匹配DLL身份下复用；掘地求财27项、SUMMERHOUSE25项focused检查分别通过。新读取器拒绝覆盖已存在回执。仓库 `docs:check` 通过（6项任务，其中5项缓存；README一致性5个测试通过）；这些检查都不建立运行性能结论。
