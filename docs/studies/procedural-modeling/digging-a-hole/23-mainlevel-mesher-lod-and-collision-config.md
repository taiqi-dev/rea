## 从初值到实际选择门

`FVoxelRendererSettingsBase(AVoxelWorld const*)` 于 `0x143E4F479–0x143E4F480` 将 `world+0x57C` 拷到 renderer settings `+0x4D`。[21](21-lod-seams-and-transition-mesh.md)已核 `FVoxelMesherAsyncWork::GetMesher` (`0x143EE3760–0x143EE3A44`) 对值 `0/1/2` 分别进入 Marching Cube／Cubic／Surface Net；本实例静态值 `0` 因而落到普通 Marching Cube，过渡任务落到 `FVoxelMarchingCubeTransitionsMesher`。`bEnableTransitions` 不是仅有字段名：`FVoxelLODSettings` 构造于 `0x143E4E72D–0x143E4E734` 把 `world+0x5B0` 复制到 LOD settings `+0x4C`；同函数 `0x143E4E737–0x143E4E741` 把 `RenderType==2` 的布尔结果写到 `+0x4D`。`IVoxelLODManager` 构造 `0x143E4FA55–0x143E4FA60` 再把两字节复制到 manager `+0x6C/+0x6D`。`FVoxelDefaultLODManager::UpdateLODs` 于 `0x143E9A089–0x143E9A096` 把它们带进 `FVoxelRenderOctreeSettings+0x35/+0x36`；[21](21-lod-seams-and-transition-mesh.md)的 `GetUpdates` 在 `+0x35` 门后才作过渡方向判定，`+0x36=0` 时比较 `neighbor.L < current.L`。所以静态初始链的值是 `(+0x35,+0x36)=(1,0)`，并非[21]构造例里未定的假设值；仍须有可见邻节点、盒交集、当前 chunk 和任务接受。

碰撞配置也经过明确的 writer。[本轮 `AVoxelWorld::CreateWorld` 原文](../../../../.cache/procedural-modeling/static-config-followup/digging-a-hole/world-create.disasm.txt)在已创建门未触发时，于 `0x1441D265F` 将 `world+0x8BC` 写零后调用 `CreateWorldInternal`。后者于 `0x1441D2B47` 调 `UpdateDynamicLODSettings`，并在 `0x1441D33C1`／`0x1441D34BB` 构造 renderer／LOD manager。`UpdateDynamicLODSettings` (`0x1441DF87A–0x1441DF8E6`) 在该零模式下将 `world+0x628`、`world+0x7AC` 分别写入动态 settings `+0x11/+0x12`，并把 `world+0x7B0` 限制到 `0..25` 后写 `+0x14`。本实例得 `(enable collision, visible collision, visible max LOD)=(1,1,2)`。若走另一个非零 play type，函数会强制两开关为 `1`、max LOD 为 `25`；不能把零模式的覆盖结果推广到预览／其他创建入口。`UpdateDynamicLODSettings` 是一处后续可再运行的 writer，因此运行中重配仍属未知。

`FVoxelDefaultLODManager::UpdateLODs` (`0x143E9A099–0x143E9A0C5`) 将动态 settings 的 `+0x11/+0x12/+0x14` 放进 octree settings `+0x37/+0x38/+0x3C`。`FVoxelRenderOctree::GetUpdates` 在 `0x143E7ACF3` 检查 `+0x37` 后，可凭有资格的专门盒相交置碰撞 bit `0x02`；另一支在 `0x143E7AD8A–0x143E7ADA9` 检查可见块碰撞 `+0x38`、当前节点可见 bit 和 `node.L <= settings+0x3C`，符合时也置 `0x02`。因此 `LOD 2` 可走可见块碰撞上限门，`LOD 3` 不走这个**可见块兜底**，但专门碰撞盒分支及其他门仍可能给它碰撞资格。`0x02` 随 chunk 更新进入[08](08-mixed-handler-submission-chain.md)的 Mixed Basic 碰撞支路；[22](22-transition-triangles-and-collision-ownership.md)已证明在 transition buffer 等后续条件成立时，过渡索引进入 Chaos cooker 所读主索引 buffer。此处不重复该合并链，也不把开关 `1` 等同于某次碰撞 cook 成功。

**静态构造演算。** 取[21](21-lod-seams-and-transition-mesh.md)的 LOD 2 当前块和 LOD 1 正 X 邻块。主关卡初始 `RenderType=0`、`bEnableTransitions=1` 使 octree 的过渡设置为 `(1,0)`；若可见、查询盒相交且节点/任务门通过，`1<2` 置正 X mask `0x02`，过渡工作选择 Marching Cube transition mesher。若该 LOD 2 chunk 同时符合可见块碰撞条件，则 `2<=2` 可置碰撞 bit；同一材料的普通与过渡 buffer 被接受后，依[22]进入碰撞构造。把当前块改为 LOD 3 时，`3<=2` 为假，不能只靠可见块碰撞兜底取碰撞 bit；其余碰撞盒路径、实际邻块和 cooker 后态仍需各自证明。这是数值和控制流演算，不是游戏内场景或碰撞实测。

**Answered（静态）**：MainLevel 的实际序列化覆盖 `VisibleChunksCollisionsMaxLOD=2` 和物理材质引用；模式／开关缺席后的原生构造写入及正常 settings 路线；`RenderType=0` 对应 Marching Cube，过渡开关与比较方向；零 play type 的碰撞开关和 LOD 上限到 chunk flag 的条件链。**Partial / Unknown**：CDO 或 actor 可能的特殊加载／后写入、游戏是否加载此关卡、每块实际 LOD／邻对／材料 buffer、碰撞盒来源、Chaos 最终形状与物理接触连续性。`bEnableCollisions=1` 等字段是静态初始配置推导，不是运行内存观测。**Not Run**：游戏启动／附加、目标函数执行、私人存档、GPU／物理现场、Ghidra 重试、外部软件安装。
