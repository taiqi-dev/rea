# 下一轮静态建议：先补提交边界，再转向美术质量与更新成本

依据[104：本轮四条链](104-four-static-waits-restoration-schedules-and-subscriptions.md)，建议下一轮按下表取一个有边界的切片。以下是**选题判断和独立设计问题，不是已经确认的原作机制**；没有因列建议而启动目标或扩展本轮调查。

## 优先顺序

| 顺序  | 题目与明确入口                                                                                                                                                                                                       | 一片内的完成标准                                                                                                                       | 停止条件／仍需运行的部分                                                                         |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **1** | **沙堡：buffer释放与旧请求是否真正汇合。** [22](sandcastle/22-native-readback-wait-cancel-boundary.md)的DestroyBuffer `0x180F6CF40`、资源虚槽+2E0与请求等待虚槽+8C0。                                                | 先恢复一种具体资源／设备虚表类型，连接销毁→等待／取消／延后释放；另核3996项表的注册消费者，提升接口配对的证据等级。                    | 若只有泛型虚槽、无类型写端，不继续靠字符串或接口名推断。GPU fence、线程并发和实际延迟仍需运行。  |
| **2** | **Tiny Glade：给三个具体system补上调度归属。** [103](103-tiny-glade-snapshot-run-conditions-and-deferred.md)的load包装`189B4A0`、Public `1E3AE0`、砖`1C3900`。                                                       | 从注册对象恢复in_set／run_if，定位executor中ApplyDeferred与消息维护相对节点；交付实际条件表，而不是再枚举阶段标签。                    | 只有包装参数获取门时保留Partial；未找到具体注册对象就不宣称同帧。画面稳定和GPU完成另证。         |
| **3** | **掘地求财：placeable的独立更新，以及载入刷新是否放大。** [20](digging-a-hole/20-partial-restore-lod-mesh-collision.md)的AddItem `0x143E33E80`、IterateTreeInBounds及监听者，旧树终端盒→GetChunksToUpdateForBounds。 | 查明placeable是否产生本次变化盒数组之外的通知；解释旧根覆盖导致多少类现存chunk候选、多个盒是否去重／合并，区分通知范围与最终提交范围。 | 不按静态盒数量估FPS；实际LOD分布、重复任务和峰值仍未测。没有新通知边就明确保留Unknown。          |
| **4** | **SUMMERHOUSE：共享变量跨场景寿命与剩余启停目标。** [21](summerhouse/21-listener-writers-and-repeat-subscription-reachability.md)的LoadSceneCoroutine、28个SetActive调用方法及四个SharedVariable资产。               | 追仍持有变量的对象／资源引用边，选一个真实启停调用者把接收GameObject接到粒子祖先或明确排除；分别判定同实例重复Add和销毁旧条目残留。    | 不再重复Add／退订IL；只凭scene资源pathID相同不能证明实例存活。所有动态调用及实测回调数仍需运行。 |

这是按本轮新入口和信息增益排序，不表示已发现四款游戏有相应故障。沙堡首次接到具体native请求层，值得优先追一个实际虚表；Tiny Glade要补的是具体注册对象，重复阶段名搜索价值已低。掘地求财和SUMMERHOUSE可转向更新范围／资产所有权，避免一直停在已确认的局部函数。

## 也值得查的新方向

| 方向                                                | 对自研的价值                                                                             | 建议的第一片                                                                                                                                                                                                                             |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **掘地求财：相邻LOD边界的接缝与碰撞覆盖**           | 挖掘时远近网格不同分辨率，视觉裂缝和物理洞口必须分别处理。                               | 从已定位render octree的LOD／transition标志选择一个相邻chunk对，追过渡网格的任务输入、边界数据与section碰撞资格；不直接宣称使用某种公开过渡算法。                                                                                         |
| **沙堡：薄水、湿沙和岸边细节是否共享同一状态**      | 解释“水退后仍湿”“薄水突然出现”怎样由阈值、法线与采样分辨率形成，也可比较美术与模拟成本。 | 由[06](sandcastle/06-surface-materials-and-effects.md)的湿沙／水层公式接一份实际材质参数和shader变体，追同一cell到颜色、法线、泡沫／岸边遮罩；最终像素保留Unknown。                                                                      |
| **Tiny Glade：细节预算的空间分配与远处退化**        | 程序化砖、瓦、常春藤如何限制实例量，何处用粗形／裁剪，直接关系大场景性能。               | 在[49](49-tiny-glade-roof-gpu-visibility-and-depth.md)、[51](51-tiny-glade-vegetation-counts-and-active-list-rebuild.md)已有可见性／活动前缀基础上，只选屋瓦或常春藤，接相机距离、预算或剔除标志的真实生产者；不重启槽23的相同写端扫描。 |
| **SUMMERHOUSE：像素化轮廓在相机移动时怎样保持稳定** | 像素风小屋的观感既取决于模型，也取决于分层目标、采样坐标、相机位置和深度回贴。           | 由[07](summerhouse/07-pixel-blit-depth-and-local-render-route.md)、[10](summerhouse/10-low-resolution-mips-and-attachments.md)追相机投影／像素网格取整到分层重绘与回贴坐标，区分材质换色、层重绘和整屏重绘；实际抖动／帧时仍需运行。     |

我更建议在提交边界补出一个新节点后，转入这四个美术／成本方向。这样可以形成“什么数据改变→哪些区域重算→怎样合成画面”的可借鉴规格，而不是把所有时间投入同一处无法定型的间接调用。

公开背景仅支持问题分类：[Unity 2023.2 SetActive](https://docs.unity3d.com/2023.2/Documentation/ScriptReference/GameObject.SetActive.html)区分本地激活与祖先层级，并说明生命周期回调；[UnloadSceneAsync](https://docs.unity3d.com/2023.2/Documentation/ScriptReference/SceneManagement.SceneManager.UnloadSceneAsync.html)区分scene对象销毁与资产释放。因此SUMMERHOUSE后续应分别追两种寿命。公开API不替代本机二进制，也不能证明本作一定累积列表条目。背景来源范围在本轮raw `public-reference.json`。

旧悬案Tiny Glade槽23与沙堡尾值3继续保留[97](97-next-study-recommendations.md)的决定性输入／停止条件；本轮没有新写端或构建writer，不将其改标完成。运行用例仍留在[74](74-runtime-validation-cases.md)，本轮及本页新建议的运行均 **Not Run**。
