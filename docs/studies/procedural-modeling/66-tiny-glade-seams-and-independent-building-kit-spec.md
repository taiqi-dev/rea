# Tiny Glade：接缝属于什么，自研造房游戏该怎样拆资产

原资产与建筑状态见[64](64-tiny-glade-building-kit-and-asset-assembly.md)，窗洞和灯具见[65](65-tiny-glade-window-holes-and-lantern-components.md)。本篇先说明已确认的接缝职责，再给出独立建模/生成规格。后半是我们自己的设计建议，不是原作源代码、美术资产或开发者意图。

## 1. “接缝”不是单一模型或单一材质

相似画面可能来自不同模块：

| 所见位置 | 已确认的生产方式 | 属于哪层 |
| --- | --- | --- |
| 一面墙的近直角转角 | 单独选角、交替铺转角砖，再反馈占用范围 | 墙构件生成器 |
| 两个建筑轮廓相交处 | 交点与有效高度段生成额外砖/梁 | 建筑关系产生的连接构件 |
| 木板之间的缝 | 区域排板、分片和实例布局形成 | 板布局及资源几何 |
| 窗口周围 | 开口重建、窗体/楣梁/条件部件覆盖边缘 | 宿主墙与装饰两条产物共同形成 |
| 所选屋瓦边界 | CPU裁剪plane及GPU半空间取消片元 | 几何参数与显示规则 |
| 共面屋顶底板 | 按墙身份分相的细微高度处理 | 顶点显示处理；具体用途仍是推断 |

所以“中间那条接缝属于房间模型还是窗模型”需要先确定缝的类型。不能把上述规则统一说成一张接缝贴图，或统一说成另建一个专用整块接缝mesh。

## 2. 建筑相交处确实另生成砖或梁

[04](04-tiny-glade-intersections.md)已恢复二维轮廓接触点、地形/两墙高度筛选与区间分界。成功后写64B接缝描述，带位置、方向、高度段、两墙ID和分支标志；`21A3960 spawn_stitches`消费它。

本轮补核实际渲染记录写端：

- 砖接缝：`21A56A2→94C790 BrickTransform.encode`，随后`21A56B0→28FA830 push<BrickTransformSsbo>`，输出64B记录。
- 梁接缝：`21A4C5C→28FAF20 push<WoodenPlankSsbo>`，输出80B记录。

这些都是额外生成的构件实例，进入已有砖/木板实例表示。它们不要求一个名为“两个房屋交接处”的独立整体模型。**但相同实例类型还不能证明下游所有flags都选择同一源网格/材质；普通brick.json的完整drawlist绑定仍未贯通。**

砖接缝和普通墙砖、普通转角使用同一个编码器；记录仍携带wallslot、seed、范围、flags等。选定砖接缝flags为`4 | (raw_tag==1 ? 0x2000 : 0)`。木接缝则为`1 + 32*(raw_tag==3)`。raw tag的玩家语义没有完整映射，不能据数值起风格名称。

木接缝末16B在所查路径为默认零；它不是已经确认的WindowCutList，也不是80B曲梁记录CurvedHalfTimberInstanceData。相同字节数不能代替类型和消费端证明。

### 构造例：高度段怎样变成两块接缝砖

选择有效段Y=[2,4]、砖分支，H=2：

```text
k = clamp(ceil(2H),3,1000) = 4
边界点数 = k−1 = 3
砖数 = 边界点数−1 = 2
```

选说明性随机输入0.7，内部比例0.52，边界为[2,3.04,4]。两块中心Y为2.52/3.52，竖直尺寸扣0.1后为0.94/0.86。横向另选随机0.5给某一轴0.4、第三轴固定0.3；最后分别编码并追加64B实例。

这是一套“根据当前接触关系摆小件”的算法，不是把两栋房子的作者mesh接缝手工焊起来。随机输入、ID和场景是构造参数，没有执行原游戏或证明最终shader外观。

## 3. 普通转角、屋瓦切边与封口不能混用

普通墙角由`14299B0`另行生产。近直角点积资格、band交替进/出切线、第三轴厚度与短片段门槛见[37](37-tiny-glade-brick-corners-and-noise.md)、[60](60-tiny-glade-wall-thickness-and-contour-joints.md)。它不同于两建筑交点接缝生成器，也不是一般miter/Boolean求解器。

屋瓦边界方面，[42](42-tiny-glade-roof-edge-planes-and-seams.md)确认同屋顶轮廓到plane、压四half并写实例；[05](05-tiny-glade-seams.md)确认fragment按`dot(p,n)+d<0`取消片元。选择plane=(1,0,0,-1)，x=0.8时结果−0.2被取消，x=1.2时+0.2保留。这能改变可见边界，**没有证明切掉CPU三角形或新增侧封口面**。

屋顶还有独立梁、尖顶资源/实例，以及底板显示。当前没有把所有屋脊、檐口、两建筑接触缝分别对应到专用mesh，更没有恢复建筑间屋顶保留侧的完整规则。因此不能说所有屋顶缝都由上述同屋顶plane负责。

## 4. 原资产给出的建模线索

原JSON可直接观察局部约定：brick在三轴±0.5；木板Y为0..1；roof_support_beam也沿Y从0到1；roof_spire带roof_profile_mult，砖/板有is_bevel等属性。它们方便后续缩放/变形或分类消费，但作者具体导出工具和所有属性用途未完整恢复。

同一源模型还可供不同渲染用途。RON的WoodenPlank和WoodenGablePlank都按相同顺序引用wooden_plank、LOD1、straight；RoofTile引用主体、LOD1、backface。主体和backface的完整position数组相同，indices分别90/108，不能仅凭独立文件就认定顶点形状独立。

实际`load_nani_meshes`和`MeshAtlasLibrary.register_meshes`调用已定位；RON顺序至shader具体atlas索引、砖专用绑定与全部variant选择仍未贯通。下述自研清单因此是独立规格，不照抄原资产或未确认字段。

## 5. 自研：先做小件库与参数定义

针对“能自由拉伸房子、移动窗、相交并自动修边”的玩法，建议将整栋房子的模板保存为参数组合。美术资产主要建这些小件：

| 我们自己的资产 | 应预先约定 | 运行时的主要职责 |
| --- | --- | --- |
| 砖模板及少量变体 | 局部原点、三轴尺寸、倒角、可拉伸区域 | 排行、缩放、裁短、转角/接缝摆放 |
| 木梁/木板 | 长轴、首末端锚点、UV重复规则 | 定长/分段、沿墙定位、开口避让 |
| 瓦片/收边件 | 铺排方向、搭接量、端部/背面规则 | 按屋面铺排、屋脊/檐口收口 |
| 窗框/窗格/玻璃 | 分件、等级或尺寸规则、切口轮廓 | 附着、位置调整、向墙发布开口 |
| 灯壳/灯内部分 | 挂墙锚点、灯内局部中心、可选支撑 | 附着、碰撞、发光和实际光源 |
| 门、栏杆、阳台附件 | 端点/连接面、伸缩段和支撑资格 | 与宿主和其它附件协调 |

坐标、单位、轴向和pivot要作为自己的一份资产契约，而不是让每个资产导入后再猜。例如我们可自行规定Y向上、局部Z朝墙外，梁用首端pivot和Y长轴；选择别的约定也可以，只需统一转换。原作一些数值相似不能替代我们的定义。

灰泥、墙基、楼板、洞口内壁等连续区域可以由程序生成面；纹理/材质处理表面。基础brick/beam实例与连续面可以并存。若需要可进入室内，则还必须自行定义内墙、地板、天花、洞口侧壁、门连接、碰撞和导航，不能认为外观开了窗就已经有完整房间。

## 6. 自研：数据和派生产物分别拥有

建议独立定义以下职责，不要求先复制原作复杂调度或GPU实现：

```text
BuildingDefinition：足迹、高度、屋顶、风格和稳定seed
Attachment：自身ID、宿主ID、墙坐标/屋顶位置、类型和参数
Cutout：开口轮廓及其产生者ID
GeneratedPart：模板、变换、显示参数、逻辑owner
Connection：相关宿主ID与接触边界
```

输入改变时先修改逻辑定义，再重建派生产物。窗的owner负责发布和清理自己的切口/框体；灯的owner负责模型和光源；两建筑接缝的owner应记两边身份，删除任何一边都能定位旧接缝。

第一版可以按受影响建筑整体重建，保持诊断与所有权清楚；得到真实耗时后再缩小到面段/区域。按模板和材质批量绘制重复件，与逻辑层保存每个对象ID并不冲突。不要一开始就把物理GPU槽位当永久对象身份。

### 独立规格演算：移动窗不留下旧洞

自造建筑A、窗W、灯L：W在墙坐标(5,3)，切口owner=W；L在(7,2)，只输出附着模型/光源。将W移至(6,3)：

1. 修改W定义并替换owner=W的切口，旧切口失效。
2. 将A及相关连接标记重建；用新开口生成当前墙体。
3. 更新W的框体/玻璃变换，按需要重新布局附属件。
4. L的独立定义仍在原位置；是否重算其世界变换取决于宿主是否改变。

若再删除A，则清理A的派生构件、附着物和与A关联的连接。这个演算是我们自己选择的owner规则；原作所有删除、事务与并发细节没有据此被宣称恢复。

## 7. 下一步值得查什么

对于实际做造房游戏，我会按以下顺序继续研究：

1. **所有权与实例化最后一段。** 已有模型请求、RON subset、loader/atlas注册和实例记录；补全请求→mesh/material handle→批绘制，才能明确资产怎样真正使用。
2. **门、阳台、栏杆和支撑连接。** 原资源已有BalconyDoor/rails等组，可查长度变化、端点与宿主开口协商，直接扩展可用小件库。
3. **连续表面和洞口内壁/封口。** 先区分目标实际支持的外观与室内结构；自己的房间玩法需要明确封闭几何、厚度和碰撞契约。
4. **交叠后的暴露面保留与局部更新。** 继续已有建筑相交缺口，用最小相交场景确认可见边界与封口；静态证据不足时再单独确定运行范围。

这份优先级是针对自研目标的建议，不意味着上述模块已全部确认或已开始实现。

自研落地规格现已拆成[Unity最小造房demo](unity-building-demo/README.md)：资产分工、墙/屋顶/真实开口、挂灯、火水与永久破坏、重建/存档及完整验收分别成篇。当前先用直墙和矩形小屋跑通闭环；本节续查方向不作为最小demo全部必须完成的前置。

未做：没有给用户产品编写生产代码，没有复用原资产，没有恢复全部renderer/室内/封口，也没有运行游戏或性能测量。

风险：共享实例格式不保证共享全部网格/材质，像素裁剪不保证闭合几何，观察到资产约定不代表必须沿用原常数。自研规格、原作证据和未决项在正文分别标注。
