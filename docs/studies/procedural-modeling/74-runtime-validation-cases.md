# 四款游戏：需要运行验证的独立清单

本页只写**尚未执行的验证规格**，与[静态续查账本](73-four-game-render-chain-closure.md)分开。所有用例当前都是 **Not Run**。本轮没有启动、附加、改写游戏或读取私人存档；现有静态调查和摘要授权不自动变成这些操作的授权。此处不请求新权限，也不把缺少运行证据当作静态链已失败。

只看到菜单或一张画面不能通过这些用例；能运行游戏也不保证发行构建允许帧调试或内部计数。可用采集工具、目标版本及可见指标需要实际确认；没有某项指标时报告该项未取得，不能用模拟脚本、资源数或平均 FPS 替代。

## 用例共用记录

每次比较保留目标版本、GPU/驱动、窗口尺寸/画质、镜头、场景与操作、采集工具和实际覆盖。将静态指令推导、玩家画面和计时分开；帧时间用毫秒，读回延迟与任务等待也分别计时。性能结果至少区分稳态和首次触发；足够样本下报告 p50/p95/p99 及样本数，并保留原始时间序列。没有自研产品预算时，只报告数值及变化，不自行设“达到 60 FPS 就通过”等标准。

下面的“通过依据”表示行为证据足以判断该问题，不保证整款游戏或自研实现性能达标。

## SUMMERHOUSE

### SH-R1：回贴过滤、透明颜色与深度

- **对应静态链**：[07](summerhouse/07-pixel-blit-depth-and-local-render-route.md)的 `_MainTex/_DepthTex → sample → SV_Target/SV_Depth`，以及包内 AlphaBlend、ZWrite。
- **最小场景**：一件有透明边缘的块与另一件前后交叠的块，固定镜头；再在两个缩放级别保持相同对象关系。
- **需要观察**：实际选用的 feature/material/pass、目标尺寸、两张输入纹理与 sampler/LOD、当前颜色/深度 attachment、有效 blend/depth state，以及边缘像素和遮挡结果。
- **通过依据**：能把实际 draw 的输入/状态对应到输出，区分过滤、源 alpha 与深度写入各自造成的效果。若无法抓取 sampler 或 attachment，只能部分回答，不能由像素外观猜默认设置。
- **不能外推**：一个缩放级别或质量档位不代表所有相机、天气和平台。

### SH-R2：改一块时，哪些对象重绘、资源是否重新分配

- **最小操作**：固定镜头先静置，再给一个块刷色、触发人物窗组合，随后只缩放镜头。
- **需要观察**：变更的 Renderer/材质、像素化 pass 的 draw 范围、RT 尺寸与重新分配、CPU/GPU 帧时间；若能取得托管分配数据，单列每次触发的分配而非全程平均。
- **通过依据**：区分块级修改、层筛选重绘和缩放引起的目标变化；确认哪些成本属于事件、哪些属于渲染调用。辅助格线只有实际启用时才纳入测试。

## Tiny Glade

### TG-R1：G-buffer 到延迟光照的资源身份

- **对应静态链**：[69](69-tiny-glade-shading-lighting-and-contact.md)的打包格式与[72](72-tiny-glade-cpu-render-bindings-and-lifecycle.md)的 CPU 注册/绘制。
- **最小场景**：一面可见普通砖墙、固定光照和相机。
- **需要观察**：该墙实际使用的 draw/callback、G-buffer 输出 attachment/子资源、solid-light 输入 binding、barrier/布局转换和 pass 顺序。
- **通过依据**：同一资源与子资源的写端、读端可对齐，墙类条目确实进入相应绘制提交。只有两张纹理内容相似或 shader 文件名相同不足以通过。
- **不能外推**：普通砖墙的证明不覆盖屋瓦、植被、所有视图或全部光照算法。

### TG-R2：局部重建与候选筛选的成本分离

- **最小操作**：固定镜头修改一面墙；再在不编辑的情况下移动镜头；另在同一场景比较少量和较多可见构件。
- **需要观察**：受影响对象数、实例记录与上传范围、候选/可见实例数、indirect 命令、各阶段 CPU/GPU 时间及同步等待。无法取得内部数量时保留未知，不能用画面可数砖块替代 GPU 候选数。
- **通过依据**：能分别解释编辑触发的产物重建和视图变化触发的筛选/绘制，避免把“未编辑”当作“该对象本帧零成本”。

## Sandcastle Demo

### SC-R1：沙水材质、取样和真实覆盖

- **对应静态链**：[06](sandcastle/06-surface-materials-and-effects.md)和[08](sandcastle/08-material-bindings-render-state-and-invalidation.md)。
- **最小场景**：固定镜头下从干沙到薄湿层再到明显水层，保留一处水面与岸边/前景交叠。
- **需要观察**：实际材质和贴图、cell buffer、湿色过渡、水面 discard、背景颜色/深度生产、折射回退、透明 pass 的 blend/depth 状态和最后像素。
- **通过依据**：能用实际输入解释湿沙与可见水采用不同门槛，并确认当前使用的取样/混合状态。若发生穿插或颜色拖拽，记录对应深度和 UV，不能只凭现象归因于某一公式。

### SC-R2：读回在途量、碰撞延迟与实际尺寸

- **最小操作**：固定场景先静置，再连续小范围铲挖，并在接缝两侧重复同一动作。
- **需要观察**：Ground/Water/Readback 各自真实 resolution、Dispatch、请求提交/完成时间与在途数、CPU 快照时间、四块碰撞更新时间和烘焙耗时。
- **通过依据**：把 GPU 可见高度、CPU 读回和碰撞生效时间分开对齐；验证实际轮询与是否出现请求重叠。0.2 秒静态参数不能代替测得间隔，32 B/格不能代替总带宽。
- **不能外推**：一个海滩或一次无延迟读回不能证明其它尺寸下不存在堆积或碰撞时差。

## 掘地求财

### HO-R1：真实地形/矿物组件与材质身份

- **对应静态链**：[04](digging-a-hole/04-mesh-materials-and-ore-presentation.md)及[06](digging-a-hole/06-mesh-material-binding-and-edit-lifecycle.md)。
- **最小场景**：逐步挖露一个矿物，在相邻地形和矿物上分别触发相同工具。
- **需要观察**：实际命中组件类别/实例身份、使用的网格和材质槽、是否动态覆盖材质、所选 Voxel mesh handler、矿物移除与地形 chunk 更新的事件关系。
- **通过依据**：区分独立矿物 StaticMeshComponent 和体素地形产物，确认代码中的条件分支在该次运行是否实际采用。包依赖或插件函数存在不足以代替实例绑定。

### HO-R2：重复挖掘、旧结果与长期保存增长

- **最小操作**：在专用测试进度中分别反复挖同一范围和持续扩展新范围；固定动作序列，另在编辑间隙与连续编辑时各触发一次保存。
- **需要观察**：chunk/任务令牌、pending 峰值、mesh/cook 在飞量、取消后退场时间、旧结果接受/丢弃、提交等待、唯一修改叶块数、快照锁时间及内存峰值、保存完成/恢复的版本关系。
- **通过依据**：区分“同类任务不重复启动”“通知不积累”“旧结果不误提交”“保存快照一致”四种不同保证；原始记录足以说明通过或具体缺失。仅存档文件变小、平均 FPS 平稳或一次读档成功不足以证明长期稳定。
- **边界**：本轮没有访问任何现有玩家进度，也未为上述用例创建、覆盖或删除存档。

## 回填规则

实际执行后，以每个用例独立的目标/场景/操作/证据/结果记录更新；结果用 Passed、Failed、Partial 或 Not Run，并附原因。只把新增运行证据确实回答的断点升级，保留静态报告的原始覆盖，不按“已经运行过游戏”整体盖章。
