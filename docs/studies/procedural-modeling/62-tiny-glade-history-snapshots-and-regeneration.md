# Tiny Glade：编辑历史、快照恢复与程序化重建

后续[99](99-tiny-glade-wall-identity-and-stable-rebuild.md)选普通砖墙追稳定seed和产物清旧：同ID还须匹配Public数组长度及行输入；快照直接装载到Public发布的完整调度仍未闭合。

本篇回答撤销/重做和读档依赖哪些状态，怎样保留对象编号，以及恢复怎样回到生成管线。沿用[固定发行版身份与方法](58-tiny-glade-input-edit-and-natural-shapes-ledger.md)：原生EXE/PDB静态读取，没有启动游戏、读取私人存档或实际执行保存。本轮完整范围和检查见[第十四轮账本](63-tiny-glade-coordination-contours-trees-and-history-ledger.md)。

结论：发行版包含**编辑序列、装饰/楼梯差异与较大的状态快照**。选定回放分支重新调用墙状态修改入口；快照加载恢复墙、装饰等逻辑状态及栅格。已经建立恢复到状态所有者的连接，尚未证明所有可见网格、随机细节和GPU槽位都在撤销或读档后完全相同。

## 1. 证据位置与表示

所有地址为preferred image base `0x140000000` 下的RVA，通过实际PE节表定位；字段是所选函数实际访问的内存偏移，不是恢复完整Rust私有结构声明。

| 入口RVA                               | 实际支持的结论                             |
| ------------------------------------- | ------------------------------------------ |
| `AE4960 / AE5180 / AE4B50`            | 开始输入记录、追加编辑、非空记录提交       |
| `AE3D70`                              | 在历史中间开始新编辑时裁掉未来记录         |
| `AE2910 / AE3200 / C47270`            | 收尾加入装饰/楼梯差异；装饰前后状态转换    |
| `B68610 / 17ECDA0 / C1C8B0`           | 编辑分派、回放命令生产、墙回放实际状态写端 |
| `AE4D80 / 1BF6820`                    | 选择候选快照、解析与校验快照数据           |
| `1BF3100 / B0DA60 / C3E520`           | 游戏状态初始化、墙状态装载、装饰恢复       |
| `B81310 / B80FB0 / 198C720 / 1920A00` | 保存请求、历史JSON生产、读取主文件         |

`History` 在所选路径中的布局可由实际读写约束：

| 偏移          | 本篇确认的用途                                                 |
| ------------- | -------------------------------------------------------------- |
| `+00/+08/+10` | 已提交记录数组的capacity/pointer/length；每项40B               |
| `+18/+20/+28` | 快照记录数组；本段每项16B，`item+8`为历史索引                  |
| `+30..+57`    | 正在录制的40B `MultiEdit`，内部编辑数组项24B；另有两个引用对象 |
| `+60`         | 选定修改路径更新的身份值；具体生成器和全部用途未恢复           |
| `+68`         | 有符号历史游标；空历史使用`-1`                                 |

不要把数组长度、当前游标和快照索引当成同一数量。`MultiEdit` 名称有实际`drop_in_place<MultiEdit>`调用支持；扩容helper存在同地址泛型别名，不能借其最短符号名把数组误判为音频或木梁消息。

## 2. 一次拖动怎样成为一条历史记录

`AE4960 start_input_recording` 创建空编辑数组，以及装饰、楼梯差异的引用对象，再写入`History+30`。这说明一个录制单位可以同时容纳多种变化，但具体鼠标按下/抬起的全部资格尚未恢复，不能声称每一帧各是一条记录。

`AE5180 add` 先检查录制是否存在；缺失走panic（`AE51A9–AE51B7`、`AE5456`）。在当前工作数组为空且 `cursor − committedLength <= -2` 时，调用 `nuke_future_states`（`AE51C1–AE51E8`）。然后把一个24B编辑项追加到工作数组，更新长度（`AE53B8–AE53F6`）。它另有特定编辑资格检查，未把它概括成所有编辑统一的校验器。

`AE4B50 finish_input_recording` 先取出工作记录，把`+30`写为无记录哨兵。只有以下任一部分非空才提交：

1. 编辑数组长度非零；
2. 装饰差异对象的选定计数非零；
3. 楼梯差异对象的两个选定计数任一非零。

实际空检查为`AE4BA5–AE4BC7`；全空走`AE4CD1`释放工作记录并返回false。非空在`AE4BFF–AE4C24`追加一个40B `MultiEdit`，再把游标加一，断言 `cursor == committedLength−1`（`AE4C50–AE4C6F`），发布后续通知并返回true。未录制就finish另走panic。

`AE2910 history_finish_recording` 的选定完成分支先调用 `C41490`、`A60A40`取得差异，再在`AE2B1C`调用`add_decorator_diff`，最后`AE2B33`调用finish。这样装饰/楼梯改变能够和本次编辑一起提交。函数前部还有消息/UI资格判断，具体原枚举含义与全部结束触发未恢复。

### 构造演算：撤销后再编辑

假定已提交`[A,B,C]`，游标为1，当前录制为空，且本例没有快照。加入D时：

- `1−3=-2`，满足未来裁剪资格。
- `AE3D90–AE3DCA`把已提交长度改为`cursor+1=2`；随后按40B步长释放C。结果为`[A,B]`。
- D写入当前工作数组，长度1，原始项负载24B。
- finish发现非空，提交一个40B记录，数组变为`[A,B,D]`；游标`1+1=2`，等于新长度减一。

这里的24B和40B是记录本身，引用的曲线和差异还有另外分配的内存。该算例验证静态分支和算术，没有在游戏里操作撤销。空录制直接finish不会追加历史项；不能把这个局部结果推成所有无效编辑都没有副作用。

`nuke_future_states` 在游标负数且仍有未来记录的分支会释放并重置历史；非负数分支还更新一项计数并调用快照数组retain（`AE3E95–AE3EAB`）。retain闭包的完整保留条件没有展开，本篇不宣称某一类快照文件必定立即被删除。

## 3. 装饰差异不是每次保存整堵墙

`C47270 convert_before_after_states_to_changes` 分别比较前后目的地表示、位置/姿态类字段和若干属性，再产生变更记录。多个float比较是精确`ucomiss`，不等或unordered均进入变化分支；在所选比较中没有发现近似容差，例如`C4734C–C47392`。

可直接写成原字段公式的一项是：

```text
delta = after.i32[+54] − before.i32[+54]
output.byte[+62] = (delta != 0)
output.byte[+63] = low8(delta)
```

依据`C47539`、`C4754D`、`C47573`。另外`+58`、`+64`的浮点差异形成标记，`+76`的字节差异另形成标记。本篇没有为尚未映射的字段擅自起产品名称，也没有把不同目的地分支的相等条件合并成一次memcmp。

构造例：其余比较字段相同且为有限数，前后`+54`从1变为3，则delta=2，变化标志为1，负载低字节为2；从3变为1则低字节为`0xFE`。后者是否按有符号增量消费要继续查消费端，不能仅凭低字节写入保证它的完整语义。

这补充了[装饰合并](59-tiny-glade-decoration-snapping-and-merging.md)的另一层职责：交互修改、modified集合和历史差异各有自己的表示，不能直接把历史记录当成绘制实例。

## 4. 回放怎样回到墙生成入口

已确认以下实际连接：

```text
replay_edit B68610
  → generate_replay_cmds_from_edit 17ECDA0（B6869C）
  → 墙回放命令 / 墙消费者 C1C8B0
      → 曲线修改92E8E0、完整状态修改92F410
      → 属性修改、删除B0E830、带ID创建B0E300
```

命令生产与墙消费者之间有缓冲/分派，尚未完整追到每种命令的实际调度；实线调用只适用于括号中已核的caller，不能把示意排列说成同步逐帧调用栈。

`C1C8B0`中的刚性变换分支先调用`C49AA0 interpolated`，再`C49BC0 transform_curve`，最后`C1CF5C`把新曲线送进`92E8E0`。这证明回放包含从逻辑变换重算曲线的路径。选定另一个分支还在`C1DE69`发送屋顶重算消息；它不是所有墙回放统一必发的消息。

带ID创建实际调用在`C1E01C`与`C1E275`。`B0E300`把传入的WallId交给墙map插入；成功后在`B0E330–B0E33A`把同一ID加入`InnerWalls+30`集合，重复ID走诊断panic。它不走普通新建时递增ID再分配的路径。集合在此处是创建相关集合，不能与[编辑dirty集合`+60`](55-tiny-glade-edit-rebuild-stages-and-upload.md)混用。

曲线/完整状态修改入口的dirty发布、公共墙替换和屋顶消费者已有[53](53-tiny-glade-wall-footprint-input-and-curves.md)、[55](55-tiny-glade-edit-rebuild-stages-and-upload.md)、[50](50-tiny-glade-roof-edit-messages-and-regeneration.md)证据。由此可以推导选定回放修改会进入既有重建体系；未证明每种撤销都使用同一路径，也未证明GPU实例槽位恢复。

## 5. 保存：编辑JSON与异步快照请求

`B80FB0 add_history_edit_to_save_file`先记录shadow file当前写入位置。不是第一条时写入两字节`2C 0A`，即逗号和换行，再调用`198C720`将当前40B记录序列化。写入后调用`ShadowFile.mark_dirty`。这是CPU缓冲更新，不能当作磁盘已持久化。

`198C720`实际写出以下JSON字段：

| 字段         | 实际生产条件与内容                              |
| ------------ | ----------------------------------------------- |
| `edits`      | 序列化编辑数组，`198C761–198C776`               |
| `decorators` | 装饰差异选定计数非零才写，`198C78C–198C7B0`     |
| `stairs`     | 两个楼梯差异计数任一非零才写，`198C7BA–198C7F8` |

名称来自原始字符串及实际长度参数，不是从私存档取得。这里不补造未恢复的内部编辑JSON schema。

`B81310 save_game`有以下实际路径：查询当前快照（`B81E40`）、捕获快照保存数据（`B820B1→1BF4DA0`）、向`Sender<AsyncSaveCmd>`发送请求（`B82142`），成功分支才登记当前快照（`B82166→AE4150`）。请求使用raw tag9并携带一个共享的pending对象。返回结果raw tag`0xB`的比较控制后续分支，其命名必须结合完整枚举解释；本篇没有把请求入队写成快照文件已经完成。

函数还读取保存线程的错误结果channel。快照文件flush、sync、pending resolve、保存触发门槛和异常后的完整恢复尚未追完，不能宣称自动保存频率、原子写入或崩溃恢复保证。

## 6. 快照与读档：保留逻辑身份，再恢复所有者

主文件读取`1920A00`实际调用文件读文本、JSON解析，并读取`Version`、`BackwardCompatibility`、`History`等字段。版本/JSON失败带错误上下文，不能把成功的局部分支推广到全部损坏文件都可恢复。

`1BF6820 validate_and_load_closest_snapshot_data`读取的选定快照字段包括：

- `Walls` → `Vec<(WallId,WallState)>`反序列化，实际调用`1BF71A6`；
- `Roofs`、`Decorators`、墙体相关颜色映射；
- `Terrain`、`Trees`、`AutoClutter`、`Stairs`、`StairsRemovedSupports`；
- `Raster`、`TerrainHeightRange`；栅格还有解压路径。

这说明快照混合保存逻辑状态与栅格数据。不能概括成只有操作日志，也不能从所选字段证明保存了所有渲染缓存或完整网格。

### 候选快照选择

`AE4D80`先调用helper收集候选，再按`item+8`历史索引做二分定位，比较左右距离。`AE4E3C–AE4E48`使用`setle`：**距离相等时取右侧较大索引**；目标超过末尾时取最后一项。它并非一定选择目标之前的快照。

构造例：假设helper已经返回按索引排序的合格候选`[0,10,20]`，目标15，左右距离均为5，选20；目标14选10；目标25选20。候选helper的完整resolved资格未展开，这个例子不把pending或损坏快照纳入候选。选到较晚快照后怎样组织反向回放、失败时怎样换候选，仍需继续确认。

### 状态恢复与编号

`1BF3100 init_game_state_from_snapshot`实际调用：

| caller    | 写端                                       |
| --------- | ------------------------------------------ |
| `1BF3572` | `B0DA60 InnerWalls.load_state`             |
| `1BF3753` | `C3E520 DecoratorStorage.restore_snapshot` |
| `1BF3F58` | `AllWorldRasterWrite.write`                |
| `1BF4051` | `PlantSampleRaster.restore_composite`      |
| `1BF44A5` | `StairsState.restore_snapshot`             |

墙装载先断言选定容器为空；按120B `(8B ID +112B state)`记录遍历，把原ID放进创建相关集合，然后恢复主map。它求输入ID最大值并写`InnerWalls+ C0`（`B0DC40–B0DCD7`）。和[53的普通新建先递增counter](53-tiny-glade-wall-footprint-input-and-curves.md)结合：构造快照中墙ID为7、12，装载counter=12，下一次该普通新建分支得到13。空墙输入走另一路径，不用本例推断空输入counter。

装饰恢复按已有DecoratorId插入，并更新调用者提供的u32计数：`next = max(current, savedId+1)`（`C3E68A–C3E69D`）。构造当前next=0、保存ID为3和9，恢复后next=10。墙counter和装饰next的加一时机不同，不能写成一套统一ID规则。

恢复原ID只建立对象身份延续。关于原砖seed、屋瓦序列、实例物理槽位、跨版本随机行为与浮点差异，仍须逐个生产者核对；参见[稳定随机性](44-tiny-glade-stable-randomness.md)。

## 7. 独立实现规格与剩余问题

可借鉴的独立设计是：一段用户操作聚合成一次可提交编辑；记录逻辑对象变化；用快照缩短回放距离；恢复原ID并重建派生结果；把请求入队、写盘完成和失败分别建模。这是我们按证据重新组织的规格，不是可复制的原作实现。

未做：没有实际撤销、重做、保存、读档、计时或性能验证；没有读取用户存档。静态调查仍未闭合全部撤销/重做游标移动、UI资格、反向回放、pending快照完成、快照GC、磁盘flush/sync和全系统恢复后的生成顺序；没有运行REA项目构建/测试，本次仅研究文档与静态证据。

风险：同地址泛型符号、不同字段布局、局部恢复与最终画面容易混淆。已核原字节和调用只能证明所选分支；不能保证运行时必经该分支，也不能保证跨版本逐像素一致。
