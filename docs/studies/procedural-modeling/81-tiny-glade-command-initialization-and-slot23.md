# Tiny Glade：间接命令的初始数据与槽 23 边界

阶段3的shadow上游、首桶传参及主命令表到只读转换节点的续查见[83](83-tiny-glade-slot23-write-growth-and-submission.md)；后续写入/扩容仍未闭合，本篇初始状态证据继续适用。

承接 [79](79-tiny-glade-draw-command-slot-provenance.md) 的同一 typed `DrawIndexedIndirectBuffer`：本轮从构造端确认其**空输入创建路径**请求 `0x1CC=460` B 零数据，即 23 条 20 B 命令的初始 payload。墙回调的槽 23 则从偏移 460 B 读取 20 B。两者构成一个**有条件的范围冲突**：只有 backing buffer 在该 draw 之前仍保持 460 B 逻辑可用长度、且阶段 3 的该条目实际到达提交时才成立。当前静态证据没有证明这些运行条件同时成立，因此不能断言游戏发生越界、无绘制或驱动错误，也不能把槽 23 称为已确认的保留槽。

## 证据范围

输入是 [70](70-tiny-glade-update-and-render-costs.md) 已核对的同版 `tiny-glade.exe`（65,612,184 B；既有 SHA256 `4627ec9f9a8abe03dd30751f6a8e22868e0dfddf9f40029a1b848a3773495fe5`）及同目录 PDB、发行目录 `compiled-shaders/country-core/compiled/` 中带 `draw_commands` 字符串的 `.precomp`。EXE 地址为 preferred VA，SPIR-V 地址为包内文件偏移。`digging-a-hole/tools/pdb_probe.py` 的 `*replace_with_data*` 原始/保留命中 19/19；`*draw_list*` 原始命中 159、正则保留 61，`*indirect_params*` 原始命中 21、正则保留 17，查询均穷尽且未触发输出上限。`tools/spirv_probe.py` 解码本轮 13 个非墙候选，均为单一模块、零 rejected；它验证指令边界，不等于完整语义或运行绑定验证。

原始证据在 `.cache/procedural-modeling/static-tail-followup/tiny-glade/`：`add.txt`、`new.txt`、`upload.txt`、`creator-caller.txt`、`direct-call-candidates.json`、`replace-symbols.json`、`command-symbols.json`、`buffer-api-symbols.json`、`update-byte-calls.json`、`nani-prepare_unsorted_draw_lists.json/txt`、`nani-allocate_draw_commands.json/txt`、各非墙 `*.json/txt`，以及本轮定点追踪的 `prepare-owner-symbols.json`、`fetch-buffers.txt`、`gpu-fetch-to-prepare.txt`、`prepare-cpu.txt`、`prepare-wrapper.txt`、`prepare-binder.txt`、`clear-lists.txt`、`draw-write-typed.txt`。沿用 [77](77-tiny-glade-draw-callback-mapping.md) 的 `indirect-draw-bricks.txt`、[79](79-tiny-glade-draw-command-slot-provenance.md) 的 typed key 与墙 shader 链。PE 字节中的 `E8 rel32` 定点扫描只提供**候选**；下表的调用点又以 `dumpbin` 指令边界复核。没有启动或附加游戏、读私人存档、GPU 抓帧或打开共享 REA native session。

## 构造与完整 20 B 初值

| 位置              | 实际数据流                                                                                                                                                                                                                                                                         | 结论边界                                                                                                                                                                  |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0x140B7F5D7`     | 静态直接调用 `AssetSsboLibrary::add_new<DrawIndexedIndirectBuffer>`（VA `0x141542760`）；在这份 `.text` 的定点 `E8` 扫描中是该特化的唯一直接调用点。                                                                                                                               | 这是库条目的创建候选；不排除未枚举的间接调用或其他重建机制。                                                                                                              |
| `0x14154277D–782` | `add_new` 把设备指针置于 `rcx`、`rdx` 清零后调用该类型的 `new_storage_buffer`（VA `0x141B138C0`）。随后 `0x1415427AE–83B` 将返回的 buffer 包入同一 typed library 的 `FrozenMap` 条目。                                                                                             | 此调用走**无调用者数据**分支，而非一个已经填好命令模板的输入。                                                                                                            |
| `0x141B138E0–15B` | `test rdx,rdx; je 0x141B1393E`；`0x141B13943–55` 用 `alloc_zeroed(0x1CC, align=4)` 取得初始数据；`0x141B13961` 令 `rdi=0x17=23`。`0x141B1396E–7A` 以 `0x1CC` 构造 `BufferDesc`；`0x141B13996–C9` 计算 `23×20=460`，将零数据指针和 460 B 长度交给 `GraphicsDevice::create_buffer`。 | 证实**初始请求与上传 payload**为 460 B 全零。底层设备可能对齐分配；这段指令没有给出随后任一时刻的逻辑可用范围。非空输入分支检查长度为 20 的倍数，但此创建调用未走该分支。 |

按 [79](79-tiny-glade-draw-command-slot-provenance.md) 已证的 20 B 结构，构造时槽 16 位于 `16×20=320` 至 339 B：`count=0`、`instanceCount=0`、`firstIndex=0`、`vertexOffset=0`、`firstInstance=0`，每项为 4 B 零值。这是**完整初值演算**，不是最终绘制模板。槽 22 占 440–459 B；槽 23 需要 460–479 B，首字节刚好在该初始 payload 的末端之后。若后续 prefix、pass2 或其他 shader 只改 `instanceCount`，仍不能凭此推定另外四字段的最终值或有效 draw。

## 替换、其他 shader 与实际提交条件

`nani_upload_derived_buffers` 在 `0x14096210D–0x14096224D` 建立的首个 `D×20` 零数组，调用目标 `0x141533320` 由完整的 `*replace_with_data*` PDB 枚举标为 **`NaniDrawListSsbo`**，不是 `DrawIndexedIndirectBuffer`。其余 18 个具名 `replace_with_data` 特化亦没有 `DrawIndexedIndirectBuffer`。这排除了把 [70](70-tiny-glade-update-and-render-costs.md) 的 `D×20` 上传直接当作本命令缓冲扩容；并不排除无同名特化的通用/内联更新。`nani/allocate_draw_commands.precomp` 虽有易混淆的文件名，其 218 条 SPIR-V 指令声明的是 `merge_window_draw_cmd_counts` 等资源，**没有** `OpName draw_commands`。

另一条容易误接的“完整命令模板”在 `nani/prepare_unsorted_draw_lists.precomp`：其 `draw_list_buffer` 为 set 0 / binding 1、stride 20 B（包偏移 `0x558/0x528`）。`0x86C–0x928` 对同一条记录的五个字段依次写入 `atlas_part_info.index_count`、0、`atlas_part_info.first_index`、0、0，即构造 `[index_count,0,first_index,0,0]`。**本轮已沿 CPU 实参证明它绑定的是 `NaniDrawListSsbo`，从而排除拿这五次 store 给墙回调的 `DrawIndexedIndirectBuffer` 填模板：**

| 桥段              | 指令与字段                                                                                                                                                                                                                                                                                             | 资源身份                                                                                                                                                         |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 取得 typed 图句柄 | tuple `BufRef::fetch` 在 `0x140A92125` 调 `write_rg_buffer<NaniDrawListSsbo>`（PDB VA `0x141529660`）；`0x140A921CE–E4` 把 20 B 返回值放到结果 `+0xB4..+0xC7`。同一 tuple 的 `write_rg_buffer<DrawIndexedIndirectBuffer>` 在 `0x140A92089`，返回值从结果 `+0` 开始。                                   | 两种 typed key 在相同 fetch 中仍是不同字段；不是按 20 B stride 猜身份。                                                                                          |
| 传到 prepare      | `gpu_generate_draw_lists` 在 `0x1409B68E9–F7` 以 `[rbp-0x1C]` 接收 fetch 结果，故 Nani 字段位于 `[rbp+0x98]`；`0x1409B6ACD–D4` 把该地址写入资源指针表 `[rbp+0x208]`，即表基址 `[rbp+0x1C0] + 0x48`。`0x1409B6BE8–BEE` 把表基址交给 `prepare_empty_unsorted_draw_lists`。                               | `+0x48` 的指针指向 Nani typed 图句柄；表 `+0` 才指向 DrawIndexed 字段。                                                                                          |
| 绑定第二资源      | `prepare_empty_unsorted_draw_lists` 在 `0x1418C3CF5` 读取表 `+0x48`，`0x1418C3D68–D94` 将其放入传给 compute wrapper 的第二个指针字段；wrapper `0x14178E4E3–50D` 原样复制该 24 B 参数并交给 shader 专门 binder。后者在 `0x141A278DB` 从参数 `+8` 取第二资源，在 `0x141A27937–3E` 登记第二个图资源访问。 | 与同一 shader SPIR-V 的第二资源 `draw_list_buffer`（set 0 / binding 1）对应。第一资源另由 `gpu_generate_draw_lists` 在 `0x1409B68FC–92B` 导入，不是命令 buffer。 |

例如两个 atlas 部件给出 `(index_count, first_index)=(36,0)` 与 `(48,36)` 时，该 shader 的两条 Nani 记录分别写成 `[36,0,0,0,0]`、`[48,0,36,0,0]`；这只是字段演算，不说明墙间接命令槽 16 或 23 获得同样数据。`write_rg_buffer<DrawIndexedIndirectBuffer>` 自身在 `0x14152B6E2–777` 通过 typed `FrozenMap` 取 buffer、`GraphImportable::import_mut` 导入图并记录句柄；该段没有填写命令五字段的 CPU byte update。主路径在 `0x1409B6AE2–AF6` 调 `clear_draw_lists` 时，所传表的直接读字段为 `+0x20/+0x28/+0x38`（清理函数 `0x1418C26CE–75A`），而随后 `0x1409B6BBE–BD2` 的 `GraphApi::clear_buffer` 在表 `+0x08` 或 `+0x10` 两者之间选择；这些均不是表 `+0` 的 DrawIndexed 字段。这只排除**该两条直接清零路径**作为 DrawIndexed 四个非计数字段的模板，不能排除其他图节点或内联/通用更新。

为避免只检查墙目录，本轮在发行 `country-core/compiled` 中精确搜索 `draw_commands` 字符串并解析 13 个非墙候选。其中 12 个模块有 `OpName draw_commands`；`nani/allocate_draw_commands` 仅文件元数据匹配。garden、path_pebbles、rocky_terrain/stairs、water 的 10 个模块，对其具名 `draw_commands` 的显式写入均是成员 **1=`instanceCount`** 的 `OpAtomicIAdd`；`garden/read_bush_positions_for_cpu` 与 `stairs_counter` 所见是读取。各模块的 `globalParams.draw_indirect_buffer_offset` 或其他索引的 **CPU 实参及 backing typed key 尚未逐一绑定**，所以这张跨目录清单仅扩大了候选 writer 范围，不能证明它们写的是本 buffer 的槽 23，也不能宣称四个非计数字段在全程序中没有生产者。按 [79](79-tiny-glade-draw-command-slot-provenance.md)，墙目录七个 compute 的具名命令写入只到槽 22。

阶段 3 的必要门控不是“每帧必然调用”：`render_bucket` 先要取得含回调的有效条目并通过绑定检查；`indirect_draw_bricks` 在 `0x1409641AE–1D5` 要求循环组 payload 高 16 位为组号 1、低 32 位为 1、bit 40 为 1。构造的循环组 `i=1` 满足 payload 条件时，`0x1409641DB–1ED` 确实选择 `r9=0x17=23`；通用回调再以 `23×20=460` B 记录一次 `draw_indirect(count=1)`。但是否有该条目、阶段 3 是否进入这个 bucket、图资源是否已扩至至少 480 B，尚无运行或完整静态调用链证据。

**已答与未答。** 初始零 payload、23 条命令的 20 B 布局、Nani shader binding 1 到 `NaniDrawListSsbo` 的同一性，以及槽 23 的进入条件已有独立地址证据。最后确认的 DrawIndexed CPU 写租约是 `write_rg_buffer<DrawIndexedIndirectBuffer>` VA `0x14152B6C0` 的图导入；已查的 `clear_draw_lists` 与显式 `clear_buffer` 不直接选择该 typed 字段。仍未恢复 **DrawIndexed 图资源上的** `count/firstIndex/vertexOffset/firstInstance` 后续写入或模板生产者、任何把它扩至 ≥480 B 的确切赋值/替换路径，也未逐一绑定非墙 candidate shader 的 CPU typed key 与绝对槽值。因此“槽 23 保留/错误/有效”均为**未知**，本研究状态为 **Partial**。运行、GPU 捕获及 FPS 观测均为 **Not Run**。
