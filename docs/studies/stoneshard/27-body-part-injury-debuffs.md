# 各身体部位受伤后的属性减益与稳定伤势

[总目录](README.md) · [证据范围](00-evidence-and-scope.md) · [部位选择与伤势产生](25-body-part-hit-selection-and-injuries.md) · [状态生命周期](11-buffs-and-effects.md)

本轮已绑定六个部位的三级普通伤势与三级稳定伤势，并恢复它们写入的属性贡献。**手部、腿部、头部、躯干有不同减益组合；稳定伤势仍调用同等级属性助手，基础属性贡献并没有统一减半。**普通伤势另有疼痛贡献、锁定列表或回合副作用，不能只看基础贡献表判断稳定治疗的全部效果。

这些结论来自本机原生指令、字符串构造与 `data.win` 对象关系。表内数值是状态 `data` 的贡献，只有已追到消费者的局部规则才解释为加法或界限；未恢复完整属性消费者的字段保留原键，不把贡献直接叫作最终面板百分比。

## 2. 从 Condition 到真正的伤势对象

上一模块已经证明 `scr_injuryChange` 先更新单位的 `Body_Parts_map[part]`，然后按 Condition 选择 form：`C<=0 → 3`，`C<=25 → 2`，`C<=50 → 1`，否则 0。比较包含浮点容差。对象更新仍受 delta / override、已有伤势及稳定状态的条件控制，不能把阈值等同于无条件创建。

本轮从这些实际对象的 Create 与 Alarm2 继续追：

```text
部位 Condition → form 与对象选择
  → 具体伤势 Create：绑定 Body_Part、等级对象与装备槽
  → Alarm2：继承初始化 / 数据处理
      → 部位 × 等级助手：写伤势实例 data
      → 普通伤势专属 Pain_Change 与其他条件分支
  → 单位活动 buffs → buffer_buff_data 逐键汇总
  → 属性消费者读取汇总、计算局部属性
  → 移除 / 替换：解除状态登记、标记属性重算，并清理专属锁定
```

`Alarm2` 是事件身份，不代表每两回合执行一次。本轮恢复了事件内容，没有动态测量调度频率。属性助手零实参调用，以当前伤势实例为上下文；内部进入其 `target` 的实例选择作用域，同时通过另一上下文引用读取原伤势 `data`。不能将其理解成直接覆盖目标单位的所有属性。

普通三级分别继承 `o_db_light_wound(5966)`、`o_db_wound(5969)`、`o_db_deep_wound(5971)`，再进入 `o_wound(5965) → o_wound_debuff(5964)`。稳定三级分别继承 `o_db_light_wound_stabil(5995)`、`o_db_wound_stabil(5996)`、`o_db_deep_wound_stabil(5997)`，再进入 `o_stabil_wound(5994) → o_wound_debuff(5964)`。因此稳定对象没有沿普通 `o_wound` 的同一继承路径执行所有副作用。

`legs` 与 `rlegs` 保留真实键，不据此猜测左右腿的显示映射。

## 3. 头部：命中、眩晕抵抗、治疗与视野相关贡献

以下是助手写入伤势 `data` 的实际值，普通与稳定的同等级基础表相同：

|---|---:|---:|---:|
| `Cooldown_Reduction` | +25 | +50 | +100 |
| `Hit_Chance` | −10 | −20 | −35 |
| `Stun_Resistance` | −10 | −20 | −35 |
| `Healing_Received` | −10 | −20 | −30 |
| `VSN` | −1 | −2 | −4 |
| `Pain_Limit` | +25 | +35 | +50 |

| 助手 | 入口 | 顺序对应上表六个写入位置 |
|---|---|---|
| light | `0x1414d8890` | `0x1414d8ac6 / 8b66 / 8c06 / 8ca6 / 8d56 / 8df6`（后五项沿用 `0x1414d` 前缀） |
| form2 | `0x1414d9b10` | `0x1414d9d56 / 9df6 / 9e96 / 9f36 / 9fe6 / a096` |
| deep | `0x1414dadb0` | `0x1414daff6 / b096 / b136 / b1e6 / b296 / b346` |

`Cooldown_Reduction` 的正号容易误读。属性消费局部把 `bCooldown_Reduction` 与贡献相加，再 clamp 到 25..200（加法 `0x140b6fd95`，clamp `0x140b6fe3e`，写字段 `0x140b6fe58`）。因此这不是“表里加25，就一定冷却更短25%”的证明；最终冷却计算的符号与单位需结合技能消费者，本文保留该字段名。

普通 head3 还有数值表以外的状态：在 target 的 `lock_mana_regen`、`lock_spells` 列表分别加入数值 1，调用位于 `0x144403061`、`0x1444030f7`。Destroy 事件会对两张列表执行删除调用（`0x144402782`、`0x1444027f9`）。这证明有配套的锁定登记和清理；本轮未恢复两张列表全部消费者及删除索引槽的生产者，不将它简化成任何时刻必然无法施法 / 恢复能量的完整规则。稳定 head3 自身 Alarm2 仅继承和调用 `scr_head_deep`，没有执行普通 head3 的这两次登记。

**构造例：**仅有 head1 贡献、基础命中字段 `bHit_Chance=80`，进入下文已确认的命中局部消费者时，`clamp(80−10,5,150)=70`。这不是对任意攻击目标的最终命中概率；目标闪避、武器、技能和后续战斗路径仍可修正。

| 属性键 | form1 | form2 | form3 |
|---|---:|---:|---:|
| `Damage_Received` | +7.5 | +15 | +25 |
| `max_hp` | −0.1 | −0.2 | −0.3 |
| `MP_Restoration` | −5 | −10 | −20 |
| `Healing_Received` | −15 | −25 | −35 |
| `Pain_Limit` | +20 | +35 | +50 |

入口与同序写入：light `0x1414dc000`，写 `0x1414dc245 / c305 / c3b5 / c465 / c515`；form2 `0x1414dd100`，写 `0x1414dd345 / d405 / d4b5 / d565 / d615`；deep `0x1414de600`，写 `0x1414de845 / e905 / e9b5 / ea65 / eb15`。缩写沿用对应的 `0x1414d` 前缀。

这里 `max_hp=-0.2` 是实际分数贡献，不能未经完整下游恢复就写成“最大生命直接减0.2点”或“最终严格减少20%”。`scr_atr_calc` 对同键有多处读取，包括基础加和、后续组合分支；装备 / 状态组合助手 `scr_inv_buff_atr` 又把两类贡献相加。本文只确认键和值，以及它确实进入属性计算。

普通 tors3.Other10 还取部位流血抵抗、构造机会并调用 `scr_bleedChange`：取抵抗 `0x1444067c2`、Chance `0x1444068f7`、流血入口 `0x1444069e9`。它属于额外回合副作用，与本表不同；完整流血解释由专门模块处理，不把 `Damage_Received` 当作直接流血概率。

**真实配置例：**tors2 的状态地图明确具有 `Damage_Received=15`、`max_hp=-0.2`、`MP_Restoration=-10`、`Healing_Received=-25`、`Pain_Limit=35`。稳定 tors2 同样调用 `scr_torso`（`0x14440e6c6`）；它的 Create 另外写自身 `pain=3`（`0x14440e514–0x14440e51e`）。这个实例字段不是 `data["Pain_Change"]`，不能把两者互换。

## 7. 普通疼痛贡献与稳定版本的差异

普通具体对象在同级助手之后向自己的 `data` 写 `Pain_Change`，这与助手共同提供的 `Pain_Limit` 不是同一个字段：

| 部位 | form1 | form2 | form3 | 对应键引用 VA |
|---|---:|---:|---:|---|
| head | +0.15 | +0.25 | +0.5 | `0x144400e0b / 0x144401af9 / 0x144402e9f` |
| tors | +0.1 | +0.2 | +0.4 | `0x14440424b / 0x144404de9 / 0x144405d19` |
| lhand | +0.05 | +0.1 | +0.2 | `0x1443f76fb / 0x1443f8379 / 0x1443f924b` |
| rhand | +0.05 | +0.1 | +0.2 | `0x1443f05eb / 0x1443f2f69 / 0x1443f641b` |
| legs | +0.075 | +0.15 | +0.3 | `0x1443fa52b / 0x1443fb089 / 0x1443fbf69` |
| rlegs | +0.075 | +0.15 | +0.3 | `0x1443fd96b / 0x1443fe4c9 / 0x1443ff3a9` |

这些数字是该键的写入贡献，未在本文闭合最终疼痛更新消费者与时间单位，不能称作固定每回合增加相同面板点数。

18个稳定对象的自身 Alarm2 都仅包含继承调用及同级属性助手，不包含普通版本的上述 Pain_Change 写入、玩家额外心理调用或普通专属事件内容。例如稳定 head1 完整事件区间为 `0x14440d9a0–0x14440da73`。因此可以确认**稳定版本在这些具体事件层面去掉了普通版本的附加处理，同时保留基础表**；尚不能说稳定状态绝对无疼痛或无所有心理影响，父类、替换路径和目标其他状态也会参与。

普通 head1 还在玩家分支调用 `scr_psy_change("SanitySituational",−5,"inj_head1")`（`0x144401030`）；普通等级父类有 `MoraleSituational` 等更新。心理模块有自身去重 / 来源规则，本轮不把所有相关调用重复相加成一个总心理损失。

普通 `o_wound.Create` 把 `stability=false` 写入 `0x1443e85e6`；稳定 `o_stabil_wound.Create` 则写 `stability=true`（`0x144407029`）和 `stack=0`（`0x144406ff0`）。这是实际类型标志，不能只根据 `_stabil` 后缀判断。

稳定父类的 Other10 读取对应部位 Condition，并按等级处理：

- form1：与90比较，非负比较结果进入销毁（`0x144407937`、`0x14440796b`）；邻近边界受通用比较容差影响。
- form2：C>50的分支将对象名中的 `2` 替换成 `1`、取资源索引并调用 `scr_inst_change_buffs`（比较 `0x144408112`，替换 / 变更 `0x144408290 / 0x14440832c`）。
- form3：同型流程与25比较，再变为较低等级；比较 `0x144408e32`，变更 `0x14440904c`。

这证明稳定状态可以随 Condition 改善降级或退出，**不能说稳定标志本身阻止部位恢复**。`scr_inst_change_buffs` 的实际局部顺序是缓存target / owner，销毁旧实例（`0x1417af0be`），再调用 `scr_effect_create` 创建新状态（`0x1417af1f8`）；不能将名字中的change解释成无损原地换类型。证据见 [治疗侧共享替换助手](../../../_reference/stoneshard-study/eighth-treatment-disassembly/gml_Script_scr_inst_change_buffs.txt)。这些事件读取恢复后的值，没有在此证明所有恢复来源、每回合恢复量或替换时所有实例字段怎样复制；完整恢复与治疗由其他模块处理。

## 8. 属性真正怎样汇总、消费和撤销

### 8.1 状态贡献先重建再相加

共享 `scr_player_buff_buffer(0x140fe5310)` 清空单位 `buffer_buff_data`（`0x140fe5575`），遍历活动 `buffs`，在有效实例 / 地图等门槛成立时调用 `scr_buff_buffer_add`（例如 `0x140fe5af7`）。该助手逐键把状态data加入缓冲，主要相加 `0x140fe87d0`、写回 `0x140fe8870`，见11。

```text
clear(unit.buffer_buff_data)
for eligibleState in unit.buffs:
    for key,value in eligibleState.data:
        unit.buffer_buff_data[key] = oldContributionOrZero + value
```

这解释了多部位贡献可以累加；不会因为同一状态事件再执行一次，就必然在单位上永久再扣一遍。实际状态数据重建、有效列表及消费者时序仍需分开判断。

### 8.2 至少一个生产者到实际字段的闭环

`scr_atr_calc(0x140b66380)` 的命中局部路径：

```text
injury.data["Hit_Chance"]
  → activeBuffs 的逐键加法缓冲
  → scr_buff_param("Hit_Chance")
  → Hit_Chance = clamp(bHit_Chance + buffContribution, 5, 150)
```

基础字段读取 `0x140b6d3b3`，输出字段选择 `0x140b6d3c9`，读取缓冲助手 `0x140b6d420`，相加 `0x140b6d45d`，界限常量5 / 150在 `0x140b6d49a / 0x140b6d4bb`，clamp调用 `0x140b6d506`。这段不是仅根据字符串推测的“减命中”，而是实际字段的加法应用。后续 combat / 装备路径仍可修正最终攻击参数。

EVS局部也读取 `bEVS` 与 `scr_buff_param("EVS")` 后相加，读取 `0x140b6c102`、加法 `0x140b6c13f`、写字段 `0x140b6c156`。

`scr_buff_param(0x140fc2fc0)` 通过单位缓冲map查传入键（`0x140fc319b`），处理缺失 / 指针分支并返回结果。不能把它当作“任何缺失键都必然0”的通用承诺：这个具体助手有不同哨兵回退路径。本文算例只使用已经实际写入且存在的键。

`scr_inv_buff_atr(0x1416b1a20)` 对指定键读取装备贡献与状态贡献，在 `0x1416b1bed` 相加后返回。字段最终可能再作为倍率、被限定或取整，所以 `max_hp` / MP分数并不自动等于最终直接扣点。

### 8.3 撤销与清理

伤势基类 `o_wound_debuff.Create` 写 `have_duration=false`（`0x1443e414f`），因此不能套用普通有持续Buff“时间扣到0就结束”的规则。伤势还会通过 Condition 变化、等级替换或明确销毁退出。

通用状态销毁沿既有链从 `target.buffs` 删除自身id（`0x1443550a4`），并置 `stats_is_change=true`（`0x1443550de`），见11；随后缓冲重建将不再纳入已移除对象。这是贡献恢复的主要已确认结构，不是销毁时把表内每个数值立即反向加回单位。

普通 deep父类另清理玩家装备槽的 `wound_block`，写假值在 `0x1443f487c`，与进入严重伤势时的槽锁定配对；head3自身又执行两张锁定列表的删除。事件继承调用在 Destroy 开头存在，专属清理不能替代通用活动列表解除登记。

本轮没有证明属性重算的精确帧、实例替换保存的所有字段、所有 GUI / map 资源释放及重复清理幂等性；不据此宣称没有状态残留或内存泄漏。

## 10. 独立设计借鉴与风险

可借鉴“部位状态、伤势等级、属性贡献、额外行为限制、治疗稳定标志”各有自己的数据和生命周期。稳定治疗可以保留基础伤势减益，同时移除持续疼痛 / 特殊副作用；恢复改善后再降级。这些层分开，更容易解释治疗到底改变了什么。

自研时应为每个属性声明单位与聚合方式，把百分比贡献、百分点、整数资源和乘数分开；每个行为锁以来源token登记 / 注销，避免把列表索引和来源身份混为一谈。若希望稳定伤势减益减半，需要自己明确规定并验证，它不是本机已确认的原作规则。

本轮未运行游戏、未改游戏或存档、未复制专有代码 / 资产到生产实现、未提交或推送。没有运行测试；执行了静态数据绑定与文档核对。剩余风险是复杂消费者、事件继承与替换上下文的覆盖缺口，尤其分数键和专属副作用的最终效果。
