# 战斗回合、伤害结算与触发链

[返回拆解目录](README.md) · [技能执行](10-combat-skill-execution.md) · [Buff](11-buffs-and-effects.md) · [召唤](12-summoned-units.md) · [预告攻击](13-telegraphed-attacks.md)

本篇解释这些模块怎样接到共同的回合和伤害入口。新增证据来自同一个本机 EXE 的静态指令与 data.win 对象索引。能确定若干局部计算、调用关系和状态写入；完整命中概率、全部抗性、每种攻击的最终伤害仍未恢复。所有数值演算均为构造输入，不是实战测量。

部位抽选和伤势的后续见 [25 身体部位与肢体伤势](25-body-part-hit-selection-and-injuries.md)：已把默认/限定部位选择、部位防御接入、汇总伤害、Condition、伤势等级和流血局部入口连起来；完整 HP 终值与全部护甲公式仍保留缺口。

## 1. 三种时间不要混在一起

| 层 | 已见状态和入口 | 能解释什么 | 不能直接解释什么 |
| --- | --- | --- | --- |
| 全局逻辑处理 | `scr_global_turn`、`scr_global_turn_end`、`turns` | 回合流程、时间更新、延迟技能消费 | 一个函数名就代表全部战斗回合契约 |
| 单位和状态阶段 | `scr_unitTurnEvents`、`scr_unitTurnBreak`、状态持续时间和冷却表 | 单位事件、状态阶段、技能冷却更新 | 所有 Buff 都在同一个位置减一次 |
| 表现和排程 | `alarm[1]`、`alarm[4]`、动画与动作阻塞 | 等待动画、安排后续事件、协调动作 | 数值 20 就代表 20 回合，或数值 1 就代表下一逻辑回合 |

这是本次最关键的边界。巨魔延迟攻击既有逻辑回合倒计时，又有表现 alarm；逻辑释放和真正命中格内单位也分处不同对象。详见 13 的完整例子。

### 玩家后续事件的排程

`scr_unitTurnNext`（`0x141699be0`，第一范围 1239 字节）使用对象选择值 **5376**。完整 OBJT 指针索引确认它对应 `o_player`，父对象是 3804 `o_unit`，不能只根据函数名将其解释为“所有单位”。

可确认的行为：未提供有效第一参数的相应默认分支写 1；`Upspeed` 条件也能将参数改成 1。随后把该值写入选中玩家的 **alarm[4]**（`0x141699fcd`，索引 4 的写助手）。这是安排事件的值，不是把全局回合计数加一。

`scr_unitTurnGetTime`（`0x1416a2830`，677 字节）同样选择玩家：读取 alarm[4]（`0x1416a2982`）和 alarm[1]（`0x1416a29a5`），交给最大值助手（`0x1416a29df`）；没有选到实例的路径返回 0。

```text
局部行为规格：
    若没有可选中的玩家实例：返回 0
    否则返回 max(player.alarm[4], player.alarm[1])
```

**例子：**构造玩家 alarm[4]=3、alarm[1]=8，此入口得到 8；改为 12 和 8，得到 12。它并没有说明这两项分别需要多少现实毫秒，也没有证明“本回合剩余 8 步”。若存在多个选中实例，with 迭代与返回覆盖行为还需专门核对；正常单玩家例子不覆盖异常多实例情况。

### 全局计数的真实加法

`scr_global_turn`（`0x1416c2a60`，12514 字节）在 `0x1416c4651` 取得 `turns` 的写访问，随后以整数 1 调用 `0x14000bd90`（`0x1416c4665`）。独立核查这个助手，有限数值路径包含 `addsd`，整数路径包含 `add`，支持该块做 **turns += 1**。

例子：进入这一个更新块时 turns=42，正常有限数路径写成 43。这不表示调用该函数的每种早退或异常路径都一定完成更新，也不表示每次渲染帧都会调用它。

该函数还调用游戏时间处理。`scr_timefreeze` 的结果在 `0x1416c391f` 后进入分支；真路径跳过包含 `scr_timeUpdate`（`0x1416c3a4d`）的一段。由此能证明“某些时间更新受冻结判断约束”，不能据此宣称冻结时战斗、Buff 和所有 NPC 都完全停止。

## 2. 单位事件和回合收尾怎样连接

`scr_unitTurnEvents`（`0x1416a13b0`，3526 字节）的选定范围有以下直接调用：

| 调用位置 | 目标 | 本轮确认内容 |
| --- | --- | --- |
| `0x1416a1600` | `scr_regen` | 存在再生处理调用 |
| `0x1416a172f` | `scr_states_duration_dec`，实际入口 `0x141ae5c20` | 两参数调用；持续时间与事件阶段详见 11 |
| `0x1416a1af3` | `scr_map_kd_decrease`，`0x141760560` | 一参数调用；冷却表写入见 10，递减规则见下段 |
| `0x1416a1e95` | `scr_unitTurnGetDamageFromTileMark` | 格子效果伤害检查被接入单位事件 |

上表按静态地址组织，并没有抹去两调用之间的条件分支。完整指令解码不代表已证明每一项每次都执行。

### 冷却表的局部递减算法

补充解码 `scr_map_kd_decrease` 的 3268 字节第一范围后，已经确认它枚举当前单位 `map_skills`，对各技能子地图读取 `KD`。读取键使用字符串槽 `0x14987ecf0`，其初始化文本已核准为 KD。第一参数是本次递减量；与 undefined 相等的默认分支将它设为 1（`0x14176090f`–`0x141760920`）。

```text
对当前单位技能表中的每个技能地图：
    k = 读取 KD
    如果 k 与 0 的有序比较为大于，并且 k < 900：
        KD = builtin_round(k - amount)
```

比较零在 `0x141760dbb`，只有正比较结果继续；严格小于 900 的助手调用在 `0x141760df6`。减法在 `0x141760efd`；调用原生 `round` 在 `0x141760f53`，随后 `ds_map_replace` 写回（`0x141760fea`）。这是**原生 round**，不是第 6 节的自定义 `math_round`，本轮没有将二者的半值规则混同。这个更新段也没有 max(0,...)，不擅自添加下限截断。

**例子：**构造四个技能的 KD 为 0、2、899、900，amount=1。前者不进入递减；中间两个写 1、898；900 不满足严格上界，保留原值。该上界的业务含义可能与特殊值有关，但未核准，不能直接命名为“永久冷却”。若非整数递减、amount 超过当前值或表结构异常，需继续检查原生 round 与调用方契约；整数例子不覆盖它们。

`scr_unitTurnBreak`（`0x14169a780`，15180 字节）提供另一层真实调用关系：

1. 在 `0x14169abf5` 调用 `scr_global_turn_end`（`0x1419c0e50`）。延迟攻击的共享父类在这里消费逻辑持续时间，详见 13。
2. 后续范围包含若干 `scr_duration_decrese_simple` 调用、单位状态处理、`scr_states_duration_dec`（`0x14169b8be`）、属性重算与伤害进度处理。
3. 较后范围在 `0x14169d82f` 调用 `scr_global_turn`。
4. 还存在新的后续排程、`buffs_is_change` 和 `buff_end_turn` 字段。

这证明收尾、状态更新和全局处理有共同调用者。不能单凭地址顺序把全部路径压成无条件的直线流程，也不能直接确定“技能创建的那一轮是否已消费第一次持续时间”。要证明画面上恰好隔一个玩家回合，需要记录技能创建、两次有效收尾、释放和玩家动作的运行顺序。

**回合例子：**某延迟技能创建后 `skill_duration=2`。假定主人有效、门禁连续通过，则两次有效收尾消费为 `2→1→0`，第二次触发释放。这是指令支持的倒计时演算。如果第一次发生在创建当轮末，玩家可在随后一轮行动；若第一次更晚发生，显示等待跨度会不同。不能把这个起算假设隐藏起来。

## 3. 预告格与通用格子效果的两套路径

`scr_unitTurnGetDamageFromTileMark`（`0x1403b9fd0`，5006 字节）选择 **5409 `c_tile_mark`**；巨魔技能研究的 **5677 `o_skill_aoe_zone`** 是另一个对象。二者不能因为都画在地图格上就合并为同一机制。

在通用入口中已确认：

- 读取待处理单位的 `is_flying`；飞行路径包含对象继承判断，其完整排除名单未恢复。
- 将 marker 的 `position_check` 真值与可选第一参数真值作阶段匹配。若参数为真，则需要 position_check 为真；参数为假，则要求 position_check 为假。匹配失败跳过该 marker（`0x1403ba531`–`0x1403ba5b0`）。
- 读取 marker 的 `delay`（`0x1403ba6b8`），经真值转换后若为真跳到下一 marker（`0x1403ba6ce`）。这段是**消费门禁**，没有证明 delay 在这里递减。
- 门禁通过后才进入 `placelist`、格坐标与占位关系处理；命中分支在 `0x1403bafaf` 把单位 id 写入 `targ`，再以 user 索引 7 调用事件助手 `0x1451ef5b0`（`0x1403bafdc`）。助手把索引加 10、事件类型设为 7，故对应本机 Other17。完整坐标编码、该事件所有子类覆写与最终伤害仍需要继续追。

```text
有限范围行为说明：
    对每个选中的 c_tile_mark：
        若 position_check 与本次阶段参数真值不匹配：跳过
        执行适用的飞行/对象过滤
        若 truth(marker.delay)：跳过
        继续处理 placelist 与单位格位置
        命中分支写入 targ 并触发 marker 的 Other17
```

**例子：**构造三个 marker，阶段参数为 false。A 的 position_check=true，即使 delay=false 也跳过；B 的 position_check=false、delay=true，跳过伤害候选处理；C 两者均为 false，能进入候选处理，但仍须通过飞行、格位置及其他分支，不能保证伤害必然发生。

巨魔的格子预告则形成另一条链：技能主体释放和动画结束 → 父 Destroy 给相应 `o_skill_aoe_zone` 排 alarm[1] → marker 查当前格内实例 → 去重并设置执行上下文 → 调用该技能对象的 Other10 → 技能伤害入口。13 给出每一步的实际对象和地址。本篇的通用 delay 门禁不能用来替代那条已核实的释放链。

## 4. 伤害分层：多类型计算、实际扣血与后置反应

第九轮进一步沿真实剑配置和普通攻击处理器继续，详见 [32 物理剑击](32-physical-attack-damage-resolution.md) 与 [35 攻击结果与事件](35-attack-results-and-event-order.md)。已恢复Slashing七实参、实际目标格挡预算、部位防御/抵抗字段选择、多标志结果优先顺序和HP局部下界/保护。下面保留第三轮调查历史；“尚未完成实参命名”不再表示新增32的选定类型也未知。

新增静态检查覆盖这些入口，而非仅按名字列候选：

| 入口 | VA / 第一范围大小 | 实际观察 |
| --- | --- | --- |
| `scr_damage_init` | `0x141048ab0` / 1527 | 处理 Weapon、Slashing、Piercing、Blunt、Fire、Frost、Shock、Poison 等伤害字段及穿透字段 |
| `scr_damage_calculation` | `0x141250670` / 60338 | 类型伤害、格挡、身体部位、伤害进度、被动和效果等多个直接调用 |
| `scr_damage_type_calc` | `0x1412f6ea0` / 2440 | tmpDEF、除乘减、下界最大值、math_round；尚未完成全部实参命名与共享常量初始化 |
| `scr_damage_block_calc` | `0x1412f8260` / 1267 | 局部除乘减、max/min，累加 `_tmpBlockReduction` |
| `scr_damage_with_calc` | `0x1412bf0e0` / 5743 | 计算、身体部位、simple_damage、Buff 调用和伤害日志 |
| `scr_physical_damage` | `0x141291910` / 6088 | simple_damage、吸血/吸魔、被动与 on_damage_method 字段 |
| `scr_pure_damage` | `0x140194010` / 3724 | math_round、simple_damage、伤害信息与日志 |
| `scr_simple_damage` | `0x141227f30` / 9623 | HP 修改、上次攻击者、敌人受击触发、NPC 犯罪反应及伤害后回调 |
| `scr_unit_try_invoke_post_damage` | `0x140179730` / 2704 | owner、方法/结构字段判断与 perkTriggerCall |

这些都是本机确定的静态关系。`pure` 这个名字并不能单独证明所有护甲、护盾和 Buff 都被绕过；`simple` 也不意味着只减 HP，实际还连接了角色和 AI 的行为。各技能是否经过某入口，要以该技能的调用链为准。

### 一条真实扣血路径

在 `scr_simple_damage` 的选定路径中：

1. 伤害值经过 `math_round`（`0x1412289be`）。
2. 读取 HP（`0x1412289df`–`0x1412289f5`），保留原值。
3. 以 HP 的写引用和已经准备的伤害值调用减法助手 `0x140005a10`（`0x141228dec`）。这个助手的有限数值分支已确认 `subsd`。
4. 后续分支可以再次写 HP，例如保护路径恢复旧值（`0x14122918f`）或特定路径设为 1（`0x141229653`–`0x141229664`）。`playerGodMode` 等字段也被检查，完整条件组合未恢复。
5. 敌人适用分支调用 `scr_enemy_AI_damage_trigger`（`0x14122a079`）；后续调用 `scr_unit_try_invoke_post_damage`（`0x14122a1f0`），后者涉及属性/技能触发回调。

**例子：**进入普通扣血路径，原 HP=50，已准备伤害=12，减法块产生 38。若随后进入恢复 HP 的保护分支，最终结果不一定是 38。所以准确规格应写“普通路径在减法块得到 38”，不能把它当成所有技能的最终 HP 公式。巨魔技能的 Blunt_Damage 也属于更早的伤害输入，不能直接从玩家 HP 中扣相同数值。

受击引发 NPC 犯罪判断属于**游戏内状态**。静态看见 `scr_npc_attack_crime` 的调用，不能推出它联网报警；网络行为本轮没有监测。

## 5. 一个已拆出的格挡局部计算

`scr_damage_block_calc` 接收至少一项必需值及可选参数。暂用零基序号 A0…A3，避免把未核准的参数硬标成“伤害百分比”“格挡效率”。有限正常数值且参数完整时，本段运算可表达为：

```text
q = A0 / A2
b = max(A3 * A1 * q, C)
result = max(C, A0 - b)
_tmpBlockReduction += min(A0, b)
```

C 是共享 RValue `0x1498722e0`。已定位本段引用，但没有完成其全初始化/写入生命周期，故这里**不把 C=0 提升为指令确认的最终配置**。缺参数、除零、非数值及 NaN 等路径不属于这个有限数公式覆盖。

关键步骤：除法 `0x1412f83b0`；乘法 `0x1412f845e` 与 `0x1412f8498`；下界 max `0x1412f84fc`；原值减 b `0x1412f8559`；min `0x1412f85f8`（助手 `0x1451de510` 在 `0x1451de5ab` 比较并保留较小值）；累计减免 `0x1412f860e`；结果下界 max `0x1412f8678`。

**带明确假设的演算：**假设 C=0，输入 A0=40、A1=0.5、A2=2、A3=1。q=20，b=10，result=30，累计减免增加 min(40,10)=10。若累计字段原为 7，则该块后为 17。第二组 A1=3 时 b=60，结果下界截成 0，累计减免增加 40。这说明累计量对本次减免设有原值上限。它不是游戏中某件盾牌的真实属性测量，也没有证明最终总伤害等于该返回值。

`scr_damage_type_calc`的选定Slashing实参和穿甲/抵抗局部公式现见32，格挡实参依次绑定为斩击分量、目标格挡预算、格挡前总基数和本次类型常数1。其他类型与共享C初始化仍须分别恢复；本节旧A0…A3算例是人工输入，不应当作某件盾牌配置。

## 6. 真正核准的取整算法

本机 `math_round`（`0x141894e50`，1472 字节）并非只凭名字解释的宿主语言 round。输入先经 `string_to_real` 处理；对正常有限数 v，后段等价于：

```text
math_round(v) = sign(v) * floor(abs(v) + 0.5)
```

证据链：`0x141895247` 调用 abs 助手 `0x1451de020`，其掩码 `0x147c643c0` 是 `0x7fffffffffffffff`；`0x141895266` 加常量 0.5（正确映射 `.rdata` 中 `0x145aadc40`）；`0x1418952a6` 调用 floor；`0x1418952e5` 调用 sign 助手 `0x1451de780`；`0x1418952fd` 相乘。掩码和常量按各自 PE 节映射读取，没有把 text 节偏移规则套到 rdata。

| 构造输入 | abs+0.5 / floor | 结果 |
| --- | --- | --- |
| 9.6 | 10.1 → 10 | 10 |
| 19.2 | 19.7 → 19 | 19 |
| 2.5 | 3 → 3 | 3 |
| -2.5 | 3 → 3，再乘 -1 | -3 |
| 0 | 0.5 → 0，再乘 0 | 0 |

这与采用银行家舍入的默认语言 round 在半值处可能不同。自研实现应自己决定规则，并用正负半值例子固定契约。字符串无效、NaN、无穷大等输入还需要检查 `string_to_real` 和底层助手的完整契约，不能由有限数公式补齐。

## 7. 对独立游戏实现的启发

以下是我们的设计建议，不是恢复出的 Stoneshard 源码：用明确的逻辑动作/回合阶段处理技能预备、释放和状态持续时间；表现层只报告动画是否完成。伤害事件携带来源、目标、类型分量和前后 HP，再分别派发 AI 受击、被动、日志与游戏内犯罪反应。这样能解释“有命中特效但没有扣血”和“预告仍在但攻击被取消”等情况。

不要让动画销毁成为自研游戏唯一的伤害真相。可用显式 Resolve/Cancel 状态防止重复释放，并为同次 AOE 的多个格子共享命中集合。原目标实际怎样处理对象销毁、事件和去重，见 13；建议是学习职责和故障模式后重新设计。

## 8. 证据与剩余缺口
