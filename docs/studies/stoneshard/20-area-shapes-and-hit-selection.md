# 范围技能：形状展开、格坐标与命中去重

[总目录](README.md) · [证据范围](00-evidence-and-scope.md) · [预告攻击](13-telegraphed-attacks.md) · [生产与释放](15-telegraph-production-chain.md) · [技能配置与提交](16-skill-commit-and-ai-gates.md)

本篇把 `scr_create_aoe`、单格生产器和格对象执行连起来。新增确认两点：normal 与 pyramid 采用不同的循环计数；单格创建后会立即派发自己的 Step0，完成部分定位，再把实例 ID 交给生成器继续使用。命中去重不是简单跳过整个事件：重复目标被替换成当前格对象自身，后续仍会派发技能事件，但公共范围伤害入口排除这种格对象目标。

没有运行游戏。候选创建数量、合法位置数量、可见提示数量和实际受伤单位数量在本篇始终分开。下面的循环演算不是实战录像，也不是原作源代码。

## 1. 适用制品与本轮证据

沿用 `E:/Steam/steamapps/common/Stoneshard/StoneShard.exe` 与 `data.win`，Windows x64 GameMaker 原生编译制品，资源包没有普通 GML 字节码 CODE 块。根调查复核摘要与既有记录一致：

| 制品 | SHA256 |
| --- | --- |
| StoneShard.exe | d45797505f04b9112c5fbb8e85c0f8cda2fa60aee954b4e108bad8a0dc514afa |
| data.win | 84034525fcdef3c6fd9803628b8de6c43fea479c930e168a95906de37a2ae19c |

本轮使用已有本机 Python 和 Capstone 5.0.9，重读选定函数及少量数值助手；RIP 名称按已核对的 `refVA-8` 布局读取。数字、对象身份、字符串槽初始化和机器指令分别核对。`_reference/stoneshard-study/fifth-aoe-*` 是可再生成、本机可选证据，不是 REA Evidence 会话，也不会随普通克隆自动提供。本文保留足以独立阅读的参数、位置和限制。

## 2. 从具体技能到范围生成接口

两个已确认真实配置是：

| 配置 | Shockwave | Rock_Toss |
| --- | --- | --- |
| 实际表行 VA | 0x145e53910 | 0x145e53830 |
| 表头 AOE_Lenght / AOE_Width | 3 / 3 | 2 / 2 |
| Pattern | pyramid | normal |
| Object | o_shockwave_birth | o_rock_toss_birth |
| 真实持续攻击对象 | o_shockwave，5515 | o_rock_toss，5528 |

表头保留制品的 `AOE_Lenght` 拼写。然而范围施法脚本实际查找的键是 **AOE_Len**（字符串槽 0x149881350，使用点 0x1418707c1 / 0x141870aa5）与 AOE_Width（槽 0x149881360，0x141870802 / 0x141870adb）。本轮没有补齐“原始表头怎样转换成运行技能字典”的全部初始化，所以不能无条件把表中的 3 或 2 当作本轮捕获到的运行实参。下面采用这组真实配置作为参考，运行 L/W 则明确设为构造前提。

`scr_cast_aoe_spell` 入口为 0x14186fd70。0x141870632 的对象常量是 3805，即 o_enemy；0x14187067d 的祖先检查为真后进入敌人相关分支。该分支读取 skill、target、当前实例 ID，查两个范围键，在 **0x141870b64** 调用 `scr_create_aoe`。另一分支检查 o_skill_ico（6423），在 0x141870ca2 调用同一生成器。不能把这两种 self 上下文混成玩家本体，也不能把 UI 的范围预览默认等同为敌人正式执行。

敌人分支传给生成器的局部参数结构可以确认到：

| scr_create_aoe 参数号 | 来源与职责 |
| --- | --- |
| 0 | 该分支读取的 target；随后会被某些循环改写为新格对象 ID，作为下一次创建的关联锚点 |
| 1 | skill 查询 AOE_Len 的结果，本文称 L |
| 2 | skill 查询 AOE_Width 的结果，本文称 W |
| 3 | 上层第 9 号参数，缺省 undefined；生成器用于移动/特殊分支判定 |
| 4 | 当前实例 ID；在选定普通形状循环中没有被继续作为单格第五参数传递 |

所有参数号从 0 开始。`scr_create_aoe` 入口 0x141851c10，先将 pattern 局部值设为 normal（0x14185200c）。若当前 self 存在 skill 字段，再用 skill 和键 Pattern 查询（0x14185231f）。还存在 Schism 特例、circle、five、line、pyramid_shift 和大尺寸/移动分支；本篇只恢复 normal 与 pyramid 的选定路径，不把它们当作所有范围技能的统一规则。

进入下述普通形状分支还有前置门禁：有限值 L 与 10 比较，L 小于该门槛且参数 3 假值才走 0x1418530a3 的普通分支。比较使用既有 epsilon 助手；本篇的 L=2、3 远离边界。L 接近 10、参数 3 为真或其他特殊配置时，下面数量公式不适用。

## 3. 单格生产：创建、赋值、立即定位、返回身份

`scr_create_one_aoe`（0x141858d60）读取参数 2 的 x/y（0x141859161 / 0x141859193），在 **0x14185921b** 创建对象 5677，即 o_skill_aoe_zone。资源记录绝对偏移为 11212992。随后在新实例上下文赋值：

| 单格参数 | 新实例字段 | 地址 |
| --- | --- | --- |
| 0 | owner | 0x141859408 |
| 1 | shift_angle | 0x141859466 |
| 2 | main_owner，且是初始坐标来源 | 0x1418594c4 |
| 3 | is_moving | 0x141859522 |
| 4 | is_start_shift | 0x141859580 |

之后调用 is_player 来设置 owner_is_player（0x14185960f / 0x141859629）。关键的新证据是 **0x141859659**：事件派发参数为 r8d=3、r9d=0，调用 0x1451ef5a0，即 Step0。再在 0x14185968c 读取新对象 id，0x14185969f 写到返回值。

因此，这个接口不是“只产生同坐标实例，等待下一帧才处理”。选定生产链在创建循环内部立即执行一次格对象 Step0，返回已经过该事件的实例 ID。实际 Step0 仍会受 owner、main_owner、is_square、is_moving、is_activate 等门禁影响；立即调用不保证每个实例都成功定位为合法攻击格。

这也解释了范围生成器为什么反复把新格 ID 放回参数 0：普通形状是关联锚点组成的链，实例定位与生成循环互相连接。不能只看到单格初始坐标来自 main_owner，就断言所有格子最终重叠在施法者脚下。

## 4. normal：固定的两侧计数加中心

normal 字符串槽为 0x149880f68，构造在 0x141857224，匹配检查在 0x14185310b；normal 与 line 共用一组循环，line 另把 is_line_pattern 置真。

在普通、有限正整数输入下：

1. 把 L 转成整数，作为外循环剩余次数；可见 `cvttsd2si` 在 0x14185336a。
2. 每排用 W / 2 计算两侧循环次数，除法调用在 0x1418533e4，整数转换在 0x1418533ec。已核对数值助手为除法，有限 double 转换采用截断，故侧计数 h=trunc(W/2)。
3. 每次两侧循环分别创建 shift_angle=-45 与 +45 的格对象，调用在 0x14185357c、0x141853742。
4. 每排再创建一个中心方向格，调用 0x141853951；该方向参数来自槽 0x149880ff8，本文记 S0。
5. 中心实例上下文中的 id 被写回范围生成器参数 0（0x1418539c4），供下一排关联使用。

S0 没有原始字节 backing，本轮未找到其运行初始化。不能把该槽的缺少文件字节解释成数值 0，也不能把中心格擅自画成固定向前一格。两侧常数 ±45 来自实际 RValue 常量 0x14954ce18 / 0x14954ce28；不等于尚未完全核对的世界朝向。

对不发生创建失败、输入变更和特殊分支的这组循环，**单格创建调用数**为：

```text
h = trunc(W / 2)
每排调用数 = 2*h + 1
普通 normal 的总调用数 = trunc(L) * (2*h + 1)
```

这是调用次数公式。它不能证明去重后的坐标数量相同，也不能证明全部格子可见、合法或能伤害一个单位。

### 构造演算：Rock_Toss 的 normal 参考配置

真实表值为 2/2、normal。假设运行查询确实返回 L=2、W=2，参数 3 假，所有创建正常：

| 排次 | 两侧计数 | 创建请求 | 累计 |
| --- | --- | --- | --- |
| 第 1 排 | trunc(2/2)=1 | -45、+45、S0 各一次 | 3 |
| 第 2 排 | 1 | 同样三次；关联锚点已用上一中心格更新 | 6 |

所以是 **6 次候选格创建**，不能由表头 2/2 直接说成 2×2=4 格。若 W=3，则 h 仍为 1；W=4 才使 h=2、每排 5 次。W=3/4 是构造输入，不是本篇对 Rock_Toss 运行配置的观测。

## 5. pyramid：侧计数逐排递减，而非固定宽度矩形

pyramid 字符串槽 0x149880fd8，构造 0x1418572fd，匹配比较在 0x141853b82；匹配成功跳到 0x141853c88。

选定路径先计算 b=L-1（0x141853cb8，减法助手 0x140005910→0x140005a10），外循环次数仍由 L 截断得到。每排执行：

1. 先以 S0 创建中心格（0x141853f45），保存其 ID，并写回参数 0（0x141853f7a）。
2. 用当前 b 的整数部分创建 +45 侧链（0x1418540f1）；每个新格 id 写回参数 0（0x141854158）。
3. 把参数 0 恢复到本排中心格（0x1418541d4）。
4. 再创建同数量的 -45 侧链（0x14185433f），每次更新参数 0（0x1418543a8）。
5. 再恢复中心（0x141854424），把 b 减 1，然后继续下一排；数值递减分支在 0x141854495 / 0x141853e20。

pyramid_shift 在类似路径中把单格 is_start_shift 输入设为 1，pyramid 则为 0（0x141853d73–0x141853d8c）。不能把这两个 pattern 当成完全相同的位置规则。

在有限正整数 L、无失败、普通分支中，侧计数依次 L-1、L-2、…、0，调用总数为：

```text
第 r 排（r 从 0 开始）：1 + 2*(L-1-r)
总调用数：sum(1 + 2*k, k=0..L-1) = L*L
```

本次读取的 pyramid 循环侧计数由 L 决定，没有像 normal 那样在该循环中用 W/2。不能因此宣称整个技能体系的 W 永远无用；W 仍作为接口输入，并在其他 pattern/特殊分支中参与运算。

### 构造演算：Shockwave 的 pyramid 参考配置

真实表值为 3/3、pyramid。假定运行 L=3、W=3，参数 3 假，全部创建正常：

| 排次 | b | 中心 / +45 / -45 请求数 | 累计 |
| --- | --- | --- | --- |
| 第 1 排 | 2 | 1+2+2=5 | 5 |
| 第 2 排 | 1 | 1+1+1=3 | 8 |
| 第 3 排 | 0 | 1+0+0=1 | 9 |

可以确认的是 **5、3、1 的生产请求结构**，不是 3×3 正方形。生成顺序不等于最终画面从远到近的顺序；S0、角度目标、位置门禁及碰撞都可能改变最终格集合，不能在这里编造一张已经实测的九格地图。

## 6. 方向与格坐标：45 度量化、26 坐标间距与中心偏移

o_skill_aoe_zone.Create 的 len_shift 确为 26（0x14415877f / 0x144158789）。其 Step0 入口为 0x144159cc0；多个分支在定位时读取 owner 坐标、main_owner 坐标、目标坐标、is_poly_cell、shift_angle 等。完整目标选择仍有特例，但选定数值支路已恢复：

- 方向助手 0x1451de650 以四个 float 坐标为输入；对同 x 的有限输入，向下差值返回 270、向上返回 90、同点返回 0。常量地址分别为 0x147c647d8 / 0x147113eb8。一般分支调用数学助手，完整异常值与所有输入路径没有恢复。
- 格对象将助手返回的角度 θ 加 22.5，截断成整数，再作有符号整数除 45，乘回 45，减 180，再加 shift_angle。这些运算在 0x14415e159–0x14415e1d5，以及另两条同结构分支 0x14415e339 / 0x14415e3f8。
- 方向量化不是任意角度连续旋转。有限非负 θ 的该路径可写成 `45 * trunc(trunc(θ+22.5)/45) - 180 + shift_angle`。中间先转整数，不能在边界无条件替换成语言默认 round。
- 使用 len_shift 和 angle 求坐标分量，x 助手调用在 0x14415e56d、y 在 0x14415ea52；它们先把角度乘 float π、除 180，再调用数学助手并乘长度，y 还翻转符号。主体符合 cos/sin 分量结构，但本轮未完整恢复内部数学库的所有 CPU 分派、取整接近整数和异常值路径，正文用 Hx/Hy 表示它们实际返回值。
- 在此定位路径，把 `owner.x + Hx(26,angle)` 与 y 对应值按格对齐，再加 **13**；x 的 +13 和写入在 0x14415e95d / 0x14415e9a7，y 写入在 0x14415ee71 后。

`scr_round_cell`（0x145181650）名称容易造成误解：默认尺度 26 写入在 0x14518193a；已读主体先把数值转换成整数，再 `idiv`，然后乘回尺度（0x14518199e / 0x1451819b9）。有限整数输入下是朝零截断的格对齐，不是“四舍五入到最近中心”。例如 299 按 26 对齐为 286，再加 13 得 299；负坐标需保留朝零语义，不直接套 floor。

辅助 `scr_side_point_target`（0x145183870）明确返回 `[26*sign(x0-x1), 26*sign(y0-y1)]`；减法在 0x1451839e9 / 0x145183aad，sign 在 0x145183a0a / 0x145183ace，乘 26 在 0x145183a2c / 0x145183af0。有限 sign 助手 0x1451de780 确认负/零/正返回 -1/0/1。此助手是按轴判断方向，不是把向量除以欧氏长度。

### 两个局部演算

1. **量化演算：**假定该定位分支得到 θ=270，shift_angle=45，则 int(292.5)=292，292 div45=6，6×45−180+45=135。θ=270 和 +45 的常数规则有直接证据；是否某次技能实际选择这组坐标输入没有运行观察。
2. **格坐标演算：**构造 owner=(273,195)，假定已选方向助手返回 Hx=26、Hy=0。原坐标加分量得到 (299,195)，分别按 26 朝零对齐为 (286,182)，再加中心偏移 13，得到格中心 (299,195)，格索引 (11,7)。这解释“间距26、中心13”如何参与定位，但分量输入是构造前提，不是 S0 已确认为 0 的证据。

## 7. 合法位置、可见提示与可伤害目标分开筛选

### 7.1 空間位置门禁不等于完整穿墙规则

Step0 有 owner、main_owner 存在性及活动状态分支。部分路径读取 posgrid，以整数格索引调用 `ds_grid_get_ext`（0x14415ae07）。返回假值时，0x14415ae48 写坐标常数 -2900，随后在 0x14415ae6f 写回 x。它不是在这个位置简单删除格对象。

这证明位置占用网格参与格子的有效呈现/放置处理；还不足以给 posgrid 全部取值命名，也不足以证明“墙后全禁”“射线遇墙终止”或房间边界的完整契约。生成器没有在每次候选请求前统一执行一条已恢复的 LOS 测试。

另有 target_group 筛选：Step0 的 0x14415d2b6 先查当前格对象，再比较其 object_index 与 target_group（0x14415d35f），不等时检查 object_is_ancestor（0x14415d41d）；通过后把 visible 置真（0x14415d49c）。还有 is_visisble_lock、invisible、owner_is_player 和图像缩放路径。所以 visible=false 不自动证明不结算，位置有效也不自动证明可见。

### 7.2 执行时重新查格，并把无效目标替换为自身

格对象 Other11 入口为 0x1441636a0。它从自己的**当前 x/y**查询 `scr_tile_get_instance`（0x14416396e），将返回结果写 target（0x144163988）。不是无条件使用准备时的原玩家引用。

查询助手 0x1417ad390 读取 o_controller（4028）的 posgrid，将输入坐标转换成整数后除 26，并加相应偏移参数，再用 `ds_grid_get_ext` 查值（0x1417ada2b）。它还有空网格、返回对象、不可破坏敌人等分支：例如对象属于 o_enemy 且 Unbreakable 为真时，返回 -4（0x1417adba8）。本篇没有恢复全部网格生产与多格单位的登记方式，不能假定一格永远只覆盖一个小单位。

Other11 后续把 undefined、实例不存在、不满足 scr_can_be_broken 或特定不可破坏场景的 target 替换成当前格的 id。例如 scr_can_be_broken 调用 0x144163efd；该局部拒绝路径在 0x1441641d3 写回自身 ID。o_abstract_stuff（5286）与 o_transitions_door（5289）有额外 can_broke 检查。它们是目标资格过滤，与位置网格过滤属于不同阶段。

### 构造演算：提示位置还在，执行对象却变了

设提示格中心 Q=(299,195)，准备时单位 A 在 Q。若结算时 A 移走、单位 B 占 Q，Other11 查询当前网格后得到 B，并继续资格/重复检查；若网格没有可用对象，则转为格自身的 target。Q 坐标与 A/B 位置是构造输入。是否该技能提示格此前跟随移动，须结合第 15 篇状态分支，不能由本例保证永久锁格。

## 8. 伤害去重：线性查询、同归属传播、哨兵目标与公共排除

Create 在 0x1441588e2 取得 target_execute_array 字段，经 array_create（0x144158916）初始化。`scr_skill_check_target_repeat`（0x14027b9b0）读取**当前 self 的数组**（0x14027bd92），查 array_length，从索引 0 开始扫描；用参数 0 与数组元素比较（0x14027bf4a）。匹配后将局部许可改为 false（0x14027bf7e）；没有匹配则保留 true。

格 Other11 在 **0x1441642eb** 调用它，参数为当前 target、false。第二参数 false 的这个调用只查询，不在助手后半段执行它另有的插入路径。

查询通过时，调用者遍历当前格 object_index 的实例（通常 o_skill_aoe_zone 5677），仅筛选 `main_owner==other.main_owner`（0x1441643c4）。向每个匹配实例的 target_execute_array 推入本次 target（0x144164498）。筛选没有再比较技能名、spell 或独立攻击 ID。

查询失败时，它在 **0x144164558** 把 target 写为本格 id。**事件没有到此 return**，仍继续调整 owner、角度并按 spell 派发技能 Other10（0x1441648d0）。这与“重复目标令整个技能事件完全不执行”不同。

公共 `o_aoe_spell.Other10`（0x143e49520）读 target.object_index；若等于 5677（0x143e49664），或等于 o_attacked_target 的 5287（0x143e496e7），跳到 0x143e498e9，绕过公共 `scr_skill_damage` 调用 0x143e497ec。所以本链的自 ID 哨兵最终被公共范围伤害排除。技能子类仍可能在父调用前后做自身逻辑；本篇没有证明重复事件绝无任何副作用。

### 构造演算：同一大目标落在两个提示格上

构造两个格 G1、G2，类型均为 5677，main_owner 均为 M，数组都为空；当前格查询都返回同一目标 B：

| 步骤 | G1 | G2 | 对 B 的影响 |
| --- | --- | --- | --- |
| G1 执行查询 | B 尚未登记，许可 true | 尚未执行 | G1 保留 target=B |
| 传播登记 | 数组加入 B | 数组也加入 B | 两格共享“已处理B”的事实 |
| G1 派发技能 | 以 B 进入技能事件 | — | 满足其他条件时接公共伤害 |
| G2 执行查询 | — | 查到 B，许可 false，target←G2.id | 原 B 不再作为该格的伤害目标 |
| G2 继续派发 | — | 公共父事件见目标类型5677，绕过 damage | 不能说整个事件没有执行 |

这给出了两个格对同一目标的具体去重链。不知道原作 posgrid 怎样登记所有大型单位，所以“大目标覆盖两格”是构造前提。去重作用域目前是**同类型、同 main_owner 的存活格对象数组**，不是已验证的“每次攻击独立集合”。同一施法者并存两种技能、数组何时清空、反复迭代、多段攻击应否再次伤害，都不能从此局部链直接推导。

## 9. 两个具体技能怎样接入结算

将本轮局部形状和前轮释放证据连接起来，可得到这两份有边界的行为规格：

### Shockwave：配置 pyramid，格执行后接钝击输入

1. 配置表指定 pyramid、范围表值3/3、o_shockwave_birth。普通敌人范围施法分支查询运行 AOE_Len/Width，进入生成器。
2. **若运行 L=3 且普通门禁满足**，pyramid 产生5、3、1，共9次候选创建；单格即时 Step0 与格门禁决定最终位置。
3. 出生效果生产 o_shockwave；逻辑等待、释放及状态销毁后，由父 Destroy 安排归属格的 alarm[1]=1，格 Alarm1 派发 Other11，具体时序见15。
4. 每格按当前坐标查目标，过滤并传播去重；若得到可用且未重复的 B，在格上下文派发 Shockwave.Other10。
5. 子类局部钝击输入为 `30*(1+0.1*d)`，读取距离调用在0x143ff1457，写入0x143ff1525；继承公共父事件后接 `scr_skill_damage`。构造 d=2 时输入36，最终掉血仍取决于公共护甲、抗性等计算。

这里未知的桥包括原表头到运行键转换、最上游巨魔事件触发，以及从具体9个候选到最终9个不同合法坐标的全部条件。不会把这些缺口补成“实战必定九格”。

### Rock_Toss：配置 normal，飞行落点驱动格结算

1. 配置表指定 normal、表值2/2、o_rock_toss_birth。若运行 L=2/W=2且普通门禁满足，normal 是6次候选创建，不直接等于2×2。
2. 出生效果缓存目标位置到 point，释放时创建石头及独立终点；飞行目标身份与原玩家身份分开，见15。
3. 石头在终点碰撞门禁通过后派发 Other11，销毁投石状态，父 Destroy 接到格结算。
4. 格 G1 首次选 B 后向同 main_owner 的其他格数组登记；G2 再选B时改成自 ID，公共父伤害入口排除G2。
5. 有效目标的局部钝击输入为 `60*(1+0.1*d)`，距离调用0x143ffef9e，写入0x143fff03d，继承派发0x143fff096。构造 d=2 时输入72；不是对所有候选格各扣72点HP，也不是实测伤害。

本例把真实技能身份、条件形状规则、生产与释放、按格选目标、去重、伤害输入串起来，同时保留几何/运行实参/最终伤害的独立未知。

## 10. 独立设计建议与目标算法的区别

我们可以借鉴按阶段拆分职责，但不照搬事件、数值或原代码：

- 用显式格集合表示形状，分别保存候选、合法位置、可见提示与可命中目标。可以选择在生成时去掉重复坐标并记录拒绝原因；目标目前确认的是循环产生实例再由事件处理，没有证明同样的纯集合接口。
- 在自研中规定宽参数是总宽、半宽还是侧链数。原作 normal 的已读公式会使W=2和W=3拥有相同侧计数；若产品希望精确偶数宽，必须自己定义中心偏移和左右不对称规则。
- 用独立 attackId 作为命中去重作用域。目标局部传播筛选是对象类型和 main_owner，尚未证明每次技能隔离；自研不应把这个局部事实当成安全契约。
- 明确“每次伤害阶段一次”“每整个技能一次”“每次脉冲一次”的去重寿命，并把控制/取消清理与命中清理分别记录。目标其他 iteration、多段、反射分支仍待核。
- 把方向量化、格尺度、中心偏移、负坐标取整作为可测试的纯数值契约。选择朝零截断还是floor属于自研决策；不要因函数名叫round就误写算法。
